# AirPlay 全量强制走「cliairplay + Sendspin 桥」— 对齐方案（2026-10-31）

> 对标基线：[MA-AirPlay-完整数据标准-2026-10-31.md](./MA-AirPlay-完整数据标准-2026-10-31.md)
> 本文件只写方案，不改代码；所有参数与验收判据都以基线文档为准。
> 现状版本：MusicFlow v4.10.7（230 本地 `507ed2d7`）。

## 范围（用户口径，先钉死）

**要强制走桥的对象：所有 AirPlay 设备的音乐播放**，覆盖三种场景：

1. **单独播放**：只投一台 AirPlay 设备；
2. **混合组**：组内同时有 AirPlay + DLNA / Sendspin 成员；
3. **纯 AirPlay 组**：组内只有 AirPlay 成员。

**不涉及其他播放器**：DLNA、Sendspin/ESPHome 等非 AirPlay 设备的出流路径保持原样，不并入桥，也不因本方案改动。

**明确不在本方案范围**：TTS / 播报（`dlna/announce.ts` 的一次性 `streamUrl` 直投）。它不属于上述三种音乐播放场景，继续走原路径；若要纳入需另立方案。

## 0. 名词对齐（先钉死，避免跑偏）

| 说法 | 在 MusicFlow 里的真实对应物 |
| --- | --- |
| MA 的 `cliairplay` | MA 外部 C 二进制：provider 以 `--latency <depth_ms>` 起进程，PCM 从 stdin 灌入 |
| **MusicFlow 的 CLIAIRPLAY（定死规矩）** | 本项目**唯一的 AirPlay 发送端实现**：AP1 走 `backend/src/services/airplay/raop.ts`，AP2 走 `backend/src/services/airplay/ap2/ap2Stream.ts`，两者同属 airplay 子进程、同一会话入口 |
| 「Sendspin 桥」 | sendspin 组泵（唯一 PCM 源）→ MFAB bridge socket → airplay 子进程（CLIAIRPLAY）→ 设备 |
| 「强制走桥」 | AirPlay 设备的**所有音乐声音只允许来自组泵**；任何「设备直连 / 逐曲 solo cast」路径都不得存在 |

**定死规矩（不可协商）**

1. **AP1 / AP2 统一使用 CLIAIRPLAY**，不允许第二套 AirPlay 发送实现并行存在（不引入 shairport 旁路、不再新增直连 RAOP/AP2 引擎）；
2. CLIAIRPLAY 是本项目的内建统一发送端（非外部二进制），AP1/AP2 只是它的两条协议通道；
3. 本方案要做的不是「换发送端」，而是**把 CLIAIRPLAY 的唯一上游收敛到 Sendspin 桥**——发送端不变，喂给它的 PCM 只能来自桥。

因此本方案的落地口径是：**AP1/AP2 仍由 CLIAIRPLAY 统一输出（定死），同时所有 AirPlay 音乐播放（单独 / 混合组 / 纯 AP 组）的 PCM 唯一来源改为 Sendspin 桥。**

## 2. 目标架构（单一出口）

```
QueueController / 外部播放入口
        │  （唯一注册点）
        ▼
AirPlay Bridge Player（单机 = 单成员伪组；多机 = 用户组）
        │  prepareBridgeRoute / bridgeJoinMember（逐设备协议：raop | ap2-realtime）
        ▼
Sendspin 组泵（48k 单时间线，唯一 PCM 源）
        │  MFAB bridge socket（28B 帧头 / 水位 / BOUNDARY）
        ▼
airplay 子进程发送端（raop.ts / ap2Stream.ts）
        │  RTP seq/ts 唯一时间线
        ▼
AirPlay 设备
```

**不变量（任何阶段都不得破坏）**

1. 一台 AirPlay 设备在同一时刻**只能有一个 PCM 上游**（桥）；
2. AirPlay 设备的**音乐播放**（单独 / 混合组 / 纯 AirPlay 组）只允许走桥，不新增第二条直连通路；TTS 播报与其它播放器不在此列；
3. 桥失败 = 本次播放显式失败（可观测、可重试），**不静默回落直连**；
4. `MUSICFLOW_AIRPLAY_BRIDGE=0` 只保留为整体回滚开关，不作为逐设备旁路。

### R1 收口「单机注册点」：单机 = 单成员伪组

- 位置：[QueueController.registerAirPlayDevice](file:///workspace/MusicFlow/backend/src/services/player/QueueController.ts#L300-L309)

### 4.3 自动换歌（最容易做错）

**MA 基线**：不 FLUSH、不 RECORD、不断流；seq/ts 连续；缓冲不动；元数据走 4515 `SET_PARAMETER`；边界音频首尾偏差 ≤8 ms。

**MusicFlow 现状**：v4.10.7 在 `track` 边界置 `explicitReanchor=true`，触发 **FLUSH + RECORD**（[bridgeSession.ts](file:///workspace/MusicFlow/backend/src/services/airplay/bridgeSession.ts#L1182)、[raop.ts](file:///workspace/MusicFlow/backend/src/services/airplay/raop.ts#L1300-L1306)）。这是**最严重偏离**。

**改造分两级（诚实拆分）**：

- **P1 结构级（可先达标）**：`track` 边界不再走 `explicitReanchor`；桥保留同一 RAOP 会话、seq/ts 继续推进，只做「内容替换」；旧曲未播完的余料从 outBuf 出清；新曲首帧映射到「已发 ts 的下一个位置」。达成：**0 FLUSH、0 RECORD、seq +1、ts 连续、缓冲仍 88,200**。
- **P2 听感级（≤8 ms 边界空档）**：需要泵侧在旧曲结束前已解出下一曲 PCM（下一首预热/交接），否则内容替换瞬间 outBuf 见底，空档会大于 8 ms。现状 `playCore` 每次换曲先 `pump.stop()`（[playerCore.ts](file:///workspace/MusicFlow/backend/src/services/sendspin/playerCore.ts#L283)），因此 P2 必须做「下一首预解码 + 同时间线拼接」。

> 不允许用「发静音续流」冒充换歌连续：MA 的边界是**真实内容**连续，静音垫片会把 ≥20 ms 空档留进抓包判据。

### 4.4 用户操作（next / prev / seek）

**MA 基线**（17 次实测）：每次操作**恰好 1 次 RTSP FLUSH**，**永不 RECORD**；中断 48–160 ms（p50 ≈85）；seq +1；ts 回拨 **1.588–1.695 s（p50 1.662）**；缓冲仍 88,200；连续操作不合并。

**MusicFlow 落点**：

- 用户操作路径只允许调用 [RaopPlayer.flush()](file:///workspace/MusicFlow/backend/src/services/airplay/raop.ts#L1412-L1441)（发 RTSP FLUSH），**不得**调用 `reanchorForNewStream`（FLUSH+RECORD）；
- 新流首个可听帧的 RTP ts 相对上一包回拨 1.6–1.7 s（实现上可按「新锚点 − 1.662 s」定标，再以抓包复核）；
- 连续 N 次操作 = N 次中断，不合并、不吞操作；
- seek 不允许完整重建会话（当前 `seekAirPlay` 的「重建」分支在桥模式下必须禁用）。

### 4.5 投递窗口 / bulk 的澄清（避免误伤已修复的曲中失声）

基线文档 §6 把「6 s bulk 灌注」列为 P2 偏离。**本方案不完全照搬**，理由：

- `ts_head − ts_player = 2.000 s` 是**设备侧缓冲**（由发送端 `--latency`/hold 决定），与**发送侧本地 outBuf 深度**是两回事；
- MA 的 cliairplay 自身 ring ≈4 s、上游 ffmpeg 管道 ≈5.7 s（见 MA `constants.py` 的 late-join 推导），发送侧本来就很深；
- v4.10.7 的 6 s bulk 是「曲中失声」的根因修复（[bridgeSession.ts](file:///workspace/MusicFlow/backend/src/services/airplay/bridgeSession.ts) + [server.ts](file:///workspace/MusicFlow/backend/src/services/sendspin/server.ts#L831-L1153)）。

**结论**：只要抓包满足 `ts_head − ts_player ≡ 88,200` 且 `gap ≥20 ms = 0`，**保留 bulk**；不为了「看起来像 2 s」去砍 outBuf。基线的 2 s 约束落在设备水位，不落在本地队列。

   D1「窗口感知垫片」（窗口 `lo/hi` 与 `anchorUs` 两侧同时认 pad）是它的最小前置项，二者不可只改一侧。

**本轮发现但不在本方案范围的缺陷（仅记录）**

- 组 `stop` 后 tracker 仍按旧位置外推到 overrun → 自动 `advance` **再起播**（混合组 `stop` 后 68 s、纯 AP 组 `stop` 后 9.8 s
  各出现一次新 `ANNOUNCE/RECORD`）；`PAUSED` 态下 `/peers/{group}/stop` 返回 200 但状态不变，需先 `POST /peers/{id}/play`（resume）
  再 `stop`，或直接 `POST /peers/{id}/reset`（本次收尾用 resume→stop→reset，实测回到 `STOPPED / idx=-1 / items=0`）。
- 测试收尾状态已核对：`全屋` = `STOPPED`、`volume=20`、队列空；HiVi 与 230-AP1 均 `STOPPED/vol=20`；临时纯 AP 组已删除。

## 9. P2 实施设计（下一阶段执行清单）

> 依据 §8.5.4 / §8.6 实测：现状边界 = 「换代 + 清队列 + 垫片丢头」，可听损失 0.41–1.26 s，距基线「边界 ≤10 ms」差两个数量级；
> 且 A/B 已证 **垫片是承重件**（`BRIDGE_TRACK_LEAD_WARM_MS=0` 首次暖边界即踢会话）——它是「拿新曲开头 Δ 秒换 Δ 秒队列深度」的权宜机制，不能直删。

**P2 完成时必须同时成立的不变量**

1. 边界前后 RTP 面不退化：单 SSRC、`seq` 跨曲 +1、`ts` 稳态 +352、`FLUSH=0` / `RECORD=0`；
2. 内容层：边界首尾偏差 ≤10 ms、`gap ≥20 ms` 计数 = 0（基线 §8）；
3. 旧曲尾部、新曲头部**均不裁头**（自然换歌不应出现 `stale` / `drop`）；
4. 冷建会话（airplay 子进程重建 / 设备重连）允许 `cold pad`，且仅限该场景。

**实施顺序（每步独立开关，可单独回退）**

| 步骤 | 落点 | 做法 |
| --- | --- | --- |
| S1 下一首预解码 | [playerCore.ts](file:///workspace/MusicFlow/backend/src/services/sendspin/playerCore.ts#L283) `playCore` / `pump.stop()`、`sendspin/decoder.ts` | 当前曲剩余 ≤ `BRIDGE_NEXT_PREFETCH_US`（建议 5 s，≤ bulk 6 s）时，用**独立解码器**把下一首 PCM 解出，按**沿用当前组游标**的连续 `ts` 写入同一 `pcm:100` ring（`ep` = 下一代）⇒ 边界时刻桥队列里已有 ≥2 s 新曲内容 |
