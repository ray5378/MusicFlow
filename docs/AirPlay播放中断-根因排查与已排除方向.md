# AirPlay 群组播放中断 —— 根因排查台账（逐轮方向 + 发版回溯 + 已排除清单）

> 适用范围：AirPlay（RAOP）设备接入 MusicFlow 群组播放时，出现**播放中卡顿数秒后恢复**、**播放中周期性断流**、或**直接无声且不自愈**。
> 目标读者：后续接手这块代码的开发。**动手前先读 §2**——每一条都花了真机实测才排除，重走一遍的代价是数小时 + 用户失聪。
> 状态：本轮根因已定位并修复（v4.10.0），真机验证中。

---

## 0. 一句话结论

**根因：服务端进程在设备「正在播放」期间消失，且没有对设备发 `TEARDOWN`。**

MUZO 系接收端（HiVi H5MKII / iEAST 等同源）对「服务器突然消失」**不做任何清理**：接收端继续挂在**旧会话**上等旧会话的包。新进程起来后 `ANNOUNCE / SETUP / RECORD` **全部返回 200**（握手 526ms，日志看不出任何异常），但设备的接收线程**没有切到新会话** —— 既不出声、也不发 timing 心跳；等旧会话超时被清掉，设备把接收端一并关断，进入**永久静音**。

> **RTSP 200 ≠ 设备接管。** 协议层接受，不代表硬件接收端已经跟着换了会话。

修复（v4.10.0）三处，缺一不可：

| # | 位置 | 干什么 |
|---|---|---|
| ① | `backend/src/index.ts` | 进程退出（SIGTERM/SIGINT）前先把 AirPlay 会话 **TEARDOWN** 掉，再关 server |
| ② | `bridgeSession.ts` `reconnectRaop()` | 重连时**先 `await oldPlayer.stop()`（真 TEARDOWN）**，再 `new RaopPlayer()`；失败才回落 `forceClose()` |
| ③ | `bridgeSession.ts` 看门狗 | 活性判据从 **ctrl 重传请求** 换成 **timing(NTP) 心跳**，阈值 45s，并加熔断退避 |

> ### ⚠️ 证据状态（2026-10-29 21:00 受控实测后修正，务必先读）
>
> 本节 §0 的「根因」表述**证据不足**，受控复现没能重现，且抓包推翻了「缺 TEARDOWN 致僵死」这一环：
>
> - **未复现**：`kill -9`（跳过优雅关闭，等价于"服务器消失且不发 TEARDOWN"）+ 自动续播 → 设备 20 秒内正常接管（`timing_in` 3→5），**没有静音**。
> - **前提被证伪**：tcpdump `tcp/4515` 实测，`docker restart` 与**手动组级 stop** 两种情况线上 **TEARDOWN 都是 0 个**；桥会话收尾走的是 `sessions: stop token=A` → `prepare token=B`（**新 token 新会话**），不是 TEARDOWN。
> - **已证实**：timing 是可靠活心跳（20 次/分钟，跨 8 次换歌不断流）；「停会话 + 新会话」确实能把无声设备拉回来；45s 心跳看门狗的方向正确。
> - **仍未解决**：2026-10-29 12:12 那次「无声 10 分钟不自愈」的**致病因**依旧 UNRESOLVED（详见 §11）。
>
> 因此三处修复的定性要改：③ 是**唯一被证据支撑**的兜底；①② 只能算「会话卫生 / 恢复动作正确化」，**不得对外宣称是根因修复**。

## 1. 症状分层（先分清在哪一层，别一上来就查代码）

用户一句话只有「卡顿几秒」「不出声了」，但它对应**五种不同层的故障**：

| 层 | 故障 | 客观判据 | 用户感知 | 本项目对应版本 |
|---|---|---|---|---|
| L1 网络 | WiFi 抖动 / 丢包 | ping 丢包率、RTT 抖动、RSSI | 卡顿（短、能自愈） | 从未成立 |
| L2 源 | 音乐源提前断流 / 坏源 | `content-length` 与实收字节对账 | 播 60s 断一次、换源后正常 | v4.8.3 |
| L3 数据面 | 服务端 RTP 停发 / 缓冲被砍 | 服务端 tick `deltaUs`、`silenceChunks`、`leadUs` | 卡顿 / 静音 | v4.9.5、v4.9.6 |
| L4 缓冲 | 换歌空窗 / 接收端就绪窗口 | 换歌间隙 vs gap-fill 窗、`0xE0` 后 2~3s | 切歌吞开头 / 换歌后无声 | v4.7.6、v4.9.6 |
| L5 **会话** | **设备接收端挂在死会话** | **timing 心跳归零 + RTSP 却 200** | **永久静音、不自愈** | **v4.10.0（本轮）** |

**本轮踩的是 L5。** L1~L4 各自都已被别的版本修掉或排除，结论见 §2。

## 3. 关键方向的「怎么查 + 查到了什么」

### 3.1 R1 设备侧 WiFi / 网络（❌ 排除）

**做法**：240 上 `ping -D -i 0.5`（秒级时间戳，便于与服务端日志对齐），每 5s `getStatus` 采 `RSSI`/`netstat`/`channel`，另 `getPlayerStatus` 2s 一次。
> 坑：字段是 **`RSSI`（大写、字符串）** 与 **`netstat`（字符串数字）**，不是 `wifi_rssi`；按常规名解析全拿到 `?`。

**结果**：40 分钟 / 13 首 / 0 次看门狗 / 0 次重连；ping 9466 包 0 丢包；RSSI -44~-50dBm；`netstat` 1071 次全 2。
**结论**：设备硬件与无线链路健康。**不是设备稳定性问题** —— 这条把排查面一刀切到「服务端会话」。

### 3.2 R2 数据面 RTP 流中断（❌ 排除）

**做法**：服务端 tick（每 chunk 一条，带 `deltaUs`）+ `silenceChunks`。
**结果**：`deltaUs` 稳定 1.06s、`silenceChunks` 不增长 ⇒ 服务端持续正确推流，而设备不出声。
**结论**：数据面正常 + 设备静音 = 会话层故障的第一强证据。

### 3.3 R3 换歌间隙饿死（⚠️ 真问题，独立病灶）

实测间隙 **4~18s**，垫片窗只覆盖 **1.3~5.3s** ⇒ 2.7~16.7s 完全无包。是另一个病灶（下一首预取/源解析等待），本轮不修，见 §9。
> 注意与 v4.9.6 的区别：v4.9.6 修的是**垫片窗内 RTP 断流**（2.5~3s，已修）；这里是**垫片窗整体不够长**（4~18s），不是同一件事。

### 3.4 R4 ctrl 重传请求静默看门狗（❌ 证伪，v4.9.8 的误杀源）

**当时的想法**：v4.9.8 观察到「失聪后 292s 零重传请求」⇒ 认定 ctrl 重传请求就是活性信号。

**实测推翻**：**重传请求是「丢包驱动」信号** —— 流越干净，设备越**不**发。
- `loss=0` 的 170s 流，`latePackets` 只有 297（≈1.7/s，带突发性）；
- 5 分钟静默**概率≈1**；
- 两次触发 **17:49:15 / 17:54:15，间隔精确 5min00s**（固定间隔 = 代码定时器，不是设备行为）；
- 每次触发后：完整重握手 → 设备缓冲放完 + 重连 5.6s ⇒ **9~14s 静音**。

**逻辑错误在哪**：v4.9.8 只证明了 `死亡 ⇒ 静默`（单向必要条件），却把它当成 `静默 ⇒ 死亡`（充分条件）。**必要条件当判据 = 系统性误杀。**

### 3.5 R5/R6 主动 NACK 探针（❌ 证伪，代码已回滚）

**想法**：静音段故意跳过若干 seq，设备若活着应发 NACK——有 NACK = 活。
**实测**：三次（单包 8ms ×2；3 块 24ms ×1，窗口 8s）**零 NACK**，同期音频完全正常。
**结论**：MUZO 不做「重传请求式」恢复 ⇒ 探针**无法区分**「干净」与「死亡」，开 ACTION 就是第二个误杀源。
**处置**：`git checkout` 回滚 + 删单测。**不要重做。**

### 3.6 R7「MUZO 正常播放会停发 timing」（❌ 旧结论推翻）

v4.9.6/v4.9.7 曾据此**缺省关闭**看门狗。用 `hb_watch.sh`（每分钟统计 timing 包数）取证：

| 时间窗 | timing 频率 | 同期状态 |
|---|---|---|
| 11:42–12:11 | **20 次/分钟**（每 3s 一次），跨 8 次换歌不断流 | 正常出声 |
| 12:13 后 10 分钟 | **0 次** | **无声**（服务端仍在推 3 条流） |

**结论**：timing 是**可靠的周期活心跳**，也是判断「设备是否接管当前会话」的唯一可信信号。旧结论错在把「无声期的 0 次」当成「正常播放的常态」。

### 3.7 R8 根因：TEARDOWN 缺失 ⇒ 接收端僵死（✅）

**静音期（2026-10-29 12:12 之后）四条并行判据**：
1. 服务端：3 条流**全部推完**（L3 正常）；
2. 协议层：`ANNOUNCE / SETUP / RECORD` **全 200**，握手 526ms（正常）；
3. 设备侧：timing **0 次 / 10 分钟**（异常）；
4. 用户侧：**完全不出声**。

**对照实验（决定性）**：`POST /peers/group:<uuid>/stop`（真 TEARDOWN）→ 紧接 `queue/play {items, startIndex}` 重放 → **立刻出声**，timing 回 6 次/分钟（短窗）。**唯一变量是 TEARDOWN** ⇒ 根因锁定「会话没有被显式拆除」。

### 3.8 判据陷阱：DLNA 位置 / `getPlayerStatus`（❌ 不可信）

- DLNA `GetPositionInfo` / `GetTransportInfo` 对 AirPlay 设备**恒报 `STOPPED`、位置不前进**（RAOP 音频直通 DSP，不经本地播放器）；
- 假死期 `getPlayerStatus` 会**自报 `status:play`**，`uri=""`、`curpos` 空走。

⇒ 「是否在播 / 播到哪」**只能**用服务端 tick 或设备 timing 心跳。

## 5. 判定「根因修复」还是「止血」的 6 条硬标准

提任何修复前逐条自问，**有一条答不上来就还是止血**：

1. **能解释 100% 的观测事实吗（含反例）**？本轮必须同时解释：数据面正常 + RTSP 200 + timing 归零 + 不自愈。
2. **恢复手段与病因同层吗**？病因在会话层，修复就是 `TEARDOWN`（同层）；不是"提高阈值""多连几次"（隔层）。
3. **有没有可证伪的对照实验**？`stop` + 重放 vs 仅重连 —— 唯一变量、结果相反。
4. **能不能解释「同一台设备在别的场景下正常」**？能：只有"进程在播放中被杀"这一条件触发。
5. **修完还有没有残留的"猜"**？「也许设备自己会好」= 猜，已被 10 分钟 0 心跳证伪。
6. **自动恢复带退避吗**？任何自动重连都必须熔断（本轮：10 分钟内 ≥2 次 ⇒ 停用 30min），否则一次误判 = 连环重连。

> 反面教材：v4.9.8 是典型止血 —— 它"解决"了症状（重连后能出声），但判据方向错、无退避、每 5 分钟杀一次健康流，**伤害大于收益**。
> 更隐蔽的教训：**必要条件 ≠ 判据**（§3.4）。写看门狗前先问「这个信号在健康态下会不会也静默」。

## 6. 信号可信度分级（哪类信号能当活性判据）

| 级别 | 信号 | 可否当活性判据 | 说明 |
|---|---|---|---|
| A | **设备 timing(NTP) 心跳** | ✅ 可以 | 周期 3s、20 次/分钟；健康不断流，僵死立刻归零且不恢复 |
| B | 服务端 tick / `deltaUs` / `silenceChunks` / `leadUs` | ⚠️ 只能判"我们在推" | 不代表设备在收、更不代表在响 |
| C | RTSP 响应码（200/204） | ❌ 不能 | 协议层接受 ≠ 硬件接管 |
| D | ctrl 重传请求（0x55） | ❌ **不能** | 丢包驱动，干净流必然静默 |
| E | 设备 NACK | ❌ 不能 | 实测零 NACK |
| F | DLNA `GetTransportInfo`/`GetPositionInfo`、`getPlayerStatus` | ❌ 不能 | 直通 DSP ⇒ 恒 STOPPED / 假 play |

**规律**：能当活性判据的只有「**设备主动、周期性、与丢包无关**」的信号。**事件驱动**的信号（重传请求、NACK）静默既可能是死、也可能是好，**永远不要**用它判活。

### 7.2 让设备僵死的确定性复现

1. 群组**正常播放**（出声、timing 有心跳）；
2. **不做 TEARDOWN** 直接杀/重启服务端（老的 `docker restart` 就是这条路径）；
3. 重启后照常起流 ⇒ RTSP 全 200、服务端 tick 正常、**设备 timing 0 次、完全无声**；
4. 判定：`hb_watch.sh` 连续 ≥5 分钟 0 心跳即僵死确认，**不要**再等它自愈。

### 7.3 恢复手法（**唯一有效**）

```text
POST /rest/api/v1/peers/group:<uuid>/stop          # 真下发 TEARDOWN
POST /rest/api/v1/peers/group:<uuid>/queue/play {"items": [...], "startIndex": N}
```

- `peerId` 是 `airplay:00226CFFA0C0`，**不是**裸 deviceId（后者 400「无效的 peerId」）；
- `/peers/:id/play` **救不活**（只起流、不重置设备会话），必须组级 `stop` + 队列重放；
- `queue/play` **必须带 `items`**（仅 stop 后不带会 400），items 从 `/peers` 的 `queue.items` 取。

| 判据 | 期望 |

| 设备 timing 心跳 | 播放中稳定 ~20 次/分钟 |

| 21:01:48 | —— | —— | `timing_in=1`，设备开始问 timing |
| 21:04:52 | `mem=439MiB` | curpos 正常推进 | `HEALTHY` |

**根因（判定器自己的 bug，不是产品的）**：`RTP>0 且 timing=0` 只是**必要条件**，不是充分条件。容器重启后新进程立刻开始推 RTP，但设备要几秒才发第一个 timing 请求；这段接管期天然满足"有 RTP、无 timing"。这和 §11.2 里 v4.9.8 犯的错是**同一类错误**：把必要条件当判据。

**修法（三道闸门，缺一不可）**：

| 闸门 | 阈值 | 挡掉什么 |
|---|---|---|
| ① RTP 必须稳流 | `>= 600 包/15s`（≈40/s；健康 116/s≈1740） | 刚起播/刚重启时窗口只覆盖几秒、RTP 只有几十包 |
| ② 连续命中 | 需 **≥2 个窗口（≥30s）** | 单窗口抖动；第 1 窗口只记 `L5_SUSPECT` |
| ③ 容器 uptime | `>= 90s`，不足判 `RECOVERING` | 重启后的接管期整段豁免 |

实施：`classify()` 增参 `l5_streak`/`uptime`，`/tmp/mf410/.l5_state.json` 落去抖状态，`container_uptime()` 读 `docker inspect .State.StartedAt`，verdict 行增 `up=` 字段。`--selftest` 从 10 例扩到 **14 例**（新增：启动期 RTP 未稳流 / 容器刚起 30s / 稳流但只第 1 窗口 / 稳流连第 2 窗口），**14/14 PASS**。

> **通用教训（比这个 bug 本身重要）**：凡是"故障期出现 X"的信号，先问一句 **健康态会不会也出现 X**。timing=0 在健康态不出现（好判据），但在**接管期**出现——所以要加的闸门不是"故障时有没有"，而是"这一刻是不是已经过了接管期"。以后每加一条判据，selftest 里必须有**一条接管期/启动期的反例**。
