### 2.2 AP1 接收端抓取链（BLK-04）

shairport 日志确认 240 的 RAOP 会话真实建立：

```
"rtsp.c:1057" Connection 1: SETUP ... from 192.168.10.240 ... Audio: 6003
"audio_alsa.c:528" alsa: output format chosen is "S32".     ← 关键
"audio_alsa.c:569" alsa: output speed chosen is 44100.
/etc/shairport-sync.conf:8  output_device = "hw:Loopback,0"
```

| 抓法 | 结果 |
|---|---|
| `arecord -D hw:Loopback,1,0 -f S16_LE -r 44100 -c 2` | ❌ 录满 22s，**peak 0 / nonzero 0.0** |
| `arecord -D hw:Loopback,1,0 -f S32_LE -r 44100 -c 2` | ✅ peak_i32 22 600 508（−39.56 dBFS）、nonzero **1.0**、分段 RMS 起伏 **12.3 dB**（真实音乐动态） |

> **BLK-04 的真正根因**：shairport 向 `hw:Loopback,0` 写的是 **S32_LE** 而非 S16。用 S16 读同一份数据，相当于只看每样本高 16 位（音乐低电平下多为 0）⇒ 全静音。
> 这同时解释了历史上「Loopback 只能采到 peak 935 / RMS −40 dBFS，以为是 RAOP 音量档」——**其实一部分是读取格式错**，S32→S16 右移 16 位恰好把 22600508 变成 ~345 量级。

## 3. 本轮新发现（按严重度）

### P0-1 🔴 配对时序死锁（服务端缺口，影响真机新设备首次配对）

| 环节 | 事实 |
|---|---|
| 服务端 | `server.ts:onClientHello` **无条件**发 `server/activate{activities:["playback"], active_roles}` |
| 客户端 | 未配对会话用 sentinel PSK，`_activities_allowed` 只准 `{pairing}` ⇒ `_admissible` 失败 ⇒ 返回 `pairing_required` 并 `goodbye_and_disconnect`（`connection.py:582-628`），**不会等待配对窗** |
| 实测 | `RuntimeError: server activation rejected (pairing_required)`，进程退出 |
| 另一头 | `pairServer.start()` 要求 `server.clients.get(clientId)` 存在且在线，否则报「客户端未连接」 |
| 结果 | 客户端已断开 ⇒ REST 配对无从启动 ⇒ **aiosendspin 客户端首次配对不可达** |

真实 ESP32（sendspin-cpp）能配对，说明 cpp 客户端收到 `pairing_required` 后行为不同（保持连接等窗），因此这问题只在 aiosendspin/标准 Python 客户端上暴露。

**建议修法（二选一）**
1. 服务端在 `onClientHello` 发现 `pairingStore.getRecord(clientId) == null` 时，首次 activate 发 `{activities:["pairing"], pairing:{method,format}}`，而不是硬发 playback（spec 正统）。
2. 或对未配对连接保留 30s "待配对" 状态（不发 activate 也不踢），让 REST `pairing/start` 有窗口可打。

> 本次验证用 `--unpaired`（客户端 `set_unpaired_access(enabled=True)`）绕过，**仅验证数据面，不代表配对通过**。

### P0-2 🔴 `arecord` 必须 `-f S32_LE`（BLK-04 根因修正）

文档与历史记录都写的 `-f S16_LE`，实测全 0。原因是 shairport 的 ALSA 输出格式为 S32。验收脚本必须改为 S32，再在分析侧归一化。

### P0-3 🔴 `cc_align` 交织立体声 2 倍误差（已修）

首版对 interleaved 数据直接互相关，`lag` 单位是 sample 而 `rate` 是 frame/s ⇒ **137ms 被测成 274ms**（恰好 channels 倍）。已改为先按 `--channels`（默认 2）降混成帧序列；并新增 `selftest_stereo()` 把这条钉成回归。

### P0-4 🟡 尾窗要求「两侧同源同长」（已加 WARN）

若一侧仍在写入或长度差 > 1s，两侧「最后 10s」不是同一时间段 ⇒ 相关到重复段落，实测出现 **−950 ms 假峰位**（quality 仍 0.935，极具欺骗性）。脚本现在长度差 > 1s 会打 WARN。**验收取数必须先冻结快照再分析。**

### P0-5 🟡 shairport 音量档会改变 PCM 电平

`ignore_volume_control is 0` ⇒ RAOP 音量直接作用于输出。实测 AP1 侧 peak −39.56 dBFS，比源侧 −17.1 dBFS 低 22 dB。

影响：互相关（尺度无关）不受影响，但 **绝对电平判据（如 `peak > 1000`）必须按抓取档位设阈值**；不同用例若音量档不同，quality 不可横向比较。建议验收前把该设备音量固定到 100，或在分析侧统一归一化。

## 5. 复现命令（照抄可跑）

```bash
# 0) 取 token（240，零写入）
docker exec musicflow node -e 'const fs=require("fs"),jwt=require("/app/backend/node_modules/jsonwebtoken"),D=require("/app/backend/node_modules/better-sqlite3");const db=new D("/app/backend/data/musicflow.db",{readonly:true,fileMustExist:true});const u=db.prepare("select id from users where is_admin=1").get();console.log(jwt.sign({uid:u.id},fs.readFileSync("/app/backend/data/.jwt-secret","utf8").trim(),{expiresIn:"4h"}))' > /tmp/mf_token.txt

# 1) 假设备（230）
/root/ssvenv/bin/python /root/fake_sendspin.py --host 192.168.10.240 --port 38927 \
  --name FAKE-1 --out /root/fake1.pcm --unpaired

# 2) AP1 抓取（230）—— 必须 S32_LE
arecord -D hw:Loopback,1,0 -f S32_LE -r 44100 -c 2 -t raw -d 40 /root/ap1.pcm

# 3) 同歌投放（240）
curl -X POST http://127.0.0.1:46400/rest/api/v1/play -H "Authorization: Bearer $(cat /tmp/mf_token.txt)" \
  -H 'x-mf-client-id: 5f1e0a7c-bridge-verify' -H 'Content-Type: application/json' \
  -d '{"peerId":"sendspin:＜FAKE clientId＞","type":"song","id":"＜songId＞"}'

# 4) 统一到 44.1k 单声道后再相关
ffmpeg -v error -f s16le -ar 48000 -ac 2 -i fake.pcm -ar 44100 -ac 1 -f s16le -y fake_mono44.raw
ffmpeg -v error -f s32le -ar 44100 -ac 2 -i ap1.pcm  -ac 1 -af 'volume=24dB' -f s16le -y ap1_mono44.raw
/root/ssvenv/bin/python /root/cc_align.py fake_mono44.raw ap1_mono44.raw --rate 44100 --channels 1 --window 45
```
