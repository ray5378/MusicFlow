## 1. 七处修法逐条

### ① BLK-01 虚拟 `pcm:100` 组 —— **PASS**

- **`encoderKey("pcm", 100)` 确实产出 `"pcm:100"`**：`server.ts:782` 是模板串 `` `${codec}:${gain}` ``；`SendspinCodec` 含 `"pcm"`（`encoding.ts:30`）。`encoderKey` 是 `private`，但在同类方法内调用合法。
- **五处副作用全部无害**：`flushAnnounceFor` 在 `for (const c of g.members)` 空循环里 no-op（`:1167`）；`scalePcm(pcm, 100)` 命中 `g >= 1` 直接返回原 `pcm`，零拷贝零计算（`:1089-1091`）；`deliveredByGroup.get(key) ?? before` 语义正确 —— 新键以 `before` 为基线，且 `resetPushMeter()` 在每次起播把 `deliveredByGroup`/`deliveredPeak`/`recentByGroup` 三者一起清空（`server.ts:847-854`，唯一调用点 `streamEngine.ts:750`），不会跨曲污染；`ringFor("pcm:100")` 正常建 ring（`:1218-1225`）；`pruneRecent` 对该键无差异。
- **唯一副作用（可接受，建议写一句）**：虚拟组会进 `meterSamples/meterBytes` 计量。真实成员在场时它排在 Map 末尾且 `sum > meterSamples` 不成立（严格大于），不覆盖既有口径；**只有桥**时 `encodedBytesPerSec` 变成 PCM 192KB/s —— 这正是期望值（原来会取 `members[0] ?? "pcm"` 的回落，现在有实测值），且此时 `deviceCapacityBytes=0` 使字节闸关闭。
- **`before` 时机**：`const before = this.deliveredPeak`（`:1143`）在 groups 建完之后，而 `groups.set` 不触碰 `deliveredPeak` ⇒ 插在 before 前/后**完全等价**，不会影响首次 `return peak - before`。文档"建完 groups 后、进入循环前"写法正确。
- ⚠️ 提示：插入语句必须**在** `for (const [key, g] of groups)` 之前，文档已写明 ✓。

### ② BLK-02 代次源改 `epoch` —— **部分成立（①②可用，③ FAIL）**

- **① 一次 seek +2 无害，但依赖一条未写明的前提**。`epoch` 自增点：`play()` `:532`、`stop()` `:1179` ⇒ seek = `+2`。若 `syncGeneration()` 只在**投递帧**时调用，`stop()`→`play()` 之间没有帧，桥只会看到最终值 ⇒ **只发 1 次 BOUNDARY**；若放进定时器轮询才会发 2 次。即便发 2 次也无害的**前提**是"BOUNDARY 只清队列+换代次、不拆 RAOP 会话"——§5.4 seek 的"禁止③重建 RAOP 会话"隐含了它，但没写成规则。**补一句**：`BOUNDARY` 语义 = 清队列 + 换代次（不 TEARDOWN），重锚只发生在收到新代次首帧时；`syncGeneration` 挂在投递路径、**不用定时器**。
- **② pump 可达但需显式注入**。`pumpFor/peekPump/transferPumpTo/stopGroupPump` 确实由 `streamEngine.ts` 导出（`playerCore.ts:13` 已 import）✓，但 `SendspinGroup` 不持有 `srv`/`pump`，`this.pump.generation` 的来源没写。**更省事的落点**：`pushLoop` 的重锚分支（`streamEngine.ts:813` `if (firstFrame || this.timelineReseed !== consumedReseed)`）本来就同时持有 `myEpoch` 与 `this.group`，直接在那里下发代次即可 —— 一次覆盖 seek/track/rehost，且不引入 `server.ts ↔ streamEngine.ts` 的反向依赖。
- **③ FAIL：`rehost()` 不自增 `epoch`。** `rehost()`（`streamEngine.ts:1270-1299`）全文无 `this.epoch`、不调 `stop()`，只做 `prev.timelineBaseUs=0n` → `this.group=next` → `timelineReseed++`。文档 §4.3 `:421`「`rehost()`…它同时自增 `epoch`（经 `stop()`）」与 §5.2 `:500`「`epoch` 与 `timelineReseed` 同时自增」**两处均为事实错误**。后果：借流移交（`handoverCore → p.transferPumpTo/rehost`）时桥看不到代次变化 ⇒ 不重锚，旧 `A` 配新组 `timelineBaseUs`。
  **改成**：(a) 删掉"经 stop() 自增"；(b) 重锚钩子挂到 ②所述的重锚分支，天然覆盖 rehost；(c) **不要**给 `rehost` 加 `this.epoch++` —— 那会让 `while (this.running && this.epoch === myEpoch)`（`:759`）立刻为假，把移交变成停播。

### ③ MAJ-01 落点改 `bridgeStartLeadUs` —— **部分成立（方向正确，`coldStart` 是真空洞）**

- 删掉"并入 `commonSendAheadUs()`"、`computeCommonSendAhead` 不动、只报 `minBufferMs=1000` —— 全部正确，与 `group.ts:76-92` 语义吻合。
- **`coldStart` 在全文只出现一次**（`:280` 的代码片段），无任何定义；接口 `:686` 也只有 `bridgeStartLeadUs(): number`（无入参）。这正是你自己预判的新缺口。
- **最小补法**：冷/热是 **airplay 侧的事实**（只有它知道本设备有没有可复用的已完成 RECORD 的会话），因此由 airplay 侧在 `CONFIG` 回执里回传 `warm: boolean`；`BridgeMember` 存 `this.warm`；`SendspinGroup.bridgeStartLeadUs()` = `max(所有桥 warm ? 2.5s : 4.5s)`（取最大，保证最慢那台够用）；**未收到回执前一律按 cold**。

### ④ MAJ-09 四锚点 —— **PASS（附 2 处补充）**

- **`baseTs` 生产消费点只有两处**：`positionSec`（`:695`）、`seekStartTs(baseTs,…)`（`:846`/`:869`）。`writeNtp`/`sendSync`/状态上报**都不用**它 —— **没有第三处** ✓。`seekPositionSec`（`:120`）虽接 `baseTs` 但 src 无调用者。
- ⚠️ 但**测试**有 4 处硬编码 `anyP.baseTs`（`raopPlayer.test.ts:116 / 335 / 627 / 967`），改锚点语义会打红，需在同一 commit 同步。
- **"禁止调用 `raop.seek()`" 的表述指向一个不存在的方法**：`RaopPlayer` 上没有 `seek()`，真实入口是 `prepareSeek()`（`:842`，唯一调用者 `control.ts:1015`）与 `setStartPosition()`（`:868`，调用者 `control.ts:456`、`sessionRuntime.ts:161`）。**改成**"禁止 `prepareSeek()` / `setStartPosition()`，以及禁止复用 `sessionRuntime.cast()` 的 `seekSec` 通道"。
- **与现有路径不冲突** ✓：bridge 会话由 `bridgePrepare` 建，不走 cast 链；组 seek 走 `fanOut("seek")`（`group/protocolPlayer.ts:181`），§5.4 的 fanOut 跳过已覆盖。

### ⑤ MAJ-10 `>>> 0` —— **PASS，但截断与对齐的**顺序**必须写死**

- `ntp2ts` 返回**非负**数；`>>> 0`(ToUint32) 与 `& 0xFFFFFFFF`(ToInt32) 在 ≥2³¹ 时**结果不同**：实测 `0xFFFFFFFF` 下前者 = `4294967295`、后者 = **`-1`**。负数会让 `headTs % CHUNK_LEN` 得负余数 ⇒ 破坏 352 对齐。⇒ **只能用 `>>> 0`**，`&` 是陷阱。
- **顺序敏感**：`2^32 % 352 = 224 ≠ 0`。实测"先对齐后截断"残 **32**（对齐被破坏）、"先截断再对齐"残 **0** ✓。文档没写顺序，补一行：`headTs = ntp2ts(ntp0, rate) >>> 0; headTs -= headTs % CHUNK_LEN; baseTs = startTs = headTs;`。

### ⑥ MAJ-06 过滤点 —— **部分成立（缺字段落点 + 一条旁路没封）**

- owner **当前不存在**：`sessionRuntime.ts:82` 的 `interface ActiveSession` 没有 owner/token 字段；`sessions = Map<string, ActiveSession>`（`:133`）按 deviceId 索引 ⇒ 一设备一会话，判断很自然。**补写**："`owner: SessionOwner` 加到 `ActiveSession`（`:82`），缺省 `{kind:"native"}`；判定 = `sessions.get(deviceId)?.owner.kind !== "bridge"`"。
- **旁路**：`stopAirPlaySession` 共 5 类调用者。`control.ts:316`（`stopAirPlaySessionsForHost` 自身，过滤点）、`:1275`（服务关停全停）、`:1245`（mDNS byebye 强停）、`routes/api/airplay.ts:96/116`（REST 手停）**都属于"设备/用户显式停"，允许停桥会话**，无需过滤 ✓。唯一要封的是 `airplay/protocolPlayer.ts:54`（`stop()` → `stopAirPlay(deviceId)`）：它只能经组 fanOut 到达，§5.4 已覆盖，但**守卫要断言**"bridge 路由下不得直接调用 `createAirPlayProtocolPlayer().stop()`"。
- token 可选（缺省=旧语义）✓ 已覆盖 `byebye`/REST 的兼容。

### ⑦ MAJ-05 socket 路径长度 —— **PASS**

- 230 实测 `os.tmpdir()` = `/tmp`；`/tmp/mfab/<11位>.sock` = 10+11+5 = **26 字节**，余 82 字节；即使 TMPDIR 被换成 80 字符的自定义目录也仍 ≤106。
- `sun_path[108]` 来自 `/usr/include/x86_64-linux-gnu/sys/un.h:32`（`char sun_path[108];`）✓；`man 2 bind` → `ENAMETOOLONG  addr is too long` ✓，即 Node 的 `listen(path)` 会 **emit `error`**（不是静默 listening）。
- ⚠️ 未做实机 bind 验证（受"禁止写操作"约束），但 26B 距 108B 有 4 倍余量，无需实测。

## 2. 三项判定

### A. 有没有引入新 Blocker —— **没有**

- `stopGroupCore`（`playerCore.ts:413`）与 `playGroupCore`（`:356`）**是不同函数** ✓：前者 = `pumpFor().stop()` + `finishPlayback()`；后者 = `pump.stop()` + `armSeek()` + `g.close()`。`g.close()`（`server.ts:1375-1382`）只清 `encoders` + `recentByGroup` ⇒ §4.3"`g.close()` 不清 bridges"与 §5.4"`stopGroupCore` 清 bridge"**不矛盾** ✓。
- 唯一隐性风险（Minor）：`g.close()` 清 `recentByGroup` ⇒ seek 后桥的晚加入 ring 为空，此时第二台 AP 加入，`seedLateJoin` 必返回 0。**给用例 6 加限定**"seek 之后 ≥3s 再加入"。

### B. 验收链是否闭合 —— **基本闭合，缺 2 个前置 + 1 个脚本**

- ✅ **`shairport-sync` 输出到 `hw:Loopback,0` 真实存在**：`/etc/shairport-sync.conf:4 output_backend="alsa"`、`:8 output_device="hw:Loopback,0"`；`arecord -l` 显示 card0 有 **device 0 与 device 1** 两路采集（aloop 对称模型），故 `arecord -D hw:Loopback,1` 正是 device 0 播出的对侧 ⇒ **命令正确**。
- ✅ `arecord`/`aplay` 在 `/usr/bin`；`snd_aloop` 已加载（`lsmod` 4 项）；当前只有 **1 个** shairport 进程 ⇒ 不会两路混进同一 loopback。
- ❌ **缺前置顺序**：`arecord` 要有音源就必须先有服务 + 一次 cast。建议 Phase 0 出口重排为：①起服务 `/ping` 200 → ②**用旧 cast 路径**投一台 AP1（不依赖 bridge）→ ③`arecord -D hw:Loopback,1 -d 5` peak>1000 → ④假 Sendspin 配对收流。
- ❌ **缺脚本**：`backend/scripts/cc_align.py` 尚无文件（§6.1 列为待建），但 Phase 0 的 137ms 自检要用它 ⇒ 把"脚本落盘 + 自检 `[selftest] OK`"并入 **Phase 0 出口**，不要留到 P8。
- ⚠️ shairport 配置未显式写采样率，抓取前应先 `cat /proc/asound/card0/pcm0p/sub0/hw_params` 确认实际是 44100（文档要求 `-r 44100`，若实际 48k 会量出假象）。

### C. 两份文档是否还有矛盾 —— **还剩 1 处（常量）**

- **D 编号**：落地方案 §0.1 映射表（D2→D3、D4→D5）与实施方案 §1 真实编号**一致** ✓。
- **阶段映射**：§0.2 表 → 实施方案 §8 编号**一致** ✓；实施方案确已存在 6a/6b（`:849-860`）✓。
- ❌ **重采样群延迟仍有 2 处 `0.33ms` 残留**：落地方案 `:283`（表 B 行"…+ **0.33ms** 群延迟"）、`:392`（Phase 1"群延迟 N/2=16 输入帧≈**0.33ms**"），而同一文档 `:783` 与实施方案 §4.5 都是 **0.3627ms** ⇒ 同一常量三处两个值。**改成 0.3627ms（17.41 输入帧）**。
- 其余常量一致 ✓：4500/2500/1000（`:152-153/162`）、384KB/1.5MB（`:372-373/728`）、147/160（`:282/392/783`）、`ANCHOR_SAFE_LEAD_US=800_000`（`:866`）。
