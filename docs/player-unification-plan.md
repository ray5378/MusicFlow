# 播放端统一化管理与遥控 方案（PLAYER_UNIFICATION）

> 状态：**方案阶段（未落码）**。目标版本线：v3.0.x。
> 一句话目标：把**所有能出声的播放端**统一成服务端"认识、可列出、可遥控、可读状态"的同一种对象，
> 并在**播放器页**与**选择播放器界面**里同等呈现、同等遥控，同时提供**推流 / 拉流**。
>
> 关联文档：`DEVELOPER.md`（整体架构）、`API.md`（接口面）、`PRE_PROBE.md`（预探测）、
> `sendspin-renderer-handoff-2026-09-13.md`（Sendspin 渲染端）。

---

## 1. 术语与角色

| 角色 | 是谁 | 出声 | 参与「本机」判定 | 进模块列表 |
|---|---|---|---|---|
| **播放端 · 设备型** | DLNA / AirPlay / Sendspin / 群组 | ✅ 设备出声 | ❌ | ✅ |
| **播放端 · 本机型** | 安卓 App / Windows App / Web 播放器 | ✅ 本机出声 | ✅ | ✅ |
| **消费方 · 纯遥控** | **HA 卡片** | ❌ 只发指令 | ❌ | ❌ |

- 「播放端」= 被服务端管理、可被遥控的出声目标。
- 「消费方」= 发起遥控的一端。可播放的消费方（Web / 安卓 / Windows）同时也是"播放端 · 本机型"；
  HA 卡片只遥控、本身不出声，**不参与「本机」判定，也不进播放器页模块列表**。

## 2. 现状与缺口（代码事实）

**已受管（现状即目标形态）**
- 类型集合：`PeerKind = local | dlna | group | airplay | sendspin`（`backend/src/services/peer.ts`，约 :53）。
- 统一契约：`ProtocolPlayer`（`backend/src/services/player/types.ts`，约 :67）——
  `playMedia / stop / pause / resume / seek / setVolume / pollState`，DLNA / AirPlay / Sendspin / 群组同形实现。
- 注册：经 `UniversalPlayer.attachProtocol` 注册进 `QueueController`，随即获得**队列 + 自动切歌 + 状态轮询**。
- 本机 peerId 为三段式 `local:<userId>:<clientId>`，唯一权威在 `backend/src/utils/peerId.ts`，
  配套四处消费：`canControlPeer / filterPeersByAccess / pruneOrphans / canSeePeer`。

**缺口（要补的）**
1. **local 是唯一短板**：音频在客户端（Web 用 Howler、客户端用 Flutter），服务端只存队列元数据；
   transport 为 no-op（`backend/src/routes/api/index.ts`，约 :3358），status 只有队列快照（约 :3659）。
2. **无法被远程遥控**：本机不可作为遥控目标；别的端/HA 遥控不了它。
3. **状态不统一**：四种 schema；且 **WS 只推 DLNA**（`backend/src/services/ws/index.ts`，约 :108 / :177）。
4. **控制面重复**：路由层 6+ 条重复的 `kind → 实现` if 链；新增一种播放端要改多处。
5. **重复工具**：`stripPlayerPrefix`（`QueueController.ts`，约 :29）与 `parsePeerId`（`peer.ts`，约 :463）职责重叠。
6. **旁路**：`/v1/dlna/cast`、client-cast stream-url、插件 renderer 的 `control(action)` 第三套控制面各自为政。
7. **UI 缺位**：`frontend/src/views/Groups/index.vue`（路由 `/groups`，侧边栏 label `layout.players`）
   现只有 **DLNA / AirPlay / Sendspin / 群组** 四个区块，缺 **客户端** 与 **Web 播放器** 两块。

## 3. 统一模型

每个播放端 = 同一对象，具备四要素：

| 要素 | 内容 |
|---|---|
| 身份 · 名字 | `kind` + 稳定 id（本机为 `local:<userId>:<clientId>`）+ 显示名 |
| 能力 | 播放 / 暂停 / 跳转 / 音量 / 静音 / 上下首 / 是否支持 seek |
| 状态 | 曲目、播放态、进度、时长、音量、在线 |
| 队列 | 播放列表、下一首、自动切歌 |

**唯一的差别是"命令往哪送"**：
- **设备型**：音频在设备上，服务端用协议直控（现状）。
- **本机型**：音频仍在本机（**不搬服务端**），服务端经**信令通道**下发指令，客户端执行后**回报状态**。

其余（队列、自动切歌、预探测、状态聚合、WS 推送、UI）**全部共用一套**。

## 4. 界面设计

### 4.1 侧边栏「播放器」页 = 管理页

**六个模块**（同级同款）：**客户端** · **Web 播放器** · DLNA 设备 · AirPlay 设备 · Sendspin 设备 · 群组。

- 「客户端」模块：安卓 App / Windows App 实例，一行一个。
- 「Web 播放器」模块：浏览器实例，一行一个。
- **本页不判定本机、不出现「本机」**：每行只显示**设备名**（安卓机型 / Windows 电脑名 / 浏览器·系统）
  或**用户自定义名**；行能力与 DLNA 行一致（改名 `playerStore.setPeerName` · 隐藏 `setPeerHidden` · 禁用 · 删除）。
- **离线端自动从列表消失**：与 DLNA 等设备一致，不保留"离线"占位行。
- **六个模块在所有端都可见**（在 Web 上也能看到安卓/Windows 实例）——因为它是管理页，与"你在哪看"无关。

### 4.2 「选择播放器」= 选择播放目标的地方

**只出现在"能播放"的端**：Web 播放器 / 安卓 App / Windows App。

- **此处才判定本机**：用 `clientId` 比对自己那一行 → 显示「本机」+ 角标 + **置顶**；其余行显示设备名。
- 选中任一端 = **远程遥控**（逻辑与 DLNA 完全相同）。
- 提供 **推流 / 拉流**（见 §5）。
- **HA 卡片不出现在列表中**——它只是纯遥控器，不是推流目标（见 §9）。
- **离线端自动消失**：条目与 DLNA 等设备同样处理；若选中后目标才掉线，需明确反馈失败原因。

### 4.3 命名规则

| 情况 | 显示名 | 谁看到 |
|---|---|---|
| 用户改过名 | 用户改的名（命中自己时 +「本机」角标） | 所有端一致 |
| 未改名 · 看自己那端 | 「本机」 | 仅自己 |
| 未改名 · 看别人那端 | 设备名（机型 / 电脑名 / 浏览器·系统） | 其他端 |
| 取不到任何 | 「本机播放」 | — |

- 判定基准：**`clientId`**（精确到 App 实例 / 浏览器标签页，同账号多端各占一条）。
- 改名持久化绑 `clientId`；同名自动加后缀去重。
- **已知边界**：网页清缓存会换 `clientId`，改的名可能对不上 → 按"同账号 + 同平台"兜底认回。

## 5. 推流 / 拉流

| 动作 | 语义 |
|---|---|
| **推流** | 把**当前正在播放**的曲目/队列送到选中播放端开始播放 |
| **拉流** | 把**选中播放端正在播放**的曲目/队列接过来，在当前端继续 |

- 二者都只搬运"队列 + 播放位置"，不搬运音频；音频始终由目标端自行出声。
- **目标必须是"在线的播放端"**：HA 卡片不是目标；离线端已从列表消失，无法被选中。
- 本机型目标需经信令通道通知对应客户端接管。

## 6. 接口草案（约定，不含实现）

**设备名片**（所有播放端统一上报/下发）
`id` · `kind` · `platform` · `model`（机型/电脑名，可空）· `clientId`（本机型）· `displayName`（用户改名，可空）· `online`

**统一状态形状**
`trackId / state(playing|paused|stopped|buffering) / positionMs / durationMs / volume / muted / updatedAt`

**本机型信令指令**（复用现有 WS / 心跳通道）
下发：`play / pause / resume / stop / seek / setVolume / setMute / next / prev`
回报：状态形状 + 执行回执（成功 / 失败原因）

**选择 / 推流 / 拉流**（选择播放器界面）
`selectTarget(peerId)` · `pushTo(peerId)` · `pullFrom(peerId)`

| 步骤 | 内容 | 验收点 | 进度 |
|---|---|---|---|
| **1** | 统一状态 + 名字：统一状态形状、本机状态回报、WS 全类型推送、命名链 + `clientId` 判定 | 名字自动命中合理；选择播放器里本机正确置顶 + 角标 | 🟡 名字链 / 实例键判定 / 服务端统一出口已落地；**本机真状态回报 + WS 全类型推送未做** |

### 7.1 进度记录

**2026-09-15（未发版）— 步骤 1 前半 + 步骤 4 的播放器页部分**

- **服务端单一出口** `services/access.ts → decoratePeersForClient()`：可见性 → **打码 + self 标记** →
  按用户级隐藏 → 套用显示名，`/v1/peers` 与 WS `peer_snapshot` 共用，杜绝两处顺序再次走偏。
  顺序是硬约束：偏好（hidden / names）以**对外 id** 为键，必须先打码才能套，否则针对本机实例的
  改名 / 隐藏会静默失效（这正是本轮修掉的缺陷）。
- **对外 id 收敛**：`self` 那行恒为规范形式 `local:<userId>`（与前端 `localPeerId` 同键），
  同账号的其它实例为 `local:<userId>:<instanceKey>`；`clientId` 明文仍不出服务端。
- **前端** 播放器页新增「客户端」「Web 播放器」两模块（按 `platform` 分流：`web` → Web 播放器，
  其余 → 客户端）。两模块**不判本机**（不置顶、不打角标），名字取「改名 → 设备名片 → 上报名」；
  支持改名与按用户级隐藏；实例离线（idle 超时）后不再渲染，重新心跳即回来。
- **验证**：后端 `963 passed / 130 files`（新增契约用例锁死「先打码后套偏好」与 self 规范形式）、
  前端 `vue-tsc` 0 错、`check-i18n` / `check-core` / 前端浮层与插件隔离守卫全绿。

## 8. 影响面与风险

- **音频路径不变**：本机音频仍在本机响；统一的只是"遥控与状态"。
- **离线语义**：客户端不在线时必须明确反馈。
- **向后兼容**：先"可列出 + 可看状态"，再"可遥控"，最后消费方接入。
- **协议接口收敛是大动作**：每一步合并后都要完整功能回归。
- **推送开销**：WS 全类型推送会增加消息量，需控频率与去抖。
- **`clientId` 易失**：网页清缓存即换 ID，改名认回需兜底策略。

## 9. 已定规则（原开放问题决议）

- **HA 卡片只是纯遥控器，不是推流目标**：它不出现在播放器页模块列表，也不出现在选择播放器的目标列表中，
  不能被推流 / 拉流。若日后 HA 要作为出声目标，须先以「Web 播放器」身份注册成播放端。
- **离线即自动消失**：本机型端离线（App 被杀 / 网页关闭）后，其条目**与 DLNA 等设备一样自动从列表移除**，
  不保留离线占位行，也不出现在选择播放器弹窗中。此处指**列表可见性**；服务端内部记录仍按现有队列回收策略
  （6h 未变动 且 离线 6h）清理，二者不冲突。
