# 倍速无缝切换-设计方案（AirPlay 桥 / Sendspin / 群组）

- 日期：2026-11-25
- 状态：**已定稿**（2026-11-25 20:02 评审通过：D1 接受延迟、D3/D5 撤销、D2/D4 按建议默认）
- 适用仓：MusicFlow（230 `/workspace/MusicFlow`），基线 `v4.15.3` / `b48cf086`
- 范围：服务端推流倍速（`atempo`）。不含客户端 UI、不含 DLNA 拉流改造

---

## 一、结论先行

1. **MA 做不到无缝切倍速**，且不是实现粗糙，而是拉流架构的天花板（证据见 §2.1）。因此"对齐 MA"与"真无缝"是互斥目标，本方案选择**超越 MA**。
2. 我们能做到无缝的物理基础：Sendspin 是**服务端主动推块 + 每块带绝对可听时刻戳**（`[0x04][i64 μs][data]`），改倍速不改 codec / sample_rate / channels ⇒ `stream/start|clear|end` 三条生命周期消息**一条都不用发**，设备端感知不到换流。
3. 落地方式：**不重建泵、不改 epoch、不改 timelineReseed**，只在泵内热换解码窗口 + 局部重锚输出轴 + 时间戳严格接续。
4. 顺带发现一个**独立缺陷**（§5）：rate≠1 时 `-ss` 用了输出轴毫秒当内容秒，seek 落点按倍速偏移。热换源必须用到这个换算，故作为 P0 前置修正。

## 二、前提与现状

### 2.1 MA 为什么做不到（逐条硬证据）

| 环节 | MA 实际代码 | 结论 |
|---|---|---|
| Sendspin | `providers/sendspin/player.py:2515` `playback_speed=1000 if is_playing else 0` | 这是 **Metadata 里的播放/暂停标记**（1000=播、0=停），**不是倍速** |
| AirPlay | `providers/airplay/*.py` 只有 `sample_rate`，无任何运行时速率控制 | RAOP/AP2 规范无变速信令，所有实现同理 |
| 群组 | `providers/group/*.py` 与 `sync_group` / `universal_group` 的 `grep speed` 为空 | 无群组级倍速概念，成员各自重开流 |
| 改倍速动作 | `player_queues/controller.py:504` set 之后走 `resume()` → `play_index()` | **整条流重建**（停旧流 → 新流带 `-ss` → 新锚点）= 有断点 |

MA 的 `set_playback_speed` 流程（`controller.py:504` 起）：先 `queue.elapsed_time = queue.corrected_elapsed_time` 结算旧速率下的墙钟秒，再 `resume()` → `play_index(item, resume_pos)` 重开流。`atempo` 只在 `streams/audio.py:1794` 的**起流一次性编码**里出现，运行中无法改变量。这是拉流模型的固有限制。

### 2.2 我们的现状（代码级）

泵内部时间轴口径（`streamEngine.ts:688-691` 注释已写明）：

> `rate` 是音频内容倍率；音频已在解码段被 atempo 压缩，因此泵内部**全部时间轴（`playCursorMs` / `durationMs` / `positionMs` / `pendingSeekMs`）统一是输出流毫秒**，对外只在 poll / seek 边界换算。

| 量 | 单位 | 位置 |
|---|---|---|
| `this.rate` | 倍率 | `streamEngine.ts:691` |
| `durationMs` | 输出流毫秒 = `内容时长 / rate` | 赋值 `:902`、`:1013` |
| `playCursorMs`（取帧游标） | 输出流毫秒 | `:559` |
| `reportedFloorMs` | 输出流毫秒 | `:572` |
| `playContentMs` / `paceAnchorMs` | 输出流毫秒 | `:508` / 起播区 |
| `group.positionMs` / `displayPositionMs` | 输出流毫秒 | poll 时 ×rate 换算 |
| 对外出口 | `posOut = positionMs × rate` | `playerCore.ts:991` |
| atempo 落点 | af 链**末尾** | `streamSource.ts:117` → `playbackSpeed.ts:49` |
| 历史保留判据 | `durSec / speed <= windowSec` | `streamEngine.ts:384` |

**当前改倍速的路径**（这就是断点根源）：

```
客户端 POST /peers/:id/speed
  → QueueController.setPlaybackSpeed (QueueController.ts:681)
     → setPlaybackSpeed 写 settings KV (playbackSpeed.ts:109)
     → 读实时现场取 posSec（内容秒）
     → playCurrent(playerId, base, posMs, "speed")   ← 整条流重建
        → playCore / playGroupCore → 新 GroupPump 或泵重起

```

泵侧 `setPlaybackRate()`（`:694`）注释即写明：**"下一次 play 生效；运行中变速由 QueueController 重投实现"**。也就是说泵已具备"按 rate 起流"的能力，缺的只是"运行中换 rate"。

## 三、目标语义（真无缝的定义）

### 3.1 三条硬定义

1. **不发任何生命周期消息**：切倍速前后日志中不得出现 `stream/start`、`stream/clear`、`stream/end`。
2. **同一个 `GroupPump` 实例**：不得 `stopGroupPump`，不得 `new GroupPump`。
3. **时间戳严格接续**：新窗口首帧 ts = 旧窗口末帧已推 ts + 帧长（25ms），**不得重打** `nowUs() + lead`。

### 3.2 可观测判据

| 判据 | 阈值 |
|---|---|
| 泵实例 | 日志 `[pump][rate]` 前后 `song=` / 实例计数不变，无 `[pump][play]` |
| 内容位置连续 | 切换前后 `group.positionMs × rate` 差 ≤ 1 帧（25ms） |
| 双机 tick | iEAST / HiVi 的 `delta` / `late` 无跳变，test5 双机残差 ≤ 50ms |
| 设备端 | 听感无静音间隙；`inQ` 不出现 ≤200ms 断粮 |
| 桥 | 无 `bridgeTimelineReset`；`notifyBridgeGeneration` 代数键不变 |

## 四、核心设计

### 4.1 一句话

**预建新窗口 → 提交切换 → pushLoop 下一拍换引用 + 局部重锚 → 关闭旧窗口。**

切换动作全部发生在"已解码但未推送"的层面，设备端看到的样本流与时间戳都是连续的。

### 4.2 时序图

```
t0  switchRate(2.0) 被调用（旧窗口仍在正常推流，不断粮）
t0  ├─ C0 = playCursorMs × r0           ← **建窗基准**内容位置（内容毫秒）
t0  ├─ 异步建新窗口：-ss = C0/1000、af 末尾 atempo=2.0
t1  └─ await ready()                     ← 预填充完成（旧窗口持续供流，前沿已推进）
t2  ├─ C1 = playCursorMs × r0           ← **提交时刻**的前沿内容位置（C1 ≥ C0）
t2  ├─ 新窗口内 seekTo((C1-C0)/r1)      ← 命中已解窗口，只改下标，零成本
t2  └─ 提交 this.pendingSwap = { win, rate: r1, contentMs: C1 }
t3  pushLoop 下一拍检测到 pendingSwap：
    ├─ win = this.window（局部变量换引用）
    ├─ 重锚输出轴：playCursorMs = C1 / r1、durationMs = 内容时长 / r1、
    │              reportedFloorMs / playContentMs / paceAnchorMs 同比换算
    ├─ paceAnchorWall = Date.now()（否则 dueMs 全落在过去 → 灌爆设备）
    ├─ rateSwitchTsUs = 旧末帧ts + FRAME_MS×1000（时间戳接续，不重打）
    ├─ group.displayPositionMs 保持派生语义（不写历史最大值）
    └─ 旧窗口 close()（回收 ffmpeg）
t3+ 后续帧按新 rate 推进，ts 沿 rateSwitchTsUs 累加
```

> ⚠️ **切换点必须取 C1（提交时刻的前沿），不能用 C0（建窗时刻）**。
> `ready()` 通常耗时 1~2s，期间旧流继续推，前沿已从 C0 推进到 C1。
> 若按 C0 提交，就等于把 C0~C1 这段**已经推给设备的音频再推一遍** —— 听感是"倒退重播 1~2 秒"。
> 新窗口是按 C0 建的（`-ss C0`），要追到 C1 需在窗口内 `seekTo` 一次：偏移量 `(C1-C0)/r1`（输出轴毫秒），
> 该点必然落在已预填充区间内 ⇒ 命中路径只改下标，不重起 ffmpeg（`streamSource.ts:310-312`）。
> 这一步是本方案最容易漏、后果最明显的一处，单测必须钉死。

### 4.3 时间轴重锚公式（必须精确到这一层）

设切换瞬间旧倍率 `r0`、新倍率 `r1`、旧游标 `P0`（输出流毫秒）。

> `P0` 指 **§4.2 中提交时刻的前沿 C1**（取 `C1 = playCursorMs × r0` 再折回输出轴），
> 不是建窗时的 C0。取错就是"倒退重播"。

```
内容位置      C  = P0 × r0            （单位：内容毫秒，不变量）
新游标        P1 = C / r1 = P0 × r0 / r1
新时长        durationMs₁ = durationMs₀ × r0 / r1   ≡ 内容时长 / r1
新下界        reportedFloorMs₁ = reportedFloorMs₀ × r0 / r1
新起播基准    playContentMs₁   = playContentMs₀  × r0 / r1
```

**必须重锚的字段**（全部输出流毫秒）：`playCursorMs`、`durationMs`、`reportedFloorMs`、`playContentMs`、`paceAnchorMs`、`pendingSeekMs`（若有）、`group.positionMs`、`group.displayPositionMs`。

**绝不能重的字段**：`playWallMs`、`paceAnchorWall`（墙钟，只重置为 now）、`rateSwitchTsUs`（时间戳，只能接续）、`epoch`、`timelineReseed`、`handoffTsUs`。

> 为什么 `posOut` 会自然连续：出口是 `posOut = positionMs × rate`。重锚后 `P1 × r1 = C × 1000`，与切换前 `P0 × r0 = C × 1000` 相等 ⇒ 进度条不跳。这不是补丁，是等式成立。

> ⚠️ **`this.rate` 与输出轴重锚必须同拍原子提交。**
> `pollCore` 的 `rate` 读的是**泵的** `playbackRate`（`playerCore.ts:990`，注释已写明"倍率以泵为准"）。
> 若在 `switchRate` 入口就先 `this.rate = r1`、等 pushLoop 下一拍才重锚 `positionMs`，
> 那这一拍里 `posOut = 旧 positionMs × r1` 会**瞬间跳一次**（客户端 UI 直接可见）。
> 正确做法：新 rate **只存进 `pendingSwap`**，由 pushLoop 换源那一拍把
> `this.rate = r1` 与 `playCursorMs / durationMs / reportedFloorMs / positionMs` 的换算
> **在同一条同步语句序列里一次写完**（中间不得 await）。
> 这与"一个数字不能同时当判定和显示"是同一条铁律的变体：对外出口读的两个量必须同源同拍。

### 4.4 为什么"不改 epoch、不改 timelineReseed"

`pushLoop` 的重锚分支里会调 `notifyBridgeGeneration(this.epoch * 1_000_003 + this.timelineReseed, "track"|"rehost", ...)`（`:1510` 附近）。

- 改 `epoch` ⇒ 桥侧判为 **track 边界** ⇒ 换代 + 发 BOUNDARY ⇒ **断点**；
- 改 `timelineReseed` ⇒ 桥侧判为 **rehost** ⇒ 重锚 ⇒ **断点**。

两者都会毁掉无缝。故新增**独立序号** `rateSeq`，pushLoop 用它做局部重锚判定，且**不**触发 `notifyBridgeGeneration`。这是本方案最关键的一处设计约束。

### 4.5 为什么窗口要热替换而不是重建泵

`pushLoop` 里 `const win = this.window`（`:1325`）在循环启动时**一次性固化**，运行中改 `this.window` 对在飞的循环无效。

- 方案 A（选定）：把它改成 `let win = this.window`，并在循环内加一段 `if (this.rateSeq !== consumedRateSeq) { win = this.window; ...重锚... }`。零 epoch 扰动。
- 方案 B（否决）：`this.epoch++` + 重起 `pushLoop` —— 会触发桥换代判定，等价于断点。

### 4.6 桥为什么天然受益、且不能碰

- 桥的 `rate: SENDSPIN_RATE`（48000）是**采样率常量，不是倍速**。桥只认"PCM 样本连续"，泵换了 rate 后样本流依旧连续 ⇒ 桥无需任何改动。
- 切换时**不得**下发新 `bridgeSpec`，否则 `syncGroupBridges` 会触发桥重锚 / hold chunk ⇒ 断点。

#### 4.6.1 桥的时间基不是独立的（决定 AirPlay 能否真无缝）

```ts
// bridgeSession.ts:245 —— 漂移对齐
targetFrames = round((tsUs - A) * rate / 1e6)   // rate = 采样率(44100/48000)，A = 锚点(host µs)
```

`tsUs` 是**组时间线可听时刻**（`bridgeSession.ts:2` 头注释）。桥做的是把这个 ts 映射成 RAOP 帧位置，而 `rate` 是**采样率**。

atempo 不改变输出采样率（恒 48k 硬编码），所以变速前后这条映射的**线性关系完全不变**。桥是"按 tsUs 到点投递"（有 `target` vs 实际位置的漂移对齐），不是"收即发"。

⇒ AirPlay 侧与直连 Sendspin 共享同一条时间轴 ⇒ 同一 ts 时刻变速 ⇒ **不错位**。

#### 4.6.2 成员延迟补偿的落点：每帧、时间量

```ts
// server.ts:1281 / :1664
b.pushAudio(e.data, e.tsUs - ahead + shift)
```

- `ahead` 是**时间提前量（µs）**，**每帧独立施加**，不是锚点级；
- 故换源后新帧只要走**同一 ts 接续源**，补偿自动一致 —— 不会二次补偿，也不会漏补；
- `ahead` 是时间量而非内容量 ⇒ 变速不改变采样率 ⇒ 补偿量仍然正确。

⚠️ 这两条互为前提：若将来引入**非 48k 输出或变采样率**方案（如按倍速改采样率来"省带宽"），4.6.1 的线性映射与 4.6.2 的时间量语义**会同时失效**，本方案的无缝结论随之作废。

### 4.7 适用范围矩阵（结论）

| 拓扑 | 无缝（不断流） | 同步（不错位） | 依据 |
|---|---|---|---|
| Sendspin 单设备 | ✅ | — | 单泵单环 |
| AirPlay 单设备（走桥） | ✅ | — | §4.6.1 |
| 纯 AirPlay 组（`isPureBridge`） | ✅ | ✅ 桥的 A 锚点是唯一时间基 | §4.6.1 |
| 混合组（AirPlay + Sendspin） | ✅ | ✅ 共享 ts 轴，同 ts 时刻变速 | §4.6.1 + §4.6.2 |
| DLNA | ❌ | — | 拉流必须换 URL（见 §6 D） |

**边界：无缝 ≠ 立即。** 已推给设备/桥的旧速率 PCM 无法撤回（撤回只有 `stream/clear`，那是断点）。真正变速时刻 = 推送前沿那个 ts，听感延迟 ≈ 该成员的推送提前量（Sendspin `send_ahead` 800ms 起；桥按成员延迟表）。关键是**"晚但齐"**：延迟对组内所有成员落在同一 ts 点，同时变速，不是依次变速。

## 五、P0 前置修正：`-ss` 口径错位（独立缺陷）

### 5.1 现象与推导

`PcmWindow` 的坐标系是**绝对交错样本**（`streamSource.ts:136-137`）：

```ts
const startSample = Math.max(0, Math.floor((startMs / 1000) * SAMPLE_RATE * CHANNELS));
this.baseSample = startSample;
this.spawn(startMs / 1000);      // ← 同一个 startMs 既当输出轴基准，又当 -ss
```

- `baseSample` 用输出轴毫秒换算样本，**正确**（内容 C 对应输出 C/r 秒样本，48k 恒定）；
- 但 `spawn(startMs/1000)` 传给 ffmpeg 的 `-ss` 是**内容时间轴**，期望值是 `C`，实际拿到的是 `C/r`。

⇒ rate=2、拖到内容 100s：`pendingSeekMs = 50s`（`armSeek` 已除 rate，`:2466`），`-ss 50` ⇒ 从内容 50s 起播。**落点偏移因子 = rate**。rate=1 时无偏差，所以日常测试（默认 1x）发现不了。`seekTo()`（`:310-327`）同款问题：`target` 是输出轴，`-ss target/1000` 也是内容秒。

### 5.2 修法

把 PcmWindow 的"坐标基准"与"起播内容点"拆成两个参数：

```ts
// 旧：constructor(source, startMs, opts?)
// 新：
constructor(
  source: WindowSource,
  pos: { streamBaseMs: number; spawnContentSec: number },
  opts?: { highSec?: number; retainWholeSong?: boolean; meta?: {...} },
)
```

- `streamBaseMs` → `baseSample`（输出轴绝对样本，保持不变的口径）；
- `spawnContentSec` → `-ss`（内容秒）；
- 换算只用 `playbackSpeed.ts` 的 `streamToContentSec` / `contentToStreamSec`，**禁止各链路自己乘除**（模块头注释已立此规矩）。

调用点同步：
- `streamEngine.ts:830 / :843`：`source(songId, startMsForSource, ...)` 的 `startMs` **统一改名为内容毫秒**，PumpSource 内部分别算 `streamBaseMs = contentToStreamMs(startMs, speed)`、`spawnContentSec = startMs/1000`。
- `streamSource.ts` 的 `seekTo()` 内部同样拆两值。

> 这条修完，倍速下 seek 落点才正确；热换源的新窗口 `-ss` 也才有可信口径。**必须先修，否则无缝切换会把错误落点固化进时间线。**

### 5.3 是否要单独发版

建议**单独一个 patch** 先修这条（可独立验收：1.5x 下拖到 60s，实际应从内容 60s 出声），再叠无缝改造。避免两类问题缠在一起难以归因。

| A11 | 新增日志 `[pump][rate] song=... r0→r1 内容Ms=... 游标 P0→P1 耗时=...ms` | 判据取证用；**必须是独立新语句**，不得改既有守卫钉住的行 |
| A12 | **原子提交**：`this.rate` 与输出轴重锚在 pushLoop 同一拍同步写完，`switchRate` 入口不得先改 `this.rate` | 见 §4.3 注记：否则 `pollCore` 出口会出现一拍 `positionMs × 新rate` 的跳变，客户端肉眼可见 |

## 七、风险与取舍

| 风险 | 评估 | 应对 |
|---|---|---|
| **atempo 接缝相位** | ffmpeg atempo 是 OLA 算法，换源首块有极小相位不连续，听感基本不可闻，但**非采样级严格连续** | 接受。采样级需自研 PCM 变速率，收益不抵风险（且会偏离"对齐 MA 的 atempo"） |
| **时间戳漏改一处** | 会重演"两套 ts → 水位按 `ts ≤ 已投` 判重丢帧"（`:1469` 注释的历史坑） | 所有推送路径共用**唯一** ts 接续来源 `rateSwitchTsUs`；单测钉死"换源后首帧 ts = 旧末帧 + 25ms" |
| **误动 epoch / timelineReseed** | 桥换代 ⇒ 断点，且下游 `pollCore` 的 `rate` 与泵不一致 ⇒ "音频 A 倍速、进度 B 倍速" | §4.4 独立 `rateSeq`；单测断言换源前后 `bridgeGenerationKey` 不变 |
| **`ready()` 期间再次改速** | 两个新窗口并存，旧的那个泄漏 | `rateSeq` 单调递增；提交时比对序号，过期窗口立即 `close()` |
| **预填充导致 CPU 双峰** | 新窗口预填充 + 旧窗口推流并行 | 与现有"下一首预取"同量级，已有先例；窗口上限 `readStreamWindowSeconds()` 不变 |
| **预取窗口 rate 陈旧** | 边界处下一首仍按旧 rate 解码 ⇒ 边界断音 | A8：换源时 `cancelNextTrackPrefetch(true)`（丢帧保"下一首是谁"） |
| **切换点取成 C0（建窗时刻）** | 把 C0~C1 已推音频重推一遍 ⇒ 听感"倒退重播 1~2 秒" | §4.2：必须取提交时刻前沿 C1 + 新窗口 `seekTo((C1-C0)/r1)`；单测钉死"无重复内容" |
| **`ahead` 被当内容量用** | 变速后补偿量按内容秒算 ⇒ 混合组永久错位 | §4.6.2：`ahead` 是时间量（µs），每帧施加；单测断言换源前后同一内容的 `ts - ahead` 关系不变 |
| **变速生效延迟被当成 bug** | 用户点完 2~3s 才变速，容易被当"没生效"反复点 | §4.7 边界：缓冲不可撤回的固有代价，D1 已接受。客户端自带倍速 UI（乐观更新），出口换算连续、显示不跳 ⇒ 无需服务端配合 |

## 八、验收方案

### 8.1 单测（`backend/src/services/sendspin/*.test.ts`）

必须新增/扩展，且**通过定向测试**（不是全量）：

1. **时间戳接续**：注入音源，泵起播 → 推若干帧 → `switchRate(1.5)` → 断言换源后首帧 ts == 换源前末帧 ts + 25_000µs。
2. **内容位置连续**：断言 `group.positionMs × rate` 在切换前后差 ≤ 25ms。
3. **不发生命周期消息**：桩 server 记录消息发送，断言无 `stream/start|clear|end`。
4. **泵实例不变**：断言 `pumpFor(...)` 返回同一对象，`activePumpCount` 不变。
5. **桥代数键不变**：断言 `notifyBridgeGeneration` 未被调用 / 键值不变。
6. **epoch / timelineReseed 不变**：直接断言字段。
7. **`-ss` 口径**（P0 修正）：mock `PcmWindow` 构造，断言 rate=2、目标输出轴 50000ms 时 `spawnContentSec = 100`。
8. **失败回滚**：`ready()` 抛错 ⇒ 旧窗口仍在、`rate` 未变、泵继续推流。
9. **无重复内容（切换点）**：模拟 `ready()` 耗时 > 0（旧流继续推进前沿），断言换源后首帧内容位置 == 提交时刻前沿 C1，且 C0~C1 区间**没有任何帧被推两次**。
10. **桥补偿关系不变**：桩 `pushAudio` 记录 `(tsUs, ahead)`，断言同一内容位置在换源前后的 `tsUs - ahead` 差值恒定（`ahead` 按时间量施加，不随 rate 缩放）。

同时必须过既有守卫脚本（改完后本地全跑 `check-*.mjs`，已知预存红 `check-element-overrides.mjs`）。

### 8.2 240 真机验收

按"①定向测试 → ②构建+热补丁到 240 → ③用户真机确认"流程：

1. 播放 Sendspin 群组（iEAST + HiVi），稳态后切 1.5x；
2. 检查日志：无 `stream/start|clear|end`、无 `[pump][play]`、有且仅有一条 `[pump][rate]`；
3. 采样判据（沿用 `docs/播放链路排障与采样手册.md` 口径）：双机 `delta` / `late` 无跳变、`inQ` 无 ≤200 断粮、test5 双机残差 ≤50ms；
4. 听感：无静音间隙（用户主观确认）；
5. 桥组同样跑一遍（AirPlay 桥 + Sendspin 混合组）；
6. DLNA 走一遍**确认它仍是有断点**（不追求无缝，但不得回归）。

**桥侧专项判据（换速那一拍必须全 0）**——这是"ts 接续是否真的连续"的最灵敏探针：

| 字段 | 期望 | 含义（`bridgeSession.ts` 头注释） |
|---|---|---|
| `realigned` | 0 | `|drift| > 1ms` 才置位；>0 即 ts 接续有偏差 |
| `insertFrames` | 0 | 补静音帧（内容落后/有洞）⇒ 听感有极小空隙 |
| `dropFrames` | 0 | 裁头帧（内容超前/重叠）⇒ 丢了内容 |
| `skipFrames` | 0 | 欠料超上限跳位（`bridgeSession.ts:253`）⇒ 听感跳段 |
| `late-drop` | 0 | `bridgeServer.ts:320`：ts 落后墙钟 |

稳态时这五项本来就全 0（本轮 19:14 采样即如此）。换速瞬间若任一项非 0，说明 ts 接续或 C1 取点有问题——**不需要听感判断就能定性**。

### 8.3 回归确认

- 暂停中改速 → 恢复后速率正确、进度不跳；
- 改速后 seek → 落点正确（依赖 §5 修正）；
- 改速后曲末自动切歌 → 下一首按新 rate；
- 重启后倍速从 `settings` KV 恢复（`playback_speed:<裸id>`）。

- `switchRate` 期间**边推边建**（不 pause 推流，否则断粮）；
