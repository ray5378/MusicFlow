## 2 CPU 尖峰定位：先分清是谁在烧

容器 CPU 是三个角色加起来的，不分开就只能看到一条曲线：

| 进程 | 角色 | 说明 |
| --- | --- | --- |
| `dist/index`（主进程） | 后端主逻辑 | HTTP、DB、插件调度、播放器管理 |
| `sendspin/child` | 推流子进程 | 25ms 推流循环，节奏的唯一权威 |
| `ffmpeg`（1..N 个） | 按需解码 | 换歌、预填、转码时出现，可以有多个并存 |

### 2.1 瞬时尖峰：`docker top` 快照

怀疑某个时间点 CPU 冲到几成甚至破百时，直接看进程级占用：

```bash
docker top musicflow -o pid,pcpu,pmem,args | grep -E 'dist/index|sendspin/child|ffmpeg'
```

配合容器总占用对照：

```bash
docker stats --no-stream --format '{{.Name}} {{.CPUPerc}} {{.MemUsage}}'
```

`docker stats` 是容器总量（多核累加可能超过 100%），`docker top` 的 `pcpu` 是单进程、同样按单核折算。**两者要对齐看**：容器 147% 而主进程只有 30%，多出来的部分基本都在 `ffmpeg` 上。

已在 4.11.17 验证过的典型归因：换歌瞬间新旧两首歌的 `ffmpeg` 解码重叠，`ffmpeg` 进程数从 1 变 2，容器 CPU 单点冲到 147%。这不是泄漏，是正常重叠，不做处理。

### 2.2 现场补充：`ps` 与 `/proc`

`docker top` 拿不到堆栈信息时，进容器看更细的现场：

```bash
docker exec musicflow ps -eo pid,ppid,pcpu,pmem,etime,rss,args --sort=-pcpu | head -20
```

- `etime` 判断是否刚 fork 出来的短命进程（`ffmpeg` 常见）。
- `ppid` 确认 `sendspin/child` 挂在 `dist/index` 下、没被孤立。
- 主进程 RSS 持续上涨而 CPU 平稳 → 方向是内存，不是 CPU，转到 §3 长周期采样看 `main_rss_mb`。

宿主机侧看是否被别的容器抢了 CPU：

```bash
cat /proc/pressure/cpu
```

`some avg10` 高说明宿主机整体在等 CPU，此时容器内的 CPU 曲线不能单独作为结论。

### 2.3 判断标准

| 现象 | 结论方向 |
| --- | --- |
| 尖峰与换歌时间重合，`ffmpeg` 同时出现 2 个 | 正常解码重叠，无需处理 |
| 尖峰期间 `sendspin/child` 独占高位 | 推流循环在空转，看 `STALL_MONITORING.md` 的 `LOOPLAG` / `LOOPDEATH` |
| 尖峰期间主进程高位且持续 | 主进程逻辑问题，进入 §4 在线 profile |
| 尖峰与任何事件都对不上，且周期性出现 | 用 §3 的 1s 采样抓，5s 采样会漏 |

## 3 长周期采样：两个粒度配合

仓库 `scripts/` 下已有三支脚本，装了就不用重写。参数、CSV 列、ALERT 类型的完整说明见 [STALL_MONITORING.md](./STALL_MONITORING.md) 第 2、3 节；这里只讲**怎么选粒度**。

| 脚本 | 粒度 | 用途 |
| --- | --- | --- |
| `sendspin-monitor-240.sh` | 5s | 长周期跑，看趋势、抓 ALERT 事件 |
| `sendspin-hires-240.sh` | 1s | 短周期跑，抓 5s 采样漏掉的瞬时尖峰 |
| `pull-240-monitor.sh` | 本地循环 | 在本机定时把远端产物拉回来 |

### 3.1 部署

```bash
scp -i /root/mykey -P 35320 scripts/sendspin-monitor-240.sh \
  scripts/sendspin-hires-240.sh scripts/pull-240-monitor.sh \
  root@192.168.10.240:/root/sendspin-monitor/
```

### 3.2 启动与停止（在 240 上）

```bash
cd /root/sendspin-monitor
nohup ./sendspin-monitor-240.sh >/root/sendspin-monitor/monitor.out 2>&1 &
nohup ./sendspin-hires-240.sh  >/root/sendspin-monitor/hires.out  2>&1 &

# 停止
pkill -f sendspin-monitor-240.sh
pkill -f sendspin-hires-240.sh
```

只跑一次看当前状态：

```bash
./sendspin-monitor-240.sh --once
```

### 3.3 回拉（在 230 的仓库根目录）

```bash
./scripts/pull-240-monitor.sh --once          # 拉一次
INTERVAL=120 ./scripts/pull-240-monitor.sh    # 每 120s 拉一次
```

### 3.4 粒度选择

- **问题已经复现、想要根因** → 两个都开。5s 给时间轴，1s 给尖峰瞬间。
- **线上观察、长时间挂着** → 只开 5s。1s 采样本身有开销，长期跑会污染 CPU 数据。
- **只要一个数字** → 别起脚本，用 §1 的 `docker stats` 一行足够。

**读取顺序**：`events.log`（先看有没有 ALERT）→ `monitor.csv`（再看那一分钟前后 CPU/RSS）→ `highs.csv`（最后看尖峰落在哪个进程）。

## 4 在线 profile：当前需人工接入

想回答"JS 里是谁在烧 CPU"，静态采样不够，需要 Node inspector。**当前代码中没有任何 `--inspect` 开关或内建 profile 入口**，容器默认启动命令不带 inspector，必须临时改启动方式接入。

### 4.1 现状

- 镜像启动命令不含 `--inspect`，也不能靠环境变量打开。
- 没有 heap snapshot、CPU profile 的采集脚本。
- 因此本节流程属于**人工临时操作**，做完必须恢复。

### 4.2 临时接入步骤

1. 在 240 上停止容器：
   ```bash
   cd /vol1/1000/SSD/docker/musicflow && docker compose stop musicflow
   ```
2. 用同一镜像、同一挂载，手工起一个带 inspector 的临时容器（只监听回环，靠 240 本机 `socat` 或 SSH 端口转发访问，**不要**把 9229 直接暴露到局域网）：
   ```bash
   docker run --rm -it --name musicflow-profile \
     --network container:musicflow-alt \
     -v /vol1/1000/SSD/docker/musicflow/data:/app/backend/data \
     -p 127.0.0.1:9229:9229 \
     ray5378/musicflow:latest \
     node --inspect=0.0.0.0:9229 dist/index.js
   ```
   > 启动命令的工作目录、可执行入口以镜像内的实际值为准，先 `docker inspect musicflow --format '{{.Config.WorkingDir}} {{.Config.Cmd}}'` 确认。
3. 建立 SSH 隧道到本地：
   ```bash
   ssh -i /root/mykey -p 35320 -L 9229:127.0.0.1:9229 root@192.168.10.240
   ```
4. 本地 Chrome 打开 `chrome://inspect` → 配置 target `localhost:9229` → 打开 `chrome-devtools://` 面板。
5. 在 **Profiler** 里 Start → 复现问题 → Stop，保存 `.cpuprofile`。
6. 采样结束**立即**停掉临时容器，用 `docker compose up -d musicflow` 恢复正式实例。

### 4.3 已有结论可复用

4.11.17 已做过一次 30 分钟采样 + 在线 profile，结论：`sendspin` 子进程约占单核 10%，JS 忙时里 `libflacjs` 占 61%、GC 占 3.3%；优化后子进程降到 6.9%，容器 CPU 的 mean / p50 / p95 分别为 19.1% / 18.2% / 40.5%。要判断"这次是不是同类问题"，先对照 [CHANGELOG.md](../CHANGELOG.md) 里 4.11.17 这一节，能对上就不用再 profile。

**注意**：`--inspect` 会显著改变时序，`sendspin` 的 25ms 循环在断点/采样期间会被拖慢，此时看到的卡顿是采样副作用，不能作为推流问题的证据。

## 6 排查纪律

1. **先对齐时间**。容器日志是 UTC，240 宿主机是本地时区，`monitor.csv` 的 `ts` 是采集机时间。三方对不上时，先统一到 UTC 再讨论。
2. **先看进程再下结论**。容器 CPU 高不等于主进程有问题，`ffmpeg` 重叠是最常见的假警报。
3. **短周期采样只在复现阶段开**。长期跑 1s 采样会自己制造 CPU 噪声。
4. **profile 是最后手段**。有 `docker top` + `highs.csv` 能回答的问题，不要上 inspector。
5. **不改 compose 的 `latest`**。排查期间如需临时变更启动方式，用独立容器，不动正式 compose 文件。
