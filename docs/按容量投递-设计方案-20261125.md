# 按容量投递（对齐 aiosendspin `BufferTracker`）设计方案

> 状态：**方案稿，待定稿**（本文只动文档，不动实现代码）
> 日期：2026-11-25
> 上游背景：《倍速无缝切换-设计方案-20261125.md》（v4.15.6 已发；方案 A 裁环已落地未发版）
> 关联：240 实测「混合组改倍速仍等 30 秒」

---

## 一、一句话立案理由

本仓把 Sendspin 音频**无条件全量推**给直连设备，设备装不下的部分无人负责；MA 用的 aiosendspin 在发给设备之前有一道**按设备宣告容量（`buffer_capacity`）的门控**，超出的内容留在服务器。

这道门控缺失带来两个后果：

1. **改倍速延迟被锁死在 30 秒**（混合组）。提交点必须落在「设备已收内容」之后，而设备被灌了 30 秒。
2. 服务端向设备**超发**，超发部分的去向（ws 发送队列 / TCP 窗口 / 设备拒收）目前**没有直接观测**，属于不可控状态。

---

## 二、现状：三段论

### 2.1 第一段：泵产出前沿 = 桥投递游标 + 30 秒

`SendspinGroup.pumpHeadroomUs()`（`server.ts`，搜同名）取「最落后的桥投递游标」，超过 `PUMP_LOOKAHEAD_DEFAULT_US = 30_000_000`（`contentDemand.ts:95`）就睡眠等消费追上。该常量对齐 MA `playback.py:922` 的 `sleep_to_limit_buffer(_PRODUCER_BUFFER_LIMIT_US)`。

**有桥在组里 ⇒ 泵写前沿稳态贴 30 秒。** 240 实测：`tailVsNowUs=35258397` / `cursorVsNowUs=5483397`，差 29.8 秒。

### 2.2 第二段：`pushFrame` 把每帧无条件发给全部直连成员

```ts
// server.ts:2964
for (const c of g.members) c.sendAudio(ts + this.sendspinDelayUsOf(c.clientId ?? ""), data);
```

`sendAudio()`（`server.ts:4297`）只做一件事：`ws.readyState !== OPEN` 就返回，否则打包发走。**没有任何容量、深度、流速判断。**

### 2.3 第三段：现有的容量闸只管「限产速度」，不管「回收深度」

`capacityLimitedPrefillMs()`（`server.ts:2761`）与 `prefillByteBudget()` / `bufferedCompressedBytes()` 三件套确实存在，但它们的消费点是 pacing 的 `wantFill`：

```ts
// streamEngine.ts:2216
const wantFill = prefillEnabled() && targetUs > ANCHOR_SAFE_LEAD_US
  && depthUs < targetUs - FRAME_MS * 1000 && byteOk;
```

语义是：

- `depthUs < targetUs` 且字节未超预算 ⇒ **不 sleep，全速灌**；
- 否则 ⇒ **按实时配速推进**（1x 产出）。

**关键：`wantFill=false` 只让产出速率降到实时，不会把已经超前的深度收回来。** 所以 30 秒前沿一旦形成就恒定维持，容量闸（10.6 秒）对它没有任何约束力。

> 240 现场印证：日志里 `预填充水位按设备容量钳制: 档位=15000ms → 实际=10611ms` 与 `预填充按真实排队字节封顶` 都在打，而 `tailVsNowUs` 仍是 35.26s —— 两条日志与 30 秒前沿**同时存在**，正说明它们是不同口径。

### 2.4 由此产生的改倍速延迟

热换源提交点取 `min(写前沿, 桥投递游标)`。混合组因为 `hasDirectMembers() === true` 被安全闸挡回写前沿（`streamEngine.ts` `resolveTrimPoint()`），于是：

| 拓扑 | 提交点 | 延迟 |
|---|---|---|
| 纯桥组 | 桥投递游标 ≈ now+5.5s | **约 5.5s** ✅（已实测） |
| 含直连成员 | 写前沿 ≈ now+30s | **约 30s** ❌ |

## 三、口径纠正（上一轮结论有误，此处归档）

| 说法 | 结论 |
|---|---|
| 「设备被迫丢 22 万帧」 | **错**。`droppedFrames` 是**桥**（`BridgeMember` / `bridgeSession.ts:1187`）的统计口径，不是 ESP32 的。`bridgeMember.ts:10` 明确写着「统计 droppedFrames 恒 0 —— 禁止丢最旧帧」。240 上那个恒定 220388 是桥侧累计，与直连设备的缓冲无关。 |
| 「`inQueueMs` 是设备库存」 | **错**。它是桥自己的 RTP 队列深度（1.5~2.7s），不是泵环、也不是设备环形缓冲。 |
| 「`prefill_buffer_ms` 改小就能提前变速」 | **错**。它只影响 `wantFill` 的追赶判定，稳态前沿由 `pumpHeadroomUs` 决定。 |

**结论：直连成员手里究竟有多少内容，本仓目前没有观测手段** —— 设备 tick 不上报水位，服务端不记账。这是本方案必须先补的第一块地基（见 §5.1）。

## 四、MA 的做法（代码证据）

MA 的 Sendspin 走 `aiosendspin.server.push_stream.PushStream`，是**两道闸**：

**① 生产端 30 秒前瞻（服务端缓存）**

```python
# providers/sendspin/playback.py:82
_PRODUCER_BUFFER_LIMIT_US = 30_000_000
# playback.py:922
await push_stream.sleep_to_limit_buffer(_PRODUCER_BUFFER_LIMIT_US)
```

判据（`aiosendspin/server/push_stream.py:1035`）：`max(_channel_timing) − now > limit + 设备输出延迟` 就 sleep。30 秒存在**服务端排程队列**里。

**② 发帧前按设备容量背压（关键差异）**

```python
# aiosendspin/server/connection.py:3540 起，每帧发送前
buffer_tracker.prune_consumed(now_us)
if bytes_needed > buffer_tracker.capacity_bytes:      # 单帧比容量还大 ⇒ 直接丢
    ...Dropping chunk larger than the client's buffer capacity...
wait_us = buffer_tracker.time_until_ready(bytes_needed, duration_needed_us, end_time_us=...)
if wait_us > 0:
    self._block_role(role, now_us + wait_us)          # 这一帧不发，等设备腾地方
    return
```

`BufferTracker`（`aiosendspin/server/audio.py:36`）文档字符串原文：*"Track the bytes a client holds in its buffer and apply backpressure when needed."* `capacity_bytes` 来自设备宣告的 `player@v1_support.buffer_capacity`（spec 明确为 per-player 硬上限）。

**三点结论：**

1. MA 的 30 秒**不会全量到达设备**，设备手里永远 ≤ 自己宣告的容量。
2. MA 的阻塞是**逐 role 的**（每个 role 有独立队列与发送协程），阻塞一个 role 不影响生产端。
3. 过期帧 MA 是**丢弃**（`_check_late_binary`），不是硬塞。

## 五、方案设计

### 5.1 核心思路

**把「限产」补成「限投递」，并且让提交点认识「实收前沿」。**

泵仍然产到 30 秒（桥需要、late-join 回填需要、这是 MA 同款语义，不动）；直连成员只收「自己装得下」的那一段；于是**最落后实收前沿**从 30 秒掉到**桥投递游标级别**（240 实测 5.49s；容量窗口 9s 只是必要条件、不是决定量，见 §5.2 A 末段），提交点跟着提前，且**不需要给设备发 clear**（它们手上的内容都在提交点之前，属于合法保留）。**故本方案的实际收益是 30 秒 → ≈5.3~5.5 秒（混合组与纯桥组同量级），而不是容量窗口的 9 秒。**

### 5.2 三个改动块

#### A. 逐成员投递闸 + 已发未播记账

`SendspinConnection` 增加（对齐 `aiosendspin.BufferTracker`）：

| 字段/方法 | 语义 |
|---|---|
| `pendingAudio: deque<{tsUs, durUs, bytes, data}>` | 待发队列（**非阻塞**入队） |
| `bufferedBytes` / `bufferedDurationUs` | 已发但**尚未到达播放时刻**的字节/时长 |
| `prunePlayed(nowUs)` | 把 `tsUs + durUs <= nowUs` 的条目移出计数（等价 `prune_consumed`） |
| `canAccept(bytes)` | `bufferedBytes + bytes <= capacity_bytes` **且** `issuedFrontUs + durUs <= 桥投递游标 B`（见本节末段：缺后一条会重发） |
| `pumpMemberQueue()` | 循环出队发送，直到 `canAccept` 为假或队列空 |

`sendAudio()` 语义改为**入队 + 触发一次出队**；实际发送留在 `pumpMemberQueue()` 里。

**为什么必须非阻塞**：本仓 `pushFrame` 是单循环同步 `await` 全部成员。若在这里阻塞等容量，泵会 stall ⇒ `starvationUs >= STALL_GRACE_US(500ms)` 记 warning，`>= maxSilentDegradeUs()`（默认 5s）直接判「编码器持续零产出」**放弃本曲提前切歌**（`streamEngine.ts:2046-2053`）。这是绝对不能碰的红线。

出队触发用「每次入队 + 250ms 定时器」双保险，与现有 `ensureBridgePushTimer()` 同构。

**★ 必须同时钳住桥投递游标（2026-11-25 复核补正；缺这条会重发）**

只按 `capacity_bytes` 时，直连成员实收前沿 `D` 会停在容量窗口（1.6MB × 0.6 ⇒ ≈9s），而桥投递游标 `B` 只有约 5.5s ⇒ `D > B`。此时 §5.2 B 的 `C1 = min(B, D, 写前沿) = B = 5.5s < D`，等于把设备**已经收到**的 `(B, D]` 这 3.5 秒重新推一遍（ts 重叠 ⇒ 重复播放），正是本方案要消灭的东西。

组内一致的物理要求是 `D = B`，两侧都不行：

- `D < B` ⇒ 设备手上只到 `D`，新内容却从 `B` 起 ⇒ `(B − D)` **空洞**（prefill 当硬闸时的 0.5s 缺口即此）；
- `D > B` ⇒ `C1` 被 `min` 拉到 `B` ⇒ `(B, D]` **重发**。

唯一解是让门控把 `D` 精确压在 `B` 上：

```ts
canAccept(bytes) =
     bufferedBytes + bytes <= capacity_bytes                      // 设备装得下（对齐 BufferTracker）
  && issuedFrontUs + durUs <= group.bridgeDeliveryCursorUs();     // 且不超过桥游标（本仓新增）
```

泵的产出远快于实时，`D` 会自然贴住 `B`（差值 ≤ 1 帧 = 25ms），故裁环点 `C1 = D` 与桥游标重合。

**`prefill_buffer_ms` 参与本闸，并且就是「混合组改速延迟」的旋钮**（第三道闸：`endUs <= now + 档位`，组内统一上界）：

- 档位 **低于**桥游标（如 5s < 5.4s）⇒ `D = 档位` ⇒ 改速延迟 = 档位；
- 档位 **高于**桥游标 ⇒ `D = 桥游标`（被封顶），档位不产生额外效果。

⇒ 想更快把档位调小即可；**物理下限仍是桥游标 ≈5.4s**，再往下只能动桥的 lead（`FLOOR`/`HORIZON`）。
MA 差异：aiosendspin 只有 `BufferTracker.capacity_bytes`、没有 prefill 概念（它的设备侧水深由生产端 30s 与容量共同决定）；本仓多这道闸，是为了让设备侧水深可配置，并顺带成为改速旋钮。

> **240 真机实测**（2026-11-25，混合组 = esp32 直连 + 2×AirPlay，档位 10s）：
> `[pump][trim] B=5412ms D=5336ms tail=35437ms 采用=5336ms` ⇒ 改速 **30s → 5.3s**，
> `裁环=1206 帧 / 提前=30126ms`、`pump=2/0`（不换代）、`gen=2000006` 不变、
> `inQueueMs=2700` 稳定、`loss*=0`、异常关键字 0 条、队列丢弃 0。

#### B. 提交点改用「最落后实收前沿」

现在的安全闸是一刀切：

```ts
// streamEngine.ts resolveTrimPoint()
if (this.group.hasDirectMembers?.() === true) return null;   // 混合组 ⇒ 回落写前沿
```

改为：混合组不再直接 null，而是把「各直连成员的实收前沿」纳入候选，取三者最小：

```
C1 = min( 桥最落后投递游标, 各直连成员实收前沿, 写前沿 )
```

其中「直连成员实收前沿」= `max(该成员 issued 帧的 tsUs + durUs)`（即它确实收到过的内容末尾），由 A 块的记账直接给出。

**为什么这样就不会断音**：裁环只裁 `C1` 之后的内容，而 `C1` 恰好是所有接收方都还没拿到的第一个点 ⇒ 没有任何设备手里有「被裁掉的帧」，不需要 `stream/clear`、不需要重锚、不产生空洞。这与现有 C 案（对直连成员发 clear → 断 6~7 秒）本质不同。

**前提（由 A 块保证，不可省）**：上式取 `min` 仅在 `D ≤ B` 时成立。若 `D > B`，`min` 会给出 `B < D` ⇒ 重发设备已收内容；故 A 块门控必须同时钳「不得超过桥投递游标」，把 `D` 压在 `B` 上（见 §5.2 A 末段）。此时 `C1 = min(B, D, 写前沿) = D ≈ B`，与桥游标重合，三条不变式同时满足。

> 裁环本身的机制、`trimRingAfter()` 与 `cursorUs` 同拍回退，沿用已落地的方案 A 实现，本文不改。

#### C. 泵的 30 秒前瞻保持不变

显式声明：`PUMP_LOOKAHEAD_DEFAULT_US` **不动**。理由是它是桥的 lead 预算与 late-join 回填深度的共同来源，砍它会同时伤抗抖与回填。本方案的收益来自「设备侧不再被灌满」，不是「服务端缓存变小」。

### 5.3 数据流（改动后）

```
ffmpeg → 编码 → pushFrame
                   ├─ ring（recentByGroup）：照旧全量入环（桥投递窗口 + late-join 回填的基准）
                   ├─ 桥：bridgePushTick 按 [now+FLOOR, now+HORIZON] 窗口投递（不变）
                   └─ 直连成员：sendAudio → 入队 → pumpMemberQueue 按 capacity_bytes 门控出队
                                                          └─ 实收前沿 = 已出队 max(ts+dur)

switchRate → resolveTrimPoint → min(桥游标, 各成员实收前沿, 写前沿) → 裁环 → 提交
```

## 六、不变式（硬约束，代码处必须加注释钉死）

1. **ring 不因投递闸回退**。`recentByGroup` 按生产推进，它是桥投递与 late-join 回填的唯一时间基准（`server.ts:2965` 的 `ring.push` 逻辑不变）。
2. **成员 ts 仍是绝对内容时间戳**。投递延迟不改变 ts、不改 `sendspinDelayUsOf` 的补偿语义。
3. **裁环点 ≥ 每个接收方的实收前沿**。任何一次裁环都不能裁掉某设备已收到的帧，否则必产生空洞。
4. **`stream/start` 在首帧「入队」时宣告**（`flushAnnounceFor` 调用点保持在 `chunks.length > 0` 处），不能等首次真正出队 —— 否则弱网设备起播宣告被无限拖后。
5. **投递闸不得阻塞 `pushFrame`**（见 §5.2 A 的红线说明）。
6. **过期丢弃必须计数 + 限流日志**，可观测（对齐 MA 的 late-drop 语义，不能静默）。
7. 队列内存上限 = `capacity_bytes × 3`；逼近上限只告警不扩，正常情况下稳态占用 = `capacity_bytes × 0.6`，不会触及。

> 用户铁律：凡对齐 MA 的参数与逻辑，代码处必须注明 MA 出处（文件/行号或常量名）与本仓差异取舍。本方案涉及 `BufferTracker` / `prune_consumed` / `canAccept` / late-drop 四处，逐处标注。

## 八、风险与降级

| 风险 | 说明 | 处置 |
|---|---|---|
| 慢成员拖累全组变速 | 取 min 意味着一个弱网成员可以把变速点拖到很后 | 超过 `MEMBER_SLOW_TOLERANCE`（初始 15s）则从变速决策中排除该成员并 warn 日志；排除后它的内容在提交点之后，需要它自己追赶（下发 `stream/clear` + 重宣告只针对该成员，属降级路径） |
| 队列积压吃内存 | 正常稳态不增长（入队 1x、出队 1x） | 上限 `cap×3` + 告警；不自动扩 |
| 设备宣告容量为 0（旧固件） | 无法计算窗口 | 回退到现行为（全量直发），不改其延迟特性，日志标明「未宣告容量，投递闸关闭」 |
| 过期丢弃造成可闻静音 | 只会在抖动超过窗口时发生 | 生效窗口 = `min(桥游标 ≈5.5s, cap×0.6 ≈9s)` = 5.5s，仍是设备 `min_buffer` 500ms 的 11 倍；一旦发生即计数并降水位告警 |
| 投递闸影响起播延迟 | 首次入队即宣告，出队受容量门控 | 起播时队列空、容量全空，首帧立即可发，无额外延迟 |
| 与现有 `wantFill` 同口径打架 | `bufferedCompressedBytes()` 数的是 ring 未播字节（≈ 已发未播） | 两者口径一致，闸门触发时机天然同步；若出现不一致以投递闸为准（真实字节） |
