# 换歌取源延迟：跨进程预热断层（方案与取证）

> 版本：v4.10.3 起
> 适用：sendspin 桥接群组（含纯 AirPlay 组经桥路由）的自动切歌
> 结论先说：**预热其实一直在做，只是白做了** —— 成果锁在主进程，真正取源的泵在子进程，
> 两份 module-local 缓存互不可见。修复后起播取源从 3.2s 降到 ~0.2s。

---

## 1. 现象

自动切歌时，桥需要往设备补一段「间隙」才能对上新的锚点（`[airplay-bridge] {"ev":"gap-fill"}`）。
这段间隙时长**恰好等于**「开始获取音源 → 音源就绪」的耗时，实测 28 次：

| 指标 | 值 |
|---|---|
| 垫片次数 | 28（14 次切歌 × 2 段） |
| 平均 | 2631 ms |
| 最小 / 最大 | 479 ms / **6705 ms** |
| 合计 | 73.66 s |

这段时间设备端没有新音频可放，全靠曲末预排的缓冲顶着，**顶不住就是可闻静音**。

---

## 2. 静音阈值为什么是 9.78 秒

`曲末排空` 不是超时值，而是「设备端已经缓冲好的音频长度」：

- 实测 15 次排空全部落在 **9760–9786 ms**（`[sendspin] 曲末排空:桥续静音 ev=bridge-drain-fill durMs=9782`）；
- 与预填充水位日志一致：`档位=15000ms → 实际=10611ms`（按设备 `buffer_capacity` 钳制）。

换算成预算模型：

```
设备可容忍的取源耗时上限 = 曲末排空量 ≈ 9.78s
实测取源耗时             = 2.2 ~ 6.7s
剩余余量                 = 3.1s
```

> 取源超过 9.78s ⇒ 设备缓冲播完、新流未到 ⇒ 真空静音。

---

## 3. 根因：跨进程缓存断层

### 3.1 进程模型

```
主进程 (server)
├── QueueController ──► drainPreheat ──► resolvePlayableRow   ← 预热的"体检"在这里做
│                                   └──► prefetchCache        ← 整曲字节也在这里
└── supervisor
     └── fork ──► sendspin 子进程 (child.ts)
                   └── streamEngine.defaultSource
                         └── resolvePlayableRow                ← 泵的"体检"又做一遍
```

`child.ts` 文件头已明写约束：

> 本进程**不 import** `../player/*`（QueueController/PlayerController 属主进程）

`playableCache` / `fallbackCache` 都是 **module-local Map**，`fork` 出来的是独立 Node 进程，
**不共享**；`ipcProtocol` 里此前也没有任何预热/预取消息。

### 3.2 真机取证（2026-10-30 19:28–20:05）

| 观测 | 结果 | 说明 |
|---|---|---|
| 主进程预热 `resolve=` | 27/28 次 `cached ms=1~6` | 主进程视角：完美 |
| 泵侧 `RESOLVE-AUDIO` | 38 次 `ensure-ok ms=2874~3932` | 子进程视角：等于没预热 |
| 泵命中 `fresh-cache` | **0 次** | 决定性证据 |
| 成对时序 | `12:45:58.534 fresh-cache ms=1` → `12:46:13.233 ensure-ok ms=3157` | 同一首歌，13s 前算过，13s 后重算 |

单次取源拆解：

| 切歌时刻 | 开始取源 | resolve 耗时 | 音源就绪 | 合计 | resolve 占比 |
|---|---|---|---|---|---|
| 12:46 | 10.076 | 3.16s | 13.399 | 3.32s | **95%** |
| 12:01（最差） | 11.765 | 3.93s | 18.466 | 6.70s | 59%（余 2.77s 为字节未命中） |

最刺眼的一次：同一首歌被探测**两遍** —— 主进程 `done ms=3250`，子进程 `ensure-ok 3.93s`。

### 3.3 这与已有事故是同一类

`ipcProtocol.ts` 里早有反方向的先例：

```ts
| { t: "songUnplayable"; … }   // 子进程判死 → 主进程必须自己再记一次负缓存
```

注释写明 2026-10-28 的事故：「子进程 18:28:22 已判死，主进程 18:28:46 重播时仍读到 unknown」。
**负结论已经打通，正结论一直没打通** —— 本次补的就是这一半。

## 4. 方案 A：把预热下推到子进程

### 4.1 链路

```
曲末前 9s（主进程）
  QueueController.notePositionAdvance
    → preheatNextOnDrain → runPreheat（主进程 resolve，1~6ms）
        → warmHook(songId)                       ← 本次新增
            → sendspinWarmPreheat               （门控：fork 模式 + supervisor 在跑）
                → supervisor.post({t:"preheat", songId})
                    → 子进程 child.ts 消息循环
                        → warmSongInChild(songId)
                            → resolvePlayableRow   （在子进程内，~3s，但已在曲末之前）
                                ⇒ 子进程 playableCache 热

起播时（子进程）
  pump.defaultSource → resolvePlayableRow → getCachedPlayability = "playable"
    ⇒ fresh-cache ~1ms（原本 ensure-ok 3.2s）
```

### 4.2 三条设计约束

1. **只做 resolve，不建流、不取字节。**
   整曲字节由主进程 `prefetchCache` 预取；泵的 ffmpeg 从回环 `/rest/stream` 拉，本来就能命中
   （实测 0.17s）。在子进程重复预取只会白占内存与带宽。
2. **门控：本进程没有在用 sendspin 的组就不探。**
   纯 DLNA / 直连播放同样会在曲末前 9s 触发钩子；此时为主进程白探一次源（3s 对外探测）
   会占上游配额、可能踩限流。判据 `hasActiveGroupPump(server)`：泵按组注册、`stopGroupPump` 才删。
3. **幂等 + 永不抛。**
   同一 `songId` 只探一次（曲末 500ms 节拍会反复触发）；上限 512 条后整批清空。
   钩子抛错被吞在 `drainPreheat` 里，绝不冒到 tracker（与预热本体同一红线）。

### 4.3 为什么否掉另两条

| 方案 | 否掉原因 |
|---|---|
| B：主进程把解析结果（row + URL）推给子进程 | `fresh-cache` 返回的是**原始 songId 那行**，而主进程 `preferred-swap` 换过行时语义对不上，会引入静默错源风险 |
| C：取消 fork、sendspin 收回主进程 | 收益最大但动架构；fork 的存在本就是为了隔离渲染器崩溃 |

## 6. 验收判据（真机）

### 6.1 必须出现的日志

```bash
# 子进程侧预热（曲末前 9s，约 3s 完成）
docker logs musicflow 2>&1 | grep -a child-preheat
# 期望：ev=child-preheat song=<id> ok=1 reason=ensure-ok ms≈3000（或 cached 更少）

# 泵起播命中缓存（关键！）
docker logs musicflow 2>&1 | grep -a "RESOLVE-AUDIO" | tail -4
# 期望：resolve <song> -> <song> (fresh-cache) ms≈1
```

### 6.2 指标

| 指标 | 修复前 | 期望 |
|---|---|---|
| 泵 `resolve` reason | 全部 `ensure-ok` | 绝大多数 `fresh-cache` |
| `gap-fill` 时长 | 2.2–6.7s | ≤ 0.5s |
| 换歌静音 | 2.2–6.7s | 无感 |

### 6.3 不得回归

- 纯 DLNA 播放时**不该出现** `child-preheat`（门控生效）；
- `曲末预热` 日志仍应每首一次（原有链路未改）；
- 无 `child-preheat` 失败重试风暴（幂等生效）。

## 7. 残留风险

1. **子进程 resolve 与主进程结论可能短暂不一致**（源在 13s 内失效）。此时子进程拿到自己的
   结果，仍是正确行为（只是没省到时间），不会播错源。
2. **字节链路未纳入本次优化**。若某首的 `prefetchCache` 未命中（如 12:01 那次），仍会多出
   ~2.8s（ffmpeg 等 2s 首帧预缓冲 + 远端取字节）。这属于第二类问题，量级与时序都不同，
   如需治本应单独做（把预取命中率纳入监控）。
3. **门控依赖泵存在**。组刚建、泵还没建的那一瞬会被挡掉，但那也正是"还没起播"，
   此时泵自己探一遍即可，不影响正确性。

## 8. v4.10.3:预览下一首与起播判据对齐(2026-10-30)

### 8.1 现象(真机 21:29)

```
13:29:15.118  曲末预热 song=0ea5a2da resolve=done(reverify-ok)   ← 预热它
13:29:19.903  子进程预热 0ea5a2da ok=1 ms=4785
13:29:23.646  playCurrent source=auto-advance idx=0 song=0ea5a2da  ← 选择正确!
13:29:23.647  song 0ea5a2da 无可用音源,跳过(留在队列)             ← 4ms 后判死
13:29:26.151  playCurrent idx=37 songId=b13bc96b                   ← 实际改播另一首
13:29:29.054  pump resolve b13bc96b ensure-ok 2895ms
13:29:29.158  gap-fill 3000ms                                      ← 预热白做
```

### 8.2 根因

`judgePlayable` 的**第一道闸**是 `getCachedPlayability(songId) === "unplayable"` → 直接
`return "skip"`,而且**不打任何日志**(所以一开始看日志完全找不到线索)。

这条负缓存来自同一首歌更早一次 `ensurePlayableStream` 的换源穷尽
(`setFallback(songId, null, {transient:false})`,TTL 2 小时)。而紧邻的
`resolvePlayableRow` 走的是最后一档 `reverify-ok`(本行复核通过)—— **该分支不写正缓存**
(`addPlayable` 只在 `ensurePlayableStream` 内部调用),即便写也会被
「负缓存未过期期间拒绝写正缓存」挡掉。

于是同一首歌在两个判据下结论相反:**解析说能播、起播说判死**,负缓存赢在起播侧。

> 注:此前曾误判为「shuffle 预览偏差」,真机日志 `playCurrent source=auto-advance idx=0
> song=0ea5a2da` 已否掉该结论 —— 预测是对的,是它被跳过了。

### 8.3 修法

预览下一首时**跳过已被判死的歌**,与 `judgePlayable` 第一道闸同一判据:

- `peekNextSongId(peek, {skipDead:true})` 取 `peekUpcomingPositions(peek, 4)`,
  逐个看,跳过 `unplayable`,返回第一个还活着的;
- 默认(`skipDead` 不传)行为**逐字节不变**(只看第 1 个位置、不查缓存);
- 只认 `"unplayable"`:`unknown` / `transient` / `playable` 一律照常预热 ——
  「不把不知道当成死的」是 2026-09-11 定下的边界,不越界;
- 判据抛错 / 全被判死 → `undefined`(不预热),绝不抛。

### 8.4 效果

- 起播会跳过死歌时,预览直接指向**真正会播的那首** ⇒ 预热不再打偏;
- 若死歌的判死来自"实时直链复核"(负缓存会被逐出、预览看不到),仍可能差一位 ——
  这属于**不可预测**的一类,不构成本次修复的回归。

### 8.5 未一并修(单列)

`resolvePlayableRow` 的 `reverify-ok` 分支不写正缓存,导致"复核通过"这个结论传不到
下一道闸,该曲在 2 小时内会反复被判死。若要治本需给负缓存**区分来源**
(内容判官写的「试听片段」不可复活;换源穷尽写下的可被复核结论复活),
涉及 `streamFallback` 的数据结构与 2026-10-27「试听片段」事故的护栏,单独评估。
