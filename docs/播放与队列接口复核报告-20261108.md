# 播放与队列接口族复核报告

- 复核日期：2026-11-08
- 基线：旧栈 MusicFlow **v4.11.21**（`/workspace/MusicFlow`）
- 被测：新栈 **0.0.14**（commit c15a7dd，镜像 `ray5378/musicflow:0.0.14`）
- 范围：`POST /play`、`POST /peers/:peerId/queue/play`、`queue/enqueue`、`queue/index`、`queue/next|prev`、`queue/shuffle`、`DELETE /queue[/:index]`、`GET /peers/:peerId/queue`、`play-mode` 读写、空队列/越界/坏 peer/坏参数、播放模式应用顺序、队列持久化与重启恢复
- 明示排除：EOS 自动推进（另有专线）；播放器出声
- 方法：旧栈源码提取全集与分支 → 两栈逐条真实请求 → **以回读为准**（200 但队列/索引未变记假成功）→ 关键项 SQLite 落库佐证

> 隔离说明：写操作全部在隔离实例完成——新栈 `qrev-new1(46448)`、`qrev-new2(46451)`、`qrev-new3(46456)`，旧栈 node 进程 `46452`；各自使用 `/tmp/qrev/{n1,n2,n3,o1}/data/musicflow.db` 独立副本。主实例 **46421 全程只读、未重启**。隔离环境 ≠ 生产。

## 五、补测结果

### 1. 持久化与重启恢复（一致）
- 旧栈 46452 与 新栈 46448 各自建：本地队列 4 项、`currentIndex=3`、`playMode=shuffle`、`isActive=true`；DLNA 未知设备 2 项、`currentIndex=1`。
- 重启（旧 node kill+同 DATA_DIR 重启；新 `docker restart`）后回读：**items / currentIndex / playMode / isActive / updatedAt 全部保持**；`shufflePos` 两栈都从 2/0 归 0（洗牌游标不持久化，两栈一致）。DLNA 队列同样保持。
- 证据：`.qrev/evidence/persist_{new,old}_{pre,post}.json`

### 2. 权限（不一致，严重）
- 新建非管理员 `qrevna` 后：
  - 旧栈：自己本地队列 `POST /play` 200；对管理员 `local:<admin-uid>:victim` 的 `/play`、`queue/play`、`play-mode`、`GET queue`、`DELETE queue`、未知 DLNA `play` **全部 403「无权操作该播放器」**，vicitm 队列保持 1 条。
  - 新栈：上述跨用户操作 **全部 200 且真实生效**，victim 队列被清空（total 0）；未知 DLNA 为 503（也不是 403）。
- 根因：旧 `peers.ts:85-111` 对 `/v1/peers/:peerId/*` 统一套 `canControlPeer` + `rendererGrantParamMiddleware`；新 `routes/queue.py`、`routes/play.py`、`routes/playback.py` 对应路由均无该门禁（`services/access.py` 的 `allow_user` 仅用于 DLNA 设备路由）。
- 建议：把 `canControlPeer` 语义移植为 `/peers/:peerId/*` 与 `/play` 的前置校验，非属主 403。
- 证据：`.qrev/evidence/extra_{new,old}.json`

### 3. play-mode 合法值（一致）
- 旧/新都接受 `order / one / all / shuffle`；`repeat-one / repeat-all / random` 均 400。探针此前误用 `repeat-one`，已补测纠正。

### 4. `/peers` 实例标识（不一致，关联接口）
- 旧 `/peers`：每个本机实例一行，`peerId = local:<uid>:<instanceKey>`，`self` 标在当前实例。
- 新 `/peers`：多个实例**塌缩为同一个 `local:<uid>`**，`self=true` 标在基础行；注册返回也是 `local:<uid>`。
- 根因：新 `routes/peers.py:59-69` `_decode_peer` 只处理二段+header；`services/peers.py:17-22` 掩码时直接截掉客户端段。
- 影响：旧客户端拿 `/peers` 的 `instanceKey` 去 `GET queue / play`，新栈会写到"幻影键"，读自己真实键为空。
- 建议：实现 instanceKey↔clientId 双向映射，并在 `/peers` 返回实例级标识。

## 六、范围外但必须记录的差异：preProbe

- 旧栈快照 `preProbe` 为真实预取状态（`at/ready/scanned/misses/cooldownUntil` 有值）；新栈恒为零值/空，仅 `play_from` 写 `_pre_probe_at`。
- 根因：阶段 6 预取调度器未接线（新 `services/queue.py` 空状态初始化 + 仅 `:716` 写时间）。
- 判定：**缺失（已知边界，阶段 6）**，不纳入本次接口族结论；如客户端依赖该字段展示缓冲状态，需在阶段 6 完成前保持字段默认值契约。
