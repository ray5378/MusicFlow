> **适用版本**：MusicFlow v4.6.72+ 后端（2026-10-24 大改版：新增 AP2 模拟接收端床与跨机实测方案，群组规则更新）
> **本地-only 文档：禁止提交 GitHub**（与《架构与优化分析报告》《交接工作》同类约定）
> **适用对象**：本机（local）/ DLNA / AirPlay（RAOP）/ Sendspin / 播放器群组；单机与跨机（230↔231）
> **配套权威文档**：[`airplay-权威方案文档.md`](./airplay-权威方案文档.md)、[`sendspin-权威方案文档.md`](./sendspin-权威方案文档.md)

## 0. 为什么需要「模拟播放器 + 双端对账」

服务端的 `/status` 只证明「我以为我在播」，**不能证明设备真的出声**。历史上多次出现：服务端 `state=PLAYING` 而设备侧 PCM 全静音；RTSP 全 200 而会话根本没建立；设备真在播却被 5s 轮询判成 `STOPPED`。

所以验收必须**双端对账**：

| 侧 | 数据源 | 判据 |
|---|---|---|
| 服务端 | `GET /v1/peers/<peerId>/status`、`/queue`、HTTP 回执 | `state`、`position` 1:1 前进、流转回执落点 |
| 播放器侧 | PCM 文件增量 / RMS / 桥接 stats / 已拉流字节 | 增量 ≈ 采样率×声道×2 B/s，RMS > -60dB，多成员 stats 逐拍一致 |

## 2. 第一代测试床（230，单机真实协议模拟器）

### 2.1 一键起停

```bash
/root/restart_players.sh        # 停旧进程 → 起 FIFO 排空器 → 起 AP1/AP2 → 起 Sendspin
# 停止/清理
pkill -f shairport-sync; pkill -f sendspin_real_player.py
pkill -f basic_client; pkill -f dlna_mock.js; pkill -f drain.sh
```

### 2.2 DLNA 模拟渲染端

```bash
node /root/dlna_mock.js 49500 192.168.10.230
curl 'http://127.0.0.1:49501/__state'
```

| 控制端点 | 作用 |
|---|---|
| `/__ctl?ssdp=0\|1` | 停止/恢复回应 M-SEARCH（模拟设备消失/出现） |
| `/__ctl?http=0\|1` | 关闭/恢复 HTTP（模拟连接被拒） |
| `/__ctl?state=PLAYING` | 直接设定传输状态 |
| `/__ctl?notify=1\|0` | 主动发 `ssdp:alive` / `byebye` |
| `/__state` | 当前状态：`state` / `RelTime` / 已拉流字节 |

验收要点：`/__state` 的已拉字节应与播放时长同步增长（设备真的在拉流，不是只回 SOAP 200）。

### 2.3 AirPlay 接收端（shairport-sync AP1/AP2）

配置 `/etc/shairport-sync-ap1a.conf`、`-ap2a.conf`：设备名 `MusicFlow-230-AP1/AP2`，RTSP 7000/7100，输出 `pipe → /root/ap{1,2}a.pcm`（S16_LE/44100/2ch）。

```
shairport-sync --(FIFO)--> /root/ap1a.pcm --(drain.sh)--> /root/ap1a_out.pcm
```

> **必须**由 `drain.sh` 把 FIFO 排空到普通文件；抓取窗口用 `apwin.py` 记偏移→等待→读增量→`ffmpeg volumedetect`。
> **AP1（`CC9514CD4F9B`）有出流互操作问题，矩阵与跨机实测一律排除**，只用 AP2。

### 2.4 Sendspin 播放器

| 实现 | 名字 | 输出 |
|---|---|---|
| aiosendspin SDK（PCM） | `MF-230-Real-PCM` | `/root/ss_pcm_out.pcm` |
| aiosendspin SDK（FLAC） | `MF-230-Real-FLAC` | `/root/ss_flac_out.pcm` |
| sendspin-cpp `basic_client` | `MF-230-CPP-Player` | ALSA file → `/root/ss_cpp.pcm` |

```bash
/tmp/sendspin-venv/bin/python /root/sendspin_real_player.py \
    ws://<240>:38927/sendspin flac /root/ss_flac.fifo MF-230-Real-FLAC
```

- SDK 客户端不会自动重连：`sendspin_real_player.py` 内置 20s 无音频块看门狗，交给 `run_ss.sh` 守护重启。
- C++ 播放器 ALSA file 插件指向普通文件（`ALSA_CONFIG_PATH=/root/asound_cpp.conf`）；静音时仍写 0 样本，必须 RMS 二次判定。

### 2.5 本机播放器（local peer）

客户端 `POST /v1/peers/register` + 30s 心跳 + 每 4s 上报 `local-status`。判据：UI 进度与 `/status` 一致、`reportedAt` 持续刷新、切歌/暂停 1 个上报周期内跟随。

### 2.6 播放器群组（2026-10-24 更新，旧文档此处写反了）

- **群组成员只允许 `airplay:` / `sendspin:`；DLNA 不能入组。** 后端 `splitMemberId()` 只认这两个前缀，DLNA 写入直接 **400 拒收**（`tests/group/GroupManager.test.ts` 有 setMembers + applyMemberDelta 双路回归）。
- 这是刻意设计：群组出流 = sendspin pump → AirPlay BridgeRing（多成员 RAOP 并行握手 + BridgeRing 按墙钟取内容），DLNA 成员在组里永远静默。
- 入口已全部过滤：Web 群组页候选、HA 卡片 v2.8.4（`_canJoinGroup` + 拒绝提示）、Flutter 客户端（`_canJoinGroup`）。240 线上 11 个组 20+ 条 memberIds 无一 `dlna:`。
- **桥接成员位置基准 = `contentClock`**（pump 首帧 0 点），不是「会话已过时长」——组内成员互差应 <0.5s，出现「某成员比组快几十秒」先怀疑孤儿会话（§3.5）。

## 3. 第二代测试床：AP2 模拟接收端（`ap2_bed.sh`）

### 3.1 资产与启动

| 主机 | 接收端源码 | venv | bed 脚本 | 端口 | 设备名 |
|---|---|---|---|---|---|
| 230 | `/tmp/ap2recv` | `/root/ap2venv` | `/root/ap2_bed.sh` | 7200-7202 | `MusicFlow-230-AP2r1..3` |
| 231 | `/root/ap2recv` | `/root/ap2venv` | `/root/ap2_bed.sh` | 7300-7302 | `MusicFlow-231-AP2r1..3` |

```bash
# 230（PI 前缀用默认 aa5cb8df-…，230 专用）
cd /root && SRC=/tmp/ap2recv BASE_PORT=7200 PREFIX=MusicFlow-230-AP2r \
  IFACE=ens2 VENV=/root/ap2venv/bin/python ./ap2_bed.sh start 3

# 231（★ PI 前缀必须换，见 §3.3）
cd /root && BASE_PORT=7300 PREFIX=MusicFlow-231-AP2r \
  PI_BASE=bb6dc9e0-8a25-4350-902b SRC=/root/ap2recv IFACE=ens2 \
  VENV=/root/ap2venv/bin/python ./ap2_bed.sh start 3
```

### 3.2 起测前四步铁律（缺一步测量就不可信）

```bash
pkill -f 'ap2[-]receiver.py'            # ① 杀残留接收端（stop 的 pid 文件会过期，不可靠）
pkill -9 -f 'ap2venv/bin/pytho[n] -c'   # ② 清泄漏子进程（见 §3.4）
./ap2_bed.sh start N                    # ③ 起床
ss -lntp | grep -E ':(7200|7300)'       # ④ 确认 LISTEN
```

### 3.3 PI 前缀必须每台机不同

230/231 是同模板克隆（连 MAC 都可能同），`ap2_bed.sh` 默认 `PI_BASE=aa5cb8df-…`。**231 沿用默认会让它的三台被服务端按 PI 合并、设备表里根本不出现**。231 固定用 `PI_BASE=bb6dc9e0-8a25-4350-902b`。

### 3.4 泄漏与清理（每会话泄漏子进程）

- 接收端**每服务过一场会话就泄漏一个 `multiprocessing.spawn` 子进程**（`python -c` 形态）。实测累积 200+ 个、单个 50–88% CPU，把 2GB 小机打到 OOM（load 20+、swap 满）。
- 泄漏的表现就是「测量不可信」：组位置恒 0、握手 30s、矩阵偶发 FAIL。清掉后 load 回落到 <2。
- 清理命令固定为 `pkill -9 -f 'ap2venv/bin/pytho[n] -c'`（`[n]` 防自杀）。
- **`ap2_janitor.sh` 已停用**：播放中触发清理会打断当时那一路音频（造过假 FAIL）。跨场实测改为「块间整床重启」（§4.3）。

### 3.5 杀过接收端 ⇒ 必须 `docker restart musicflow`（孤儿桥接会话，待修）

接收端被杀后，服务端会留下**孤儿 bridge session**：`[airplay-bridge] stats` 单独一条时间线继续打印、`resync=0`、`clamped` 暴涨（实测 clock=8050s、clamped=2.2e10）；新组播不会替换它，该成员上报荒谬位置（实测 165.9s vs 组 23s）。`/peers/:id/stop` 与 `stopGroupAirPlayBridge` 都拆不掉，**唯一可靠清法是重启容器**。

- 判别：`docker logs -a --since 3m musicflow | grep 'airplay-bridge. stats'`，比对多成员时间线是否同拍。
- 待修线索（未实施）：`stopSession` 失败只 `log.debug`；`stopAirPlayMemberBridge(deviceId)` 已存在但未接入拆除链路。
- 真实设备断电/重启可复现同一问题。

### 3.6 pkill 自杀陷阱

**同一条 shell 命令里，`pkill -f <pat>` 的命令文本本身不得再含 `<pat>` 字样**（包括 grep 的路径、echo 的说明）。例：`pkill -f 'ap2-receiver.py'; grep PI /root/ap2bed/ap2-1/ap2-receiver.py` 会把自己杀掉。杀接收端一律走 pid 文件：

```bash
for d in /root/ap2bed/ap2-*; do [ -f $d/pid ] && kill -9 $(cat $d/pid) 2>/dev/null; done
```

## 4. 跨机验收方案（脚本在 240 上执行）

### 4.1 脚本与母本

- **母本在本机工作区 `_mf_impl/`**，经 rc.py `put`（持久到 /root）或 `exec`（临时上传运行）上机。240 `/root` 常驻：`mf_transfer_matrix.py`、`mf_fix_verify.py`、`mf_group_sync2.py`、`mf_group_mk.py`、`mf_song_ttfb.py`、`mf_rows.py`、`mf_chunks.sh`。
- 登录：脚本内置（BASE `http://127.0.0.1:46400/rest` + `/api`）。设备 peerId 形态：`airplay:<deviceId>`、`dlna:<uuid>`、`sendspin:<clientId>`、`group:<uuid>`。

### 4.2 挑歌（TTFB 决定 cast 成败）

`serveCastStream` 对 AirPlay 是整曲缓冲（`buffering:true`），`MF_CAST_TIMEOUT_MS`（30s）是硬顶。**慢歌（实测 TTFB 26–32s）必挂 cast**，快歌 0.08–0.13s。

```bash
python3 mf_song_ttfb.py          # 测 GET /rest/stream?id=&format=flac 首字节
# 只挑 TTFB<4s 且 dur≥90s 的歌；把选中 id（完整 uuid）喂给后续脚本的 MF_SONG_IDS
```

### 4.3 流转矩阵（`mf_transfer_matrix.py`）

```bash
# 同机可用别名；跨机必须写完整 peerId。一批 ≤5 格，后台跑 + tail 轮询
P='airplay:aa5cb8df-…-000000000001>airplay:bb6dc9e0-…-000000000001,…'
setsid nohup timeout 900 python3 -u mf_transfer_matrix.py \
    --pairs "$P" --seek 45 --out /root/tr_x1.json > /root/tr_x1.log 2>&1 < /dev/null &
```

- **块间必须整床重启**（230/231 各跑 §3.2 四步）：`pkill` 杀子进程后端口还在、会话能建，但音频管线已废——表现为「落点对但位置不前进」，序列恒 `[x, x+2, x+4, 0]`，是环境假红不是产品缺陷。
- 脚本内置判据（2026-10-24 版）：
  1. **响应落点 ≈ 源端定格值**（发起动作前定格，摘组 detach 也算「改变源端状态的动作」）；
  2. **响应说非 null ⇒ 目标端真在落点附近起播**（`wait_landed`：`state=PLAYING` 且 pos ∈ [落点−TOL, 落点+自请求起算墙钟+10]）；
  3. **跨设备 DLNA 目标走「晚读数」分支**：起播之后才读源端进度，allow += `transfer_ms`（设计意图，不是误差）；
  4. 源端基准落位校验，两次不达标 SKIP（不拖出连带假红）；
  5. 目标未起播且响应落点已对 → 自动重试一次。
- **排除 AP1**（`CC9514CD4F9B` = shairport-sync:5000，出流互操作问题）。

### 4.4 e2e：组 → 组内最后一台成员（`mf_fix_verify.py`）

```bash
MF_MEMBER_A=airplay:aa5cb8df-…-000000000001 \
MF_MEMBER_B=airplay:bb6dc9e0-…-000000000001 \
MF_SONG_IDS=<完整uuid>,<完整uuid>,… \
python3 -u mf_fix_verify.py <groupId>
```

三步判据：① 组→A，回执 position ≈ 源端定格值；② A→组内最后一台 B（不传 position），回执 ≈ 定格值且 B 真起播；③ 成员数 2→1→0（逐个 stop 全部干净）。

- **`MF_SONG_IDS` 条目必须完整 uuid 且带真实 duration**：`duration=0` 的裸条目会让组播被判「已播完」立刻 advance——组起播即 IDLE、连跳数首，看着像桥接挂了。脚本已改为「各 peer 队列 + 库首页建池过滤」，挑歌用 `_mf_impl/mf_pick.py`。

### 4.5 群组同步（`mf_group_sync2.py`）

```bash
python3 mf_group_mk.py mk x     # 建组（母本见 _mf_impl；230/231 成员 id 显式给出）
python3 -u mf_group_sync2.py <groupId> --observe 30 --tol 2.0
```

判据：各成员与组 position 差 ≤1s（脚本 tol 2.0）、各组进度比 1.00×。
**权威判据（内容同步铁证）**：

```bash
docker logs -a --since 3m musicflow | grep 'airplay-bridge. stats' | tail
```

多成员的 `w`/`m` 逐拍相同、`lead=850ms` 一致、`clock` 相差 <120µs、`clamped=0` ⇒ 出流齐。
**测量前必须整床重启且无孤儿会话**（§3.5），否则成员报出比组快几十秒的假红。

### 4.6 实测基准（2026-10-24，v4.6.72，9 设备：230×3 + 231×3 + DLNA mock + sendspin，AP1 排除）

| 项 | 结果 |
|---|---|
| 跨机流转矩阵 | 16/16 + 部署后复跑 7/7 PASS；跨机 AirPlay 落点差 **−0.62~−0.85s = AirPlay lead**，与同机完全同构，跨机无额外误差 |
| 跨机 e2e（组→最后一台） | 组→A 回执≈定格、目标起播 = 定格 −0.85s；成员 2→1→0 全干净 |
| 跨机群组同步 | 三成员与组差 max **0.31s**、各自 1.00×；bridge stats 三成员 clock 差 <120µs |

## 5. 验收判据汇总

### 5.1 单链路功能矩阵（第一代床，保留）

| # | 用例 | 操作 | 通过判据 |
|---|---|---|---|
| F1 | 起播 | `POST /v1/peers/<pid>/queue/play` | ≤2s `PLAYING`；10s 内 PCM ≥ 8s 且 RMS > -60dB |
| F2 | 暂停 | `POST .../pause` | `PAUSED_PLAYBACK`；PCM 停止增长；恢复后 position 不跳 |
| F3 | 停止 | `POST .../stop` | PCM 停止；队列保留；无残留会话 |
| F4/F5 | seek / 连续 seek | `POST .../seek` | 落点误差 ≤1s；两次都成功无挂死 |
| F6/F7 | 切歌 / 自然结束 | `next` / 播完 | `currentIndex+1` 新曲有声 / 自动下一首不重播 |
| F8/F9 | 音量 / 静音 | `volume` / `mute` | 设备侧跟随；真静音且取消后恢复 |
| F10 | 离线/回归 | 关设备 10s 再开 | 队列悬挂；回归后续播不从头 |

### 5.2 跨链路与跨机矩阵（第二代床）

| # | 用例 | 通过判据 |
|---|---|---|
| X1-X5 | DLNA↔AirPlay 流转、互斥、连续×10、快速流转 | 落点一致；**单条** RTSP 会话；`RestartCount` 不增长；设备闸串行 |
| X6 | 组同步（成员仅 airplay/sendspin） | 成员与组差 ≤1s；bridge stats 多成员 `w/m` 逐拍相同、`clamped=0` |
| X7 | 容器重启恢复 | `docker restart musicflow` 后续播成功；注意 ~3.5 分钟沉默期（§8） |
| X9 | **跨机流转**（§4.3） | 响应落点≈定格值 + 目标端真起播；跨机 AirPlay 落点差 = lead 0.85s（同机构） |
| X10 | **跨机 e2e**（§4.4） | 组→最后一台：回执≈定格、目标真起播；成员 2→1→0 |
| X11 | **跨机群组同步**（§4.5） | 成员与组差 ≤1s（基准 0.31s）；bridge stats clock 差 <120µs |

### 5.3 240 部署与复测闭环

1. 发版（改 CHANGELOG → commit → push main → tag）后**核对 CI 全绿**（tag 组 + main 的 ci——ci 只在 main push 触发）。
2. **240 不保证自动拉新镜像**：`/ping` 版本号落后就手动 `cd /vol1/1000/SSD/docker/musicflow && docker compose pull && docker compose up -d`。
3. 重启后 ~3.5 分钟沉默期（entrypoint chown 17GB data），健康窗口 ≥10min 再开测。
4. 复测流程 = §4 全套（矩阵 + e2e + 群组同步），在**新版本容器**上重跑。

## 6. 排障路径（按现象）

| 现象 | 先看什么 | 常见根因 |
|---|---|---|
| 设备列表没有目标 | 是否 host 网络 / 多播是否通；231 设备查 PI 前缀 | SSDP/mDNS 收不到；**PI 前缀与另一台机重复被合并**（§3.3）；`disabled=1` |
| 起播 200 但无声 | PCM 增量 + RMS | cast 未真正建立；有数据但全 0（音量/静音） |
| 流转 cast 挂死 30s | `mf_song_ttfb.py` 挑歌 | **慢歌 TTFB 吃满 cast 硬顶**（§4.2）；目标掉线 |
| 流转「成功」但目标静默、回执有落点 | 回执 `applied` | 旧版谎报缺陷（v4.6.71 已修：cast 失败 ⇒ applied=false ⇒ 回 position=null） |
| 落点对但位置不前进，序列 `[x,x+2,x+4,0]` | 是否杀过接收端子进程没重启床 | 音频管线已废，**整床重启**（§4.3） |
| 某成员比组快几十秒 | bridge stats 是否孤儿时间线 | **孤儿桥接会话**，`docker restart musicflow`（§3.5） |
| 组起播即 IDLE、连跳数首 | 队列条目 duration | **duration=0 被判已播完**，喂真实时长（§4.4） |
| 组位置恒 0 / 握手 30s / 矩阵偶发 FAIL | 泄漏子进程数 | **床脏**，§3.2 四步 |
| 容器反复重启 | `RestartCount` + 挂死日志 | 超时回调在定时器里 throw |
| 设备音量跳变到 20 | `[peer-volume] … ua=HomeAssistant` | HA 自动化干的（§7.1），与本项目无关 |

## 8. 环境陷阱

| 陷阱 | 说明 | 规避 |
|---|---|---|
| 230/231 内存仅 ~2GB | 接收端每会话泄漏子进程，累积 OOM | 每场实测前 §3.2 四步；测完清理 |
| PI 前缀重复 | 克隆机沿用默认 PI ⇒ 设备被合并不可见 | 231 固定 `PI_BASE=bb6dc9e0-…` |
| 杀接收端留孤儿桥接 | stats 单独时间线继续泵；stop 拆不掉 | `docker restart musicflow` |
| janitor 清理会打断播放 | 已停用 | 改块间整床重启 |
| `pkill -f` 自杀 | 命令文本含 pattern 即自杀 | `[n]` 技巧或 pid 文件 |
| PCM 写满磁盘 | `*_out.pcm` 无限增长 | 每轮前 `: >` 截断 |
| FIFO 不能直接读大小 | `ls` 显示 0 字节 | 走 `drain.sh` 落普通文件 |
| C++ 播放器无声但写盘 | ALSA file 写 0 样本 | RMS 二次判定 |
| `flutter test` 并发挂起 | 多文件并发静默卡住 | `--concurrency=1` |
| mDNS 缓存 | 改名/换 IP 残留 90s | 等 `STALENESS_MS` 过期 |
| 容器重启沉默期 | restart 后 ~3.5 分钟 chown | 健康窗口 ≥10min 再开测 |
| e2e 判据用绝对值 | cast 慢时「目标 pos≈定格值」天然不成立 | 用相对量判据（§4.3/§4.4 脚本内置） |
| PCM 互相关用文件头 | 量到的是「会话起始时刻差」 | 用尾窗 |
