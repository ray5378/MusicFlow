## 1. 为什么不能用 `/status` 当基准

`/status` 是「给 UI 看的出口」，不是「链路状态」。它自身有 4 类缺陷，拿它当基准等于给 bug 打卡：

| # | 缺陷 | 实测证据（本次基准窗口） | 后果 |
|---|---|---|---|
| 1 | `position` **整秒 int**（只有 sendspin 是 float） | 同一时刻 `group=45 / airplay=43 / sendspin=43.433` | 精度只有 1s，判不了 <1s 的漂移 |
| 2 | group 与成员**口径不一致** | `group − airplay` **p50 恒 +2.0s**，`zero%` 仅 2.85% | 换个目标看就差 2s，基准值取决于选谁 |
| 3 | 换曲窗口**两组描述不同曲目** | `group − airplay` **p95 = +223.8s**（group 还 hold 旧曲） | 曲线出现 200s 级假跳变 |
| 4 | `updatedAt` **每次 poll 刷成 now** | `uaAge` p50 **0.0ms** / p95 **0.5ms** / `>1000ms` 占比 **0%** | 时间戳无信息量，卡片“按上报时刻外推”形同虚设 |

出口**不返回** `buffering` / `reportedAt` / `displayPosition`（字段 dump 已核实：v4.15.8 的 `/status` 只有 `state/position/duration/volume/muted/speed/queueRevision/updatedAt/media`）。
所以「显示准不准」只能作为**待收敛指标**观察。

## 2. 采样面

| 面 | 来源 | 频率 | 关键字段 | 定位 |
|---|---|---|---|---|
| `tick` | `[airplay-bridge]` 日志 | **~2s 一条**（内部 250ms 采样聚合，`samples=25`） | `deltaUs` `deltaP95Us` `inQueueMs` `queueMs` `maxQueueMs` `realigned` `late` `lossReq/Resent/Miss/Stale/Future` `silenceChunks` `inserted/dropped/skippedFrames` `driftUs` `gen` `anchorUs` `leadUs` `timingAgeMs` | **A 层主判据** |
| `ring` | `ring-diag` 日志 | 事件式 | `inQMs` `budgetMs` `buffered` `pushed` `dropOld` `pull` `prefilled` | 设备真实水位 |
| `prog` | `[PlayerController][report]` | ~5s | `state` `pos`(小数) `dur` | 内部播放位置真值 |
| `media` | `/peers/{group,airplay,sendspin}/status` | 2s | + `bu` `ua` `uaAge` `rtt` | **B 层，仅记录** |
| `anchor` / `bridge-servo` / `bridge-ack` | 日志 | 事件式 | 锚点、投递游标、设备 ack | 定位用 |

v3（2026-11-26）新增：`bu`（`state=='BUFFERING'` 推导）、`ua`（`updatedAt` 原值）、`uaAge`（`RTT 中点 − updatedAt`，**即卡片实际外推的毫秒数**）、`rtt`、`ss`（sendspin 成员，peerId 每 60s 动态解析，不硬编码）。
另加「重启水位」`.last_run_cst`：重启后按 `--since` 接续，不再重复写入历史行。

## 3. 基准指标集（A 层）

### 3.1 投递 / 实收（tick）

| 指标 | 含义 | 健康方向 |
|---|---|---|
| `deltaUs` | 设备出音前沿相对锚点的**提前量** | 每设备各自稳定（HiVi 2.061s / iEAST 1.561s），**p5~p95 跨度 < 10ms** |
| `deltaUs.negPct` | `deltaUs<0` 占比 | **必须 ≈0**；正值大 = 该出声的位置没声 |
| `inQueueMs` | 设备侧待播队列 | 闸目标 2500ms；p50 2625 / p95 ≤2750 / max 2750 |
| `inQueueMs.overCapPct` | 超设备容量 4163ms 占比 | **必须 0** |
| `queueMs` | 待发包缓存 | ~205ms（与水位无关，恒定） |
| `realigned/min` | 对齐器重排增速 | 同 `gen` 内恒 0；**阶跃式**，跨世代才爆发 |
| `late/min` | 迟到帧 | 0.8~1.3 |
| `lossMiss` `lossStale` /min | 重传未命中 / 请求比缓冲更老 | **必须 0** |
| `silenceChunks` | 补静音块 | **必须 0**（可听缺口铁证） |
| `state.live%` | tick 正常态占比 | 100% |

### 3.2 设备水位（ring）

| 指标 | 基准值 |
|---|---|
| `inQMs` | p5 2400 / p50 2525~2550 / min 2375 |
| `budgetMs` | p50 450~475 / p95 600（预算远小于实有 = 有余量） |
| `bufferedZeroPct` | 100%（没有待补包积压） |
| `dropOld/min` | 0 |

### 3.3 播放位置（prog）

| 指标 | 基准值 |
|---|---|
| `advanceRate` | **1.0005**（曲中，剔除切歌/seek） |
| `backwardsCount` | **0** |
| `state` 分布（24min） | PLAYING 85.2% / BUFFERING 12.9% / IDLE 1.9% |

> BUFFERING 12.9% 不是异常——是每首换曲重建缓冲的必然占比（24 分钟约 6~7 首）。它的危害只在**出口把它报成“未播放”**时，而这属于 B 层问题。

## 4. 阈值与推导

| 判据 | 阈值 | 推导 |
|---|---|---|
| `silenceChunks` FAIL | > 0 | 补静音 = 已发生可听缺口 |
| `deltaUs.negPct` FAIL | > 1% | 正常恒 0；出现即前沿越过已投递内容 |
| `deltaUs.p50` FAIL | < 基准 − **800ms** | 实测波动仅 4ms（p5→p50），800ms = 200 倍；4.15.9 实测塌 1775~1827ms，余量充足 |
| `inQueueMs.p95` FAIL | > 基准 + **1200ms** | 基准 2725/2744 + 1200 = 3925~3944，仍低于容量 4163；越过说明投递闸失效 |
| `inQueueMs.overCapPct` FAIL | > 基准 + 5% | 基准 0%，+5% 容忍单次换曲瞬态 |
| `realigned/min` FAIL | > 基准 + **30** | 正常 0；30/min ≈ 每秒 0.5 次对齐 |
| `late/min` WARN | > 基准×3 + 3 | 正常 0.8~1.3 |
| `lossMiss`/`lossStale` WARN | > 0.05/min | 正常 0 |
| `state.live%` FAIL | < 99% | tick 非 live = 链路异常态 |
| `prog.advanceRate` FAIL | 偏离 1.0 > 0.02 | 位置推进异常（快进/慢放/卡住） |
| `prog.backwards` WARN | > 3 次/10min | 曲中回退 |
| `tick/min` WARN | < 20 | 实测 30.2；过低说明采样缺口 |

## 6. 判读流程

```
① silenceChunks > 0 ?
   ├─ 是 → 已确认缺口。看同刻 lossMiss/lossStale 与 ring.buffered
   └─ 否 ↓
② deltaUs < 0（或 negPct > 1%）?
   ├─ 是 → 设备前沿落后锚点。看 inQueueMs 是否同步异常
   │        ├─ inQueueMs > 4163 → 投递灌爆（4.15.9 形态）
   │        └─ inQueueMs 正常 → 设备实收滞后，查 pcap / bridge-ack
   └─ 否 ↓
③ inQueueMs.overCapPct > 5% ?
   ├─ 是 → 投递闸失效。查 prefill_buffer_ms / BRIDGE_FEED_CAP 是否生效
   └─ 否 ↓
④ realigned/min 暴涨 ?
   ├─ 是 → 时间线不稳（重锚/换代过频）。查 anchor 事件与 gen 变化
   └─ 否 ↓
⑤ late/min 暴涨 ? → 是 → 重传压力，抓 pcap 看丢包
```

**判定「服务端 vs 设备」**：看两台设备指标是否**对称**。
- 对称（4.15.9：两台 `inQueueMs` 都 100% 溢出、`realign` 增量 52242/52244）⇒ 服务端投递/时间线。
- 单台异常 ⇒ 该设备链路（WiFi / 固件）。

### 7.4 CI：每次发版自动跑一轮

`.github/workflows/playback-baseline.yml` 三层，职责不同：

| job | runner | 触发 | 判据 | 阻塞发版 |
|---|---|---|---|---|
| `sim-e2e`（5 拓扑 matrix） | `ubuntu-latest` | tag / 手动 | 真镜像 + 模拟接收端 + **切歌 5 次** + 全程采样 → 分拓扑绝对不变量 | 否 |
| `judge-selftest` | `ubuntu-latest` | push main / PR / tag | fixtures 断言（判读器与阈值未被改软、退出码契约、多拓扑切歌/帧判据） | 是 |
| `live-check` | `[self-hosted, musicflow-live]` | tag（需变量 `MF_LIVE_CHECK=true`）/ 手动 | 现网采 `--window 12` → 对宿主机真实基准 `--strict-devices` 判读 | 否 |

**L0 五种拓扑**（`MF_TOPO`，`strategy.matrix` 并行、`fail-fast:false`，任一失败不影响其余取证）：

| 拓扑 | 成员 | A 层真值 |
|---|---|---|
| `mixed` | airplay1 + airplay2 + sendspin | tick / ring（桥）+ sendspin 帧 |
| `ap-only` | airplay1 + airplay2 | tick / ring |
| `ap1-only` | 仅 airplay1 | tick / ring |
| `ap2-only` | 仅 airplay2 | tick / ring |
| `ss-only` | 仅 sendspin | **只有 sendspin 帧**（不建 RAOP 会话，不可能有 tick） |

- **不需要真机也不需要 self-hosted**。含 AirPlay 成员的组起 1~2 个 `shairport-sync`
  （各自独立 mDNS 名 `MF-CI-AP1/2`、独立 RAOP 端口、独立 FIFO 丢弃音频），
  A 层 `ev:"tick"` / `ring-diag` / `deltaUs` / `inQueueMs` 仍由
  `services/airplay/bridgeSession.ts` 在服务端计算，模拟接收端足以产出同口径数据。
- **纯 sendspin 组不能用 tick 判**：它不经过桥，A 层改用
  `backend/scripts/baseline/sendspin_frame_probe.py` —— 用 `aiosendspin==9.1.1` 以真实
  拨入播放器身份接入 `:38927/sendspin`，每帧写一行 `sendspin_frames.jsonl`，
  汇总成 `A_ssFrame`（帧数 / 最大帧间隔 / 每次切歌后帧增量）。
  两种接收端都起，才能避免「某种拓扑永远采不到证据」的假绿。
- 共同流程：10 首不同频率/时长的正弦音 → 建组 → `queue/play` 全入队 →
  每 25s `POST /peers/group:<gid>/next` 共 **5 次**，每次轮询 `/status` 确认 `songId`
  真的换了（写 `switch_log.jsonl`，只数 API 返回 200 不算）→ 采样 8 分钟 →
  `baseline_cap.py` → `invariant_guard.py --topo <...> --require-switch`。
- 判据是绝对阈值（不依赖真机基准，模拟设备 key 不同不会假 FAIL）：
  `deltaUs p50 ∈ [0.5,4]s` 且 `negPct≤1%`、`inQueueMs p95≤4163ms`、`overCapPct≤5%`、
  `realigned/min≤30`、`advanceRate∈[0.98,1.02]`、无回退；
  全拓扑追加 `A_switch.count≥5`、`failed=0`、`maxSettleMs≤25s`；
  有 sendspin 成员的拓扑追加 `A_ssFrame.chunks≥200`、`maxGapMs≤500ms`、
  `minPerSwitch≥20`。tick<20 算环境问题（exit 2），不冒充指标 FAIL；
  纯 sendspin 拓扑 `--min-ticks 0` 并跳过 tick 判据。
- **切歌暂态必须分段判（否则正常版也被自己判红）**：含 5 次切歌的采样里，
  v4.15.8 正常态在切歌窗口同样有 `inQueueMs` 拉高、`deltaUs` 下降、
  `realigned` 阶跃（混合组锚点 lead 5s + 预填充 ~10s）。`baseline_cap.py`
  用 `switch_log.jsonl` 的 `t0` + 15s 窗口（`MF_SWITCH_WINDOW_MS` 可覆盖），
  借采样器 tick 新增的 `_wall`(epoch ms) 把 tick / 音频帧拆成**稳态**与
  `switchWindow` 两段：绝对阈值只判稳态段；切换段只判「桥仍出 tick ≥3 条」
  /「每次切歌后仍收到 ≥20 帧」。这是分状态判，不是放宽阈值 —— 全程证据仍全量落盘。
  老样本没有 `_wall` 时自动退化为整段判，历史基准依旧可比。
- L1 不需要设备：三份真实样本（正常基准 / 前版正常 / 4.15.9 反例）固化成回归，
  它防的是「守卫被改软后线上永久假绿」——阈值被悄悄放宽、某条判据被删、设备失配被降级，都会在这里变红。
- L2 才需要真机（内网 self-hosted）。L0/L2 **绝不挂在 `build.yml` 的 needs 链上**：
  tag CI 门禁失败会触发回滚 job，把已推镜像打回旧 digest。体检只出 Job Summary + artifact，不允许反向动镜像。
- 设备 key 脱敏：fixtures 用 `DEVICE_ALPHA/DEVICE_BETA` 占位，只用于 L1；
  L2 必须用宿主机上的真实基准（含真实 MAC），否则 `--strict-devices` 会全员失配。

## 8. 已知盲区

| 盲区 | 说明 | 影响 |
|---|---|---|
| `displayPosition` 采不到 | 出口不返回，只合并进 group 的 `position` | 无法单独验证「显示轴 / 判定轴」分离是否生效 |
| `buffering` 采不到 | 出口不返回，采样器用 `state=='BUFFERING'` 推导 | 若某版本改用别的字段表达缓冲，`bu` 会失真 |
| `updatedAt` 无信息量 | 每次 poll 刷成 now（`uaAge` p95=0.5ms） | 无法用时间戳判断「上报是否陈旧」 |
| `realigned` 阶跃 | 同 `gen` 内不增长，换曲/重锚才爆发（实测 01:05~01:20 恒为 57267） | 短窗口可能为 0，**不能单靠它判死** |
| tick 频率 2s 而非 250ms | 日志聚合输出 | 2s 内瞬态缺口可能被平滑；抓瞬态必须上 pcap |
| 无 pcap 常驻 | 目前只有日志面 | 网络丢包需临时抓包（见 `曲中失声-抓包取证方法论与复盘-2026-10-31.md`） |
| sendspin peerId 会变 | psk 派生 hash，重配即变 | 采样器每 60s 动态解析；变更记在 `base_evt.log` 的 `sendspin target changed` |
| 4.15.9 反例 `silenceChunks=0` | 该时段设备未补静音块，但 `deltaUs` 100% 为负 | 说明「缺口」有两种形态：补静音（有记录）/ 纯滞后（无记录，只能靠 `deltaUs`） |

## 9. 维护规则

1. **改投递/桥/时间线代码后**：热补丁 → `baseline_guard.py --window 10` 通过 → 才算部署成功。不要只靠听感。
