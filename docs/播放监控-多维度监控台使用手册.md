# 播放监控台 —— 多维度采集与「可判定」使用手册

> 适用对象：需要观测 AirPlay / 群组播放质量、并在出问题时**直接判到层**的开发与运维。
> 配套文档：`docs/AirPlay播放中断-根因排查与已排除方向.md`（判据背后的血泪史，先读它再看本手册的判定码表）。
> 平台：240（fnOS，`192.168.10.240`），被观测设备默认 `HiVi H5MKII = 192.168.10.30`。

---

## 0. 为什么需要「多维度」而不是「看一个数」

过去所有误判都源于**单一信号当判据**：

| 误判 | 单一信号 | 为什么错 |
|---|---|---|
| v4.9.7 关掉看门狗 | 「播放中 timing 停了」 | 那是无声期的采样，不是健康期 |
| v4.9.8 每 5 分钟杀一次健康流 | 「ctrl 重传请求静默 = 通道死」 | 重传请求是**丢包驱动**，干净流必然静默 |
| 长期误判「设备在播」 | DLNA `GetTransportInfo` | AirPlay 直通 DSP，恒 `STOPPED` |
| 误判「设备已接管新会话」 | RTSP 200 | 协议层接受 ≠ 硬件接收端换了会话 |

因此本监控台的设计原则是三条：

1. **每个维度必须能单独"证伪"一件事**（不许两个维度其实是同一份数据换了字段名）；
2. **判据必须是"设备主动、周期性、与丢包无关"**（详见根因文档 §6 信号可信度分级）；
3. **一旦异常，输出必须指到层**（L1 网络 / L3 数据面 / L5 会话 …），而不是只报"有点问题"。

## 2. 九个采集维度（互不重叠，各自能证伪一件事）

| # | 维度 | 文件 | 间隔 | 能证明什么 | **不能**证明什么 |
|---|---|---|---|---|---|
| 1 | ping 设备 | `ping.log` | 0.5s | 设备 IP 层可达性、丢包率、RTT 抖动 | 设备是否在出声 |
| 2 | **ping 网关（对照）** | `ping_gw.log` | 1s | 区分「设备这一条链路差」与「整个局域网都差」 | 无线侧的具体原因 |
| 3 | 设备 WiFi | `wifi.log` | 5s | RSSI / `netstat` 连接态 / 信道 | 吞吐、干扰、重传率 |
| 4 | 设备本地播放器 | `ply.log` | 5s | LivePi 自报 `status`/`curpos` | **会撒谎**：假死期仍自报 `play`、`curpos` 空走 |
| 5 | DLNA 传输态 | `pos.log` | 1s | 仅 DLNA 直投时有效 | **AirPlay 直通 DSP ⇒ 恒 `STOPPED`**，不能判在播 |
| 6 | **UDP 抓包计数** | `udp.log` | 15s 窗口 | **设备 timing 请求数**（设备真的在问）+ **服务端 RTP 外发包数**（我们真的发出去了）+ 重传请求数 | 设备收到后是否解码出声 |
| 7 | 服务端资源 + 内核 UDP 栈 | `sys.log` | 20s | CPU/MEM/load；`netstat -su` 的**接收缓冲错误增量**（纯服务端丢包） | 容器内部线程阻塞点 |
| 8 | 服务端 tick + 日志事件 | 由判定器直接读 `docker logs` | 20s | 推流节拍 `deltaUs`、`silenceChunks`、`queueMs`、世代号 `gen`；`timing reply` 数；看门狗/重连/TEARDOWN/gap-fill 计数 | 设备侧任何状态 |
| 9 | 分层判定 + 汇总 | `verdict.log` / `summary.log` | 20s / 10min | 直接给结论码；跨时段对比 | —— |

### 2.1 抓包维度为什么值钱（本监控台的核心）

`udp.log` 一行：

```
2026-10-29T20:47:01 win=15s rtp_out=1748 timing_in=5 timing_out=5 ctrl_in=0 sync_out=14 other=0
```

报文长度即语义（2026-10-29 实测确认）：

| 方向 | 长度 | 语义 | 实测频率 |
|---|---|---|---|
| 240 → 设备 | `1428` | RTP 音频块 | ~116/s（8ms 一块） |
| **设备 → 240** | `32` | **timing(NTP) 请求** | 每 3s 一条（≈5/15s） |
| 240 → 设备 | `32` | timing 应答 | 与请求 1:1 |
| 240 → 设备 | `20` | sync / 控制 | ~14/15s |
| 设备 → 240 | `8` | 重传请求（ctrl 0x55） | **0 = 链路干净**；丢包才出现 |

**关键**：`timing_in` 是**设备主动发出**的，独立于服务端日志 —— 服务端日志里的 `timing reply` 只说明"我们回了什么"，而 `timing_in` 说明"设备还在不在问"。两者交叉才不会自欺。

## 3. 判定码表（`verdict.log` / `latest.txt`）

判定按**优先级从上到下**匹配，命中即停。

| 判定码 | 触发条件 | 指向层 | 处置 |
|---|---|---|---|
| `IDLE` | 无 tick、无 timing、RTP 外发=0 | —— | 没在播放，不判 |
| `L1_DEVICE_LINK` | ping 设备 `loss≥2%` 或 `avg>150ms` | L1 设备链路 | 查 WiFi/RSSI/信道；对照组看是否只有它差 |
| `RECOVERING` | `RTP_out<600/15s`（还没稳流）**或** 容器 `up<90s` | —— | **接管期豁免**：刚重启/刚起播时"有 RTP 无 timing"是正常的，别当故障 |
| `L5_SUSPECT` | RTP 已稳流(`≥600`)但 `timing_in=0`，**仅第 1 个窗口** | L5 会话 | 记账不告警；下一窗口仍为 0 才升级 |
| **`L5_SESSION_DEAD`** | **RTP 稳流 `≥600/15s`，且 `timing_in=0` 连续 ≥2 窗口(≥30s)，且容器 `up≥90s`**（设备 ping 正常） | **L5 会话** | **根因签名**：组级 `stop` → `queue/play` 恢复；45s 看门狗也会自愈 |
| `L3_DATA_STALL` | RTP 外发=0 且 `tick_age>12s` | L3 数据面 | 服务端没推流：查换歌/预取/源解析/子进程 |
| `L1_HOST_UDP_DROP` | `netstat -su` 接收缓冲错误**增量 >0** | 服务端内核 | 收包缓冲被丢：查 CPU/负载/缓冲参数（纯服务端原因） |
| `L1_LINK_DEGRADE` | 网关对照也差（`loss≥2%` 或 `avg>100ms`） | 局域网/上游 | 不是这台设备的问题，查 AP/交换机 |
| `WATCHDOG_RECOVERED` | 5 分钟内有 `liveness watchdog` 触发 | 自动恢复 | 说明 45s 心跳看门狗已重连新会话，记录频次 |
| `HEALTHY` | 以上都不命中 | —— | 正常 |

> ⚠️ **`L5_SESSION_DEAD` 的三道闸门是血的教训**（2026-10-29 21:01 误报）：容器刚重启时 `mem=5.082MiB`、新进程已推 20 个 RTP 包、设备还没发第一个 timing ⇒ 单靠"RTP>0 且 timing=0"会误判成根因。**必要条件 ≠ 判据**。看到 `L5_SESSION_DEAD` 的第一件事是核对同一行的 `up=` 和 `mem=`：`up` 很小或 `mem` 只有几 MB，说明是重启后的接管期，判定器本不该报。

`latest.txt` 单行含义（以实测为例）：

```
2026-10-29T21:06:09 verdict=HEALTHY | RTP_out=1753 timing_in=5 ctrl_in=0 | timing_log=12 tick_age=1.3 state=live silence=0 queueMs=20 gen=5000015 |
dev_loss=0.0% dev_avg=3.5 gw_loss=0.0% gw_avg=3.4 rssi=-48 netstat=2 | cpu=26.7% mem=442.6MiB udpErr=0 | up=322s wd=0 brk=0 recon=0 gap=0 td=0
```

| 字段 | 含义 | 健康特征 |
|---|---|---|
| `RTP_out` | 15s 窗口内发往设备的音频包数 | 1700~1800（≈116/s）；**<600 = 还没稳流，不参与僵死判定** |
| `timing_in` | 同一窗口设备 timing 请求数 | 4~6（每 3s） |
| `ctrl_in` | 重传请求数 | 0（干净）；偶发小值正常 |
| `timing_log` | 35s 内服务端 `timing reply` 行数 | 10~13 |
| `tick_age` | 最后一条 tick 距今秒数 | ≤2s |
| `silence` | `silenceChunks`（垫片静音块） | 换歌时短暂上涨，之后不持续增长 |
| `queueMs` | 桥内队列深度 | 个位数~十几 |
| `gen` | 世代号（换歌/重锚会变） | 播放中稳定，换歌跳变属正常 |
| `dev_loss/dev_avg` | 设备 ping | 0% / <10ms |
| `gw_loss/gw_avg` | 网关对照 | 0% / <5ms |
| `udpErr` | 内核 UDP 接收缓冲错误增量 | 0 |
| `up` | 容器已运行秒数（`docker inspect .State.StartedAt`） | 单调增长；**忽然变小 = 刚重启，接管期数据不可当故障** |
| `wd/brk/recon/gap/td` | 看门狗 / 熔断 / 重连 / gap-fill / teardown 计数（5min 窗口） | 全 0 |

## 5. 四个典型剧本（照着读就能定位）

### 剧本 A：健康
```
verdict=HEALTHY  RTP_out≈1750  timing_in 4~6  ctrl_in=0  tick_age<2  dev_loss=0%
```
→ 什么都不用做。

### 剧本 B：设备僵死（本轮根因签名）
```
verdict=L5_SESSION_DEAD  RTP_out=1700+  timing_in=0  ctrl_in=0  tick_age<2  dev_loss=0%  up=3600s
```
判读顺序：**我们在稳流（RTP_out≥600）→ 设备连续 ≥2 窗口不问（timing_in=0）→ 但 ping 正常（不是网络）→ 容器已经跑了一会儿（up 不小）** ⇒ 只能是会话没被设备接管。
**先看 `up=`**：`up<90s` 或 `mem` 只有几 MB ⇒ 这是重启接管期，不是僵死（判定器已内置豁免，但日志里可能有旧代码打的假警报）。
处置：
1. 等 45s 看是否出现 `WATCHDOG_RECOVERED`（v4.10.0 自愈）；
2. 若 60s 仍是 `L5_SESSION_DEAD`，手动恢复：`POST /peers/group:<uuid>/stop` → `POST .../queue/play {items,startIndex}`。

### 剧本 B'：接管期（别误判成 B）
```
verdict=RECOVERING  RTP_out=20~300  timing_in=0  up=15s  mem=5~400MiB
verdict=L5_SUSPECT  RTP_out=1700    timing_in=0  （只有这一个窗口）
```
→ 容器刚起 / 刚起播，等 30~60s 再看。**不要在这里动手**。

### 剧本 C：服务端没推流
```
verdict=L3_DATA_STALL  RTP_out=0  timing_in=0  tick_age=30+
```
→ 不是设备问题。查 `docker logs --since 5m musicflow | grep -a -E '换源|prefetch|unplayable|error'`。

### 剧本 D：网络真的差
```
verdict=L1_DEVICE_LINK  dev_loss=6%  gw_loss=0%     ⇒ 只有设备这条链路差
verdict=L1_LINK_DEGRADE dev_loss=6%  gw_loss=5%     ⇒ 整个局域网都差(不是设备)
```
对照 `ping_gw.log` 是这一条判断的关键 —— 没有对照组就只能猜。

## 6. 受控复现（**已实测：2026-10-29 未复现，结论要照这个读**）

> ⚠️ 会中断播放 15~30 秒。**只在需要取证时做**，做完立刻恢复。
> **执行前先读 §6.1 的实测结果** —— 这套操作在 240 真机上**没有**打出预期现象。

```bash
# 1) 记录当前队列(必须:恢复靠它重放)
python3 /tmp/mf240_snap_stop.py      # 快照 + 组级 stop

# 2) 跳过优雅关闭杀掉容器(kill -9 ⇒ 不发 TEARDOWN)
docker kill -s KILL musicflow && docker start musicflow

# 3) 等 30~60s,观察判定器
grep -v 'verdict=HEALTHY' /tmp/mf410/verdict.log | tail -5

# 4) 再等 45s,看 v4.10.0 看门狗是否自动触发
docker logs --since 3m musicflow 2>&1 | grep -a 'liveness watchdog'

# 5) 若仍无声,手动恢复
python3 /tmp/mf240_resume.py
```

### 6.1 实测结果（与预期相反，务必照实读）

| 阶段 | 原本期望 | **2026-10-29 实测** |
|---|---|---|
| kill -9 后 20~40s | `L5_SESSION_DEAD` | ❌ **没报**：`timing_in` 3→5，`verdict=HEALTHY`，**设备自行接管了** |
| 45s 后 | 看门狗 `timing 心跳已停 ≥45s` | ❌ **没触发**（因为 timing 一直是活的，看门狗本来就不该触发） |
| 重连后 | `raop reconnected` | 未发生 |
| 恢复后 | 设备出声 | ✅ 出声（**但不是靠我们恢复的，是设备自己接管的**） |

**结论：不发 TEARDOWN 也不会僵死。**「缺 TEARDOWN 是僵死致因」已被证伪。详见 `docs/AirPlay播放中断-根因排查与已排除方向.md` §11.1（E1）与 §11.2。

同时在 `docker restart` 场景抓到：`ANNOUNCE/SETUP/RECORD` 各 1 次、**`TEARDOWN` = 0**、设备 15s 内自行恢复出声；恢复的真实机制是 `sessions: stop token=A` → `prepare token=B`（**新 token = 新会话**），不是 TEARDOWN。

### 6.2 下一个该做的实验（唯一可能复现 12:12 那次的变量）

**长 warm 会话再重启**：连续换歌 15+ 首、跑够 1 小时后 `docker restart`。12:12 那次正是「4h 运行 + 15 次换歌」之后，**会话寿命**是目前唯一还没排除的自变量。做完之前不要改代码。

## 7. 踩过的坑（照着避）

| 坑 | 现象 | 正解 |
|---|---|---|
| `pkill -f` 自杀 | 命令 exit 127，后面全不执行 | 停/启分两条命令；模式用 `mo[n]` 括号技巧 |
| 重复 ping 实例 | **假丢包**（同一 target 两条线，一条丢就 50%） | 只允许一个 ping；校验 `ping.log` 行增速 = 2 行/秒（0.5s 间隔） |
| `docker logs -f` 长连接 | 容器 restart 后管道僵死，日志不再更新 | **轮询式**：每轮 `docker logs --since Ns` |
| `docker logs` 不带 `-t` | 无时间戳 ⇒ 算不出 `tick_age`（会话层判据失效） | 必须 `docker logs --since 35s -t` |
| `tail -F \| awk >> file` | fnOS 上 awk 重定向不 flush，文件空 | 改纯 shell `while read` 逐行写，或用 python |
| DLNA 位置当判据 | 恒 `STOPPED`、位置不动 | AirPlay 直通 DSP，位置类判据一律用服务端 tick |
| `getPlayerStatus` 当判据 | 假死期仍自报 `play` | 只作参考，不作判据 |
| `netstat -su` 看绝对值 | boot 以来 7 万多次，误以为一直丢包 | 必须看**增量**（`sys.log` 的 `d_rberr`） |
| 抓包用 `-i any` | 同包被重复计数（伪 2 倍） | 指定物理口 `-i eno1-ovs` |

## 9. 与发版/运维流程的关系

- **热补丁或重启前**：先组级 `stop`（让 TEARDOWN 走完）→ 重启 → `queue/play` 恢复；
  否则旧进程被 SIGTERM 时不发 TEARDOWN，会把设备打进僵死（本监控台的 `L5_SESSION_DEAD` 就是抓这个）。
- **重启后**：务必确认 `latest.txt` 回 `HEALTHY` 且 `timing_in` 恢复 4~6，再离开现场。
- **判定器改逻辑**：先跑 `--selftest`，**14 条全 PASS** 才允许上线（否则等于把判据废掉还不知道）。**每新增一条判据，必须同时新增一条「接管期/启动期」反例**——2026-10-29 21:01 就是漏了这个反例，把容器重启接管期误报成僵死。
