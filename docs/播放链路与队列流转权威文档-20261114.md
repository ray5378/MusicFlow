## 0. 阅读顺序与口径

### 0.1 一句话模型

**队列只存在于服务端（主进程）的 `QueueController` 里；所有链路都只是「把队列当前项变成声音」的执行器。** 直连设备（DLNA / AirPlay solo）由设备自己拉流或收 RTP；sendspin / AirPlay 桥由一个服务端泵（`GroupPump`）把 PCM 推给设备/桥。客户端（Flutter / Web）的本机播放是唯一例外：**音频与进度权威在客户端，服务端只镜像队列**（`services/peer.ts:765-779`）。

### 0.2 三个必须区分的「队列」

| 名字 | 存在位置 | 谁写 | 用途 |
|---|---|---|---|
| 权威队列 | 主进程 `QueueController.queues: Map<bareId, QueueData>`（`services/player/QueueController.ts:168`） | 所有 cast 链路 + 本机队列的 peer 层 | 决定下一首、切歌、状态出口 |
| 持久化队列 | `device_queues` / `group_queues` / `local_queues`（`db/schema.ts:392/407/448`） | `persist()`（队列）/ `PeerManager.local*`（本机） | 重启恢复、流转搬运 |
| 客户端镜像 | Flutter/Web 内存 + 本地会话文件 | 客户端自己（服务端只广播） | UI 显示、本机播放 |

### 0.3 写法约定

- 「设备」= DLNA renderer / AirPlay 设备 / sendspin client；「泵」= `GroupPump`；「组」= 用户组（`player_groups`）。
- `bareId` = 去掉 `dlna:` / `group:` / `airplay:` / `sendspin:` 前缀后的 id。`stripPlayerPrefix()` 定义在 `services/player/QueueController.ts:39`。
- 关键结论后均括注 `文件:行号`；同一事实只在一处展开，其它章节用「见 §x」。

## 1. 总览：三条时间轴

### 1.1 三条时间轴

| 时间轴 | 定义 | 主要载体 | 谁在读它 |
|---|---|---|---|
| **内容时间轴** | 「这首/这段内容自己的第几秒」，从 0 到 duration | 单曲：队列项 `duration`；flow：`FlowSession.itemStartSec()`（`services/audio/flow.ts:760`）；sendspin：`GroupPump.playCursorMs`（`services/sendspin/streamEngine.ts:503`） | 切歌判定、进度条、seek 目标 |
| **输出流时间轴** | 「服务端已经产出/写出的音频秒数」 | flow：`session.streamSec() = emittedFrames / sampleRate`（`flow.ts:760`）；sendspin：`cursorUs` 时间线游标 + `timelineBaseUs`（`streamEngine.ts:1102-1130`）；DLNA 单曲：ffmpeg 已写字节，无绝对秒 | flow 的可听时钟下界、sendspin 帧时间戳 |
| **设备可听时间轴** | 「扬声器此刻真正在放的第几秒」 | DLNA `GetPositionInfo.RelTime`；sendspin `audiblePositionMs = pushedMs − 缓冲深度`（`streamEngine.ts:1076-1081`）；flow `createAudibleClock` 对 RelTime 做增量积分（`flow.ts:209-228`） | 显示、flow 队列推进 |

### 1.2 谁是权威

| 问题 | 权威 | 代码 |
|---|---|---|
| 队列下一首是谁 | `QueueController.pickNext()`，洗牌序列由服务端持有 | `QueueController.ts:1153`、`1171-1242` |
| 这首是否播完 | 单曲设备：`PlaybackTracker`（PLAYING→IDLE 等迁移）；flow：出流侧 `flowAdvance`；sendspin/桥：泵内容结束后 tracker 判 IDLE | `services/player/PlaybackTracker.ts:182/282`；`QueueController.ts:693-1030`；`routes/rest/index.ts:2037-2047` |
| 显示上的「当前曲」 | `displayHold` 持有期间强制显示旧曲 | `QueueController.ts:2034-2116` |
| 进度条数值 | 每个链路自己的状态出口（`/status`） | `routes/api/peers.ts:1133-1270` |
| 本机客户端播放状态 | **客户端上报**（`/local-status`，TTL 30s） | `services/peer.ts:778-817` |

> **硬口径**：`queueClock`（`QueueController.ts:256`）**只**用于曲末预热，明确「绝不参与切歌/结束判定」；显示外推由 `displayHold` 单独负责。不要在排障时把三者混为一谈。

## 2. 队列权威与数据模型

### 2.1 QueueController 的单例与 key 规范

- `QueueController` 是进程内单例（`services/player/QueueController.ts:167`），所有设备的队列都在 `queues` Map 里，**key 恒为裸 id**（`stripPlayerPrefix`，`:39`；调用入口 `:476/698/1790`）。
- `PlayerController` / `PlaybackTracker` 的 key 则是**带前缀**的 `playerId`（`dlna:<id>` / `group:<gid>` / `airplay:<id>` / `sendspin:<clientId>`），由各 `ProtocolPlayer.playerId` 给出（`services/player/types.ts:86-128`）。
- 组激活期间，成员设备的个人队列决策被忽略：`isMemberOfActiveGroup()` 在 `handleDecision` 最前面 `return`（`QueueController.ts:699-701`、`1037-1043`）。

### 2.2 `QueueData` 字段语义

定义在 `QueueController.ts:78-100`（纯内存，不直接持久化）。

| 字段 | 类型 | 语义 | 写入点 |
|---|---|---|---|
| `items` | `QueueItem[]` | 队列实体；`QueueItem` 至少含 `songId/title/mime`，其余展示字段可缺省，`resolveItem()` 起播前补齐 | `setQueue:1800`、`playFrom`、`enqueue:2159`、`removeAt:2186`、`reorder:2212` |
| `currentIndex` | number | 当前曲下标；`-1` = 无 | 起播/切歌/flowAdvance/跳播 |
| `playMode` | `"order"\|"one"\|"all"\|"shuffle"` | 播放模式（定义 `services/player/types.ts:62`） | `setPlayMode:1917` |
| `isActive` | boolean | 队列是否处于「在播/可续播」；`false` 时 stalled/frozen 自愈一律不动 | `setQueue:1803`、`stopPlayback:2249`、熔断 `:998` |
| `ended` | boolean | 队列自然播完（`markEnded:1054`）；DB 不存，重启恒 `false` | `markEnded`、advance 时清 `false` |
| `contentContext` | string? | 「队列来自哪个内容」，如 `playlist:<id>`；**不持久化**，重启即失效 | `setQueue:1799`；`getContentContext:1815` |
| `shuffleOrder` | number[]? | 服务端权威洗牌序列（一轮不重复的下标数组） | `rebuildShuffle:1171`、`ensureShuffleReady:1192` |
| `shufflePos` | number? | 当前曲在 `shuffleOrder` 中的位置，`-1` = 未就绪 | 同上 |
| `shuffleLen` | number? | 序列长度（重建判定用，不对外） | 同上 |

### 2.3 `QueueSnapshot` 字段语义（对外）

定义 `services/player/types.ts:132-199`；构造 `QueueController.snapshot():2009-2029`；HTTP 出口 `GET /v1/peers/:id/queue`（`routes/api/peers.ts:216-257`）；WS 出口 `queue_changed` / `peer_queue_changed`（`services/ws/index.ts:254-257`、`:277`）。

| 字段 | 语义 / 消费者注意事项 | 代码 |
|---|---|---|
| `items` | 队列项；`/queue` 支持 `offset/size` 分页，`total` 另给；WS 超过 200 首只发 `items: []` + `total` | `types.ts:133`；`ws/index.ts:206-212` |
| `currentIndex` | 显示用当前下标；**持有期间是旧曲下标** | `QC:2017` |
| `playMode` | 缺省 `"shuffle"`（历史默认），不是 order | `QC:2018` |
| `isActive` | 队列是否在播/可续播 | `QC:2019` |
| `ended` | 队列是否自然播完 | `QC:2020` |
| `updatedAt` | 队列最近变动 ms 时间戳；**仅本机快照有**（来自 `local_queues.updated_at`），cast 端缺省 | `types.ts:138-145`；`peer.ts:742` |
| `revision` | 单调递增版本号；客户端每 2s 轮询 `/status` 比对后才拉 `/queue` | `types.ts:146-157`；`QC:2005-2006` |
| `startPosition` | 一次性起始位置（秒），**仅随首次广播带出**，随后删除 | `types.ts:158-166`；`peer.ts:904-914` |
| `shuffleOrder` / `shufflePos` / `shuffleEpoch` | 服务端权威洗牌序列、位置、版本号；客户端**不得自行生成** | `types.ts:167-185` |
| `preProbe` | `PreProbeScheduler.status()`：`exhausted` 等；仅 Web 端消费 | `types.ts:186-199`；`QC:2027` |

> **注意 revision 的时序**：`revision` 在 `queue_changed` 事件监听器里自增（`QC:269-272`），而事件携带的快照是 **emit 之前**构造的，因此**事件里的 revision 是变更前值**（`:265-268`）。客户端以 `/status` 的读数为准，不会漏拍。

### 2.4 三张持久化表

| 表 | 主键 | 列 | 写入者 | 读取者 |
|---|---|---|---|---|
| `device_queues` | `device_id` | `items_json`, `current_index`, `play_mode`, `is_active`, `updated_at`（`db/schema.ts:392-399`） | `QC.persist():2510-2526` | `QC.loadFromDb():2457-2469` |
| `group_queues` | `group_id` | 同上（`schema.ts:448-455`） | `QC.persist():2490-2508` | `QC.loadFromDb():2470-2482` |
| `local_queues` | `peer_id` | 额外 `user_id`、`last_active_at`（`schema.ts:407-416`） | `PeerManager.localPlayFrom:879-900`、`localEnqueue:918`、`localSetIndex:1030`、`localClear:997` 等 | `PeerManager.getQueueSnapshot:735`、`localPeekSource:843` |

- `persist()` 以 `getGroupManager().get(playerId)` 是否为组来选表（`QC:2489`）；**不写 `local_queues`**（本机队列由 `peer.ts` 单独维护）。
- `ended` / `contentContext` / 洗牌序列**都不持久化**（`QC:2454-2455`、`types.ts:95-96`）。
- 本机队列还会被 `PeerManager.runCleanup()`（`:1054`）按 `QUEUE_TTL_MS = 6h`（`:125`）静默回收；启动 20s 后有一次全量清扫（`:127`、`sweepStaleQueues:1074`）。

### 2.5 `revision` 自增与 `persist` 时机

**revision**

- 唯一自增点：`this.on("queue_changed", ...)`（`QC:269-272`），即**任何对外可见的队列变更**（换歌/增删/排序/播放模式/预探测）都会 +1。
- `queueRevision(playerId)` 读当前值（`QC:2005`），用于各 `/status` 出口的 `queueRevision` 字段（`peers.ts:1167/1194/1218/1241/1259`）。

**persist（写 DB）时机（现状，逐点）**

| 场景 | 代码 |
|---|---|
| 整队替换 `setQueue` | `QC:1807` |
| 自动/手动切歌成功后 | `QC:842` |
| 冻结第 2 次放行切歌 | `QC:910` |
| 连续卡死放行切歌 | `QC:1012` |
| 跨曲熔断停止 | `QC:1000` |
| 起播时因无源跳过若干首 | `QC:1593` |
| flow 跨曲边界 `flowAdvance` | `QC:2152` |
| 清空/停投/失活 | `QC:1972-2004`、`2230-2268` |
| 睡眠定时器到点 | `QC:2294-2317` |

> `persist` 是**同步 SQLite upsert**（`better-sqlite3` 风格 `.run()`），不做防抖；因此可以在切歌路径上直接调用。

### 2.6 洗牌权威（服务端唯一）

- 起播分界线：`startIndex` 为 `null`/未给/负数/`0` ⇒ 视为「整列表播放」，shuffle 下**服务端随机挑首**；正整数/断点恢复 ⇒ 必须尊重调用方（`playFrom` 大段注释 `QC:1819-1842`；实现 `:1890` 附近）。
- 之后自动续播一律走 `shuffleOrder`：`pickNext→shuffleNextIndex→ensureShuffleReady/rebuildShuffle`（`QC:1153-1242`）。
- 客户端只镜像（`types.ts:167-185`），**不得自行洗牌**；纯离线队列例外由客户端本地洗。

### 2.7 `playMode` 下 `pickNext` 的语义

| 模式 | `pickNext` 行为 | 依据 |
|---|---|---|
| `order` | 下标 +1；末尾返回 `-1` | `QC:1153-1170` |
| `one` | 恒返回当前 index；被判死连续 2 次时由 `repeatOneGuard` 改下一首 | `QC:1082-1100`、`794-805` |
| `all` | 末尾回卷到 0 | `QC:1153-1170` |
| `shuffle` | 沿 `shuffleOrder` 走；序列耗尽重建 | `QC:1213-1242` |

`peekNext()`（`:1137`）是**只读**版本，供下一首预取/提示使用；起播路径严禁用 `pickNext` 取「下一首是谁」，否则会推进 `shufflePos`（`:1641-1650` 注释）。

## 3. 逐链路章节

> 每章统一模板：**入口 → 起播序列 → 出流/推流 → 进度与切歌判定 → seek → 暂停/停止/恢复 → 失败与自愈 → 观测点/日志关键字 → 已知约束**。

### 3.1 DLNA 单曲管道

#### 入口

| 项 | 值 |
|---|---|
| 设备拉流 | `GET /rest/dlna/stream/:token`（`routes/rest/index.ts:2799`） |
| token 来源 | `createCastSession(songId, deviceId, baseUrl)`（`services/dlna/control.ts:629`），`castToDevice` 时铸造（`:851`） |
| 通用 HTTP 流 | `GET /rest/stream?id=&token=`（`routes/rest/index.ts:2469`） |
| 起播调用 | `castToDevice()`（`control.ts:835`），由 `createDlnaProtocolPlayer().playMedia()` 进入 |

#### 起播序列（`castToDevice`）

1. 禁用设备/未知设备直接拒绝（`control.ts:836-839`）。
2. **双协议互斥**：先停同 host 的 AirPlay 会话（`control.ts:840-850`）。
3. 建 cast session，把 `timeOffset` 编进流 URL（`:851-857`）——seek/流转的起点是**新流**，不是「先播再 Seek」。
4. 构造 DIDL-Lite（`buildDidlLite`，`:179-198`、`:859`）。
5. `Stop`（容错）→ `SetAVTransportURI` → `waitForCanPlay(10s)` → `Play`（`:867-896`）。
6. 写 `currentMedia`（`:899-909`）、`media_changed` / `player_refresh`（`:909-911`）、位置基线（`:912-939`）、事件缓存 `PLAYING`（`:951-955`）、GENA 订阅（`:958`）。
7. 返回 `mediaUri = streamUrl`（`:960`）。

#### 出流（`servePipelinedSong` + `serveFfmpegPipe`）

- `servePipelinedSong`（`routes/rest/index.ts:1833-1862`）解析通道编码（`resolveChannelCodec`）与输入（`resolvePipelineInput`），用 `buildPipelineCommand({timeOffsetSec})` 生成 `-ss`（`:1843-1850`），再走 `serveFfmpegPipe`（`:1851-1861`）。
- 实时管道：无 Range 语义，一律全流 200；seek 由客户端改带 `timeOffset` 重新拉流（`:2475-2477`、`:2494-2514`）。
- 缓冲策略：网络源默认**整曲内存缓冲**（`resolveTranscodeInput({buffering:timeOffset===0})`，`:2520`；`membuf` 逻辑 `:2235` 起）；大文件直通只对 DLNA 开放（`serveCastStream:2711/2733`）。
- DLNA 兼容头：`contentFeatures.dlna.org` + 12h 假 `Content-Length` + 按请求给 ICY（`serveCastStream:2749-2758`）。

#### 进度与切歌判定

- 设备侧 `GetPositionInfo.RelTime` 由 `getDeviceStatus` 读取；无 RelTime（MUZO/HiVi 恒 0）时按**起播锚点 + 墙钟外推**（`control.ts:912-939`）。
- 服务端状态 → `QueueController` 的 `PlayerController.reportState` → `PlaybackTracker`；`advance/track_changed/idle_early` 统一进 `handleDecision`（`QC:693`）。
- 自然播完：`advance` → `pickNext` → `playCurrent(..., "auto-advance")`（`QC:784-849`）。

#### seek

- `seekDevice()`（`control.ts:1244`）：若该设备被标记「SOAP Seek 不可靠」，直接 `reseekByRecast()`（`:1251-1258`）——settle 400ms、串行化、带 `timeOffset` 重投（`:1194-1242`）。
- 否则 SOAP `Seek(REL_TIME)`（`:1267-1268`），并同时做三件事：事件位置、外推基线改锚、落位保护窗（`:1270-1283`），随后异步 `verifySeekLanding`（`:1288`）。
- `/v1/peers/:id/seek` 在进入前先 `markSeekIssued`（`peers.ts:971`），保证 8s 冷静期内 IDLE 不被判成结束（`services/player/seekSettle.ts:31/48/58`）。

#### 暂停/停止/恢复

- `pauseDevice` / `stopDevice`（`control.ts:1124/1141`）；`playDevice`（`:1107`）。
- 播放端路由：`/play`、`/pause`、`/stop`（`peers.ts:773-866`）；DLNA stop 是「先落队列停止态，再 best-effort 停传输」（`peers.ts:843-862`）。
- 恢复：`QueueController.resumeActive()` 重投当前首（`QC:677-690`），组看门狗 10s 周期触发（§5.7）。

#### 失败与自愈

- `idle_early` 复查：链路不可用/抛错 → `noteLinkLost`，暂不放行（`QC:729-771`）。
- `stalled`：同一首第 1 次重投，第 2 次放行切歌；跨曲连续 3 首 → 停队列（`QC:923-1028`、`STALL_SKIP_LIMIT:165`）。
- `frozen`：先复查位置是否推进；否则第 2 次放行切歌（`QC:855-921`）。
- cast 30s 硬顶 + 超时回收半开会话（`QC:1627-1638`、`abortTimedOutCast:1471-1480`）。

#### 观测点

`[cast] <dev>: BEGIN/Step 2/Step 4/END`（`control.ts:861/878/894/959`）；`[DLNA][seek]`（`:1215/1266/1283`）；`[QueueController][playCurrent]`（`QC:1495/1607`）；`[ws][state]`（`ws/index.ts:241`）。

#### 已知约束

- 双协议设备（HiVi/MUZO）音频输入互斥：DLNA 起播前必须停同 host AirPlay（`control.ts:840-850`）；反向由 AirPlay 侧 `yieldSiblingDlnaForAirPlay`（`services/airplay/control.ts:583-618`）冻结 DLNA 队列。
- 设备不报 RelTime ⇒ 进度靠外推；外推基线的 `songId` 必须同步记，否则换歌检测会删基线（`control.ts:935-939`）。
- 实时管道上 Range 无意义（`routes/rest/index.ts:2475`）。

### 3.2 DLNA flow 连续队列流

#### 入口

- 设备侧唯一入口仍是 `GET /rest/dlna/stream/:token`（`routes/rest/index.ts:2799`）；在 `serveCastStream` 内分流：
  - 条件：`kind==="dlna" && timeOffset===0 && deviceId` 且 `resolveFlowSettings().enabled && crossfade`（`:2765-2768`）。
  - 否则回退单曲管道 `servePipelinedSong`（`:2783-2789`）。
- `flow=1` 的 HTTP 入口在 `GET /rest/stream`（`:2533-2558`），需 `peerId` 且 `flow=1`，且 `prefetch!==1 && timeOffset===0`（`:2538`）；当前 Web 前端**不传** `flow=1`（`frontend/src/stores/player.ts:497-504`）。

#### 起播序列（`serveFlowQueue`）

1. 取队列快照 + 候选：`selectFlowCandidates(snapshot, songId)`——**只有 `playMode==="order"`**、从当前曲往后连续截断（`services/audio/flowSource.ts:77-89`）。
2. 候选 < 2 首 → 返回 `null` 回退（`routes/rest/index.ts:1933`）。
3. 每曲 af **一次算定**（`:1935-1940`），但**只同步解析首曲**，其余懒解析（`:1941-1959`）。
4. 首曲解析失败或解析出的 key 不是当前曲 → `null`（`:1969-1970`）。
5. 采样率/位深取播放器目标（`:1983-1994`），`startFlowSession(items, {...crossfade, fade, onItemStart, onItemEnd})`（`:1996-2017`）。

#### 出流/推流（`services/audio/flow.ts`）

- 会话锚定 48kHz/2ch（`flow.ts:44-47`），曲目解码强制 `-ar/-ac`（`:238-247`）；编码器缺省 mp3 320（`:73`）。
- **交叉淡入**：上一首尾段与下一首首段加权混合，混合块写完后 `markStart()` 记录本曲在**流内容时间轴**的起点（`flow.ts:601-603`）。
- `itemStartSec[index] = emittedFrames / sampleRate`（`:600-603`）；index 0 恒 0。
- **实时节流**：`dueMs = 已出流秒*1000 − 墙钟 − LEAD`，`LEAD=5s`，`FLOW_REALTIME_LEAD_SEC` 可覆盖、0 = 关闭（`:62-70`、`:474-478`）。
- 预取：距曲末「过渡窗口 + 2s」启动下一路解码（`:49`、`:687-710`）。
- 会话头：`X-MusicFlow-Flow: 1`、`X-MusicFlow-Transcoded: 1`（`routes/rest/index.ts:2074-2083`）。

#### 进度与切歌判定（flow 的权威在出流侧）

- `createAudibleClock(flowStartedAt, () => session.streamSec())` 对设备 RelTime 做**增量积分**：正常递增累加；归零/回退保留已积分值；领先已出流 >5s 的陈旧值丢弃（`flow.ts:209-228`）。
- 200ms 定时器：`sec = audibleClock.sec() ?? session.streamSec()`；`idx = pickItemIndexAtSec(itemStartSec, sec)`；`qm.flowAdvance(deviceId, startIndex + idx)`（`routes/rest/index.ts:2035-2048`）。
- `pickItemIndexAtSec` 规则：`start <= sec` 才算进入该首，**跨过边界的前一拍仍是上一首**（`flow.ts:179-188`）。
- `flowAdvance` 只改 `currentIndex` + `persist` + 广播，**不重投**（`QC:2145-2155`）。
- 同时，`handleDecision` 对 `flowOwned` 设备的 `advance/track_changed/idle_early` 一律吞掉；`ended` 不吞（`QC:705-712`）。

#### seek

- **flow 会话内没有 seek**：`timeOffset>0` 一律不走 flow（`routes/rest/index.ts:2763`），因为连续流没有「第 N 秒」的稳定语义。设备/客户端 seek 会让设备带 `timeOffset` 重新拉流 → 走单曲管道 → 旧 flow 会话被新会话中止（`:2050-2055`）。
- `flowOwned` 在会话结束时摘除（`:2057-2062`），否则该设备后续切歌决策会被永久吞掉。

#### 暂停/停止/恢复

- 暂停/停止是**设备传输层**动作（`pauseDevice/stopDevice`），flow 会话本身不感知；设备断开 → `killOnCancel` → `session.abort()`（`:2064-2070`）。
- 停止投屏时 `QueueController.deactivate/stopPlayback` 会 `flowOwned.delete`（`QC:2232/2252`），出流侧由 HTTP cancel/新会话接管。

#### 失败与自愈

- 单曲解码失败/空流：`onItemEnd(ok=false)` 只上报测量，不写队列（`routes/rest/index.ts:2007-2016`）；会话内 `stats.skipped++`（`flow.ts:712-714`）。
- 候选曲解析失败：懒解析返回 `null`，会话跳过它继续（`flow.ts:93-103`、`:690-696`）。
- 旧会话堆积：每设备只保留一个 `activeFlowAborts`，新会话先中止旧会话（`routes/rest/index.ts:1903-1910`、`2050-2055`）。

#### 观测点

`[flow] <songId> 首曲解析完成 → 起流（队列候选 N 首）`（`:1978`）；`X-MusicFlow-Flow` 响应头；`[stream] ... timeOffset=...`（`:2491`）；`[membuf] ... 跳过整曲缓冲`（`:2432`）。

#### 已知约束

1. **flow 会话内绝不允许变速**；输出采样率与每曲 DSP 锚定率必须同一个键算出（`routes/rest/index.ts:1984-1990`）。
2. **只支持 `order`**；`shuffle/one/all` 一律回退单曲（`flowSource.ts:83`）。
3. 至少 2 首候选，且首曲必须可解析（`:1933`、`:1970`）。
4. `timeOffset>0` 不走 flow（`:2763`）；`prefetch=1` 不走 flow（`:2538`）。
5. 队列推进按**可听边界**，不是编码边界；`onItemStart` 只负责 ICY 元数据（`:2002-2006`、`:2027-2034`）。
6. 实时节流默认允许领先墙钟 5s；关闭后设备贪婪读会把队列瞬间推后几分钟（`flow.ts:62-70`）。
7. 每曲 af 链**不含限幅器**，限幅必须在混合之后（`routes/rest/index.ts:1864-1870`）。
8. flow 开关的真实缺省：`FLOW_ENABLED` 缺省 `"1"`，但 `crossfade` 缺省 `disabled`，因此**实际默认不出 flow**（`flowSource.ts:51-63`）。`routes/rest/index.ts:2760` 注释写「缺省关」是结果描述，不是 `enabled` 的默认值。

### 3.3 sendspin 单设备泵

#### 入口

- 设备连接：`sendspin` WebSocket 服务（`services/sendspin/index.ts:272` 进程内 / `:394` 子进程模式；`isForkMode:74`）。
- 播放器实现：`createSendspinProtocolPlayer(clientId)`（`services/sendspin/protocolPlayer.ts:56`），进程内为 `createSendspinInprocPlayer`（`:252`），fork 模式为 `createSendspinProxyPlayer`（`:327`）。
- 队列 key：裸 `clientId`（`sendspin:<clientId>` 解析后）。

#### 起播序列

1. `playCore(srv, clientId, item, onPlayFailed, seekPositionMs?, bridge?, onUnplayable?, nextSongId?, preferRowId?)`（`services/sendspin/playerCore.ts:266`）。
2. 取/建**同名单设备组**：`srv.group(clientId)`（`:294`）——单设备也是一个「组」，只是成员只有一个。
3. **借流**：`borrowFor` + `handoverCore`（`:297-304`），同曲已在别的泵上播则整体接过来（§4.2）。
4. `pumpFor(srv, g)` → `pump.stop()`（`:305-306`）；起播 seek 先 `pump.armSeek()`（`:307-308`）。
5. 复位旧流：`g.close()`；能 keep_stream 则 `g.clearPlayback()`，否则 `g.finishPlayback({silentState:true})`（`:317-338`）。
6. 写 `g.positionMs / audibleStarted=false / g.current`（`:339-343`）。
7. `conn.group=g; g.add(conn)`，先 `sendGroupUpdate()`，`pendingAnnounces.push(conn)`（`:344-359`）——`stream/start` 延迟到**首块音频**（`:361-370`）。
8. 后台 `pump.play(item.songId, nextSongId, preferRowId)`（`:362`）。

#### 出流/推流（`GroupPump.pushLoop`）

- 帧长 `FRAME_MS=25ms`（`streamEngine.ts:230`），采样 48kHz/2ch（`services/sendspin/encoding.ts:31-32`）。
- 首帧 lead `FIRST_FRAME_LEAD_US=250ms`；seek 重锚 lead `SEEK_RESEED_LEAD_US=3s`（`:264/274`）。
- 时间戳按**实测样本数**推进，`timelineBaseUs` 首帧确立、seek 后重锚（`:1102-1130`、`:1208-1267`）。
- pacing 锚点对 `(paceAnchorMs, paceAnchorWall)`，`dueMs = anchorWall + (i*FRAME_MS − anchorMs)/speed`；seek 后必须同步重设 pacing 锚点（`:460-475`、`:1249-1261`）。
- 进度上报 = `audiblePositionMs(pushedMs, cursorUs, floorMs) = pushed − 缓冲深度`，下界 `floorMs` 是起播/seek 目标（`:1061-1081`）。
- 音频源：整曲 `pcm` 或流式 `PcmWindow`（`services/sendspin/streamSource.ts:134`），窗口高低水位与 `seekTo()` 重定位（`:46-50`、`:134-211`）。

#### 进度与切歌判定

- 泵自然结束：`contentEnded`（`stream-eof` 或 `decode-exhausted`，`streamEngine.ts:1199-1204`）→ 收尾 `stop()`（`:1929`）→ 设备侧状态停止 → `PlaybackTracker` 判 `advance` → `QueueController` 切歌。
- `S1` 下一首预取：曲末剩余 ≤5s 启动独立解码器，按**沿用当前组时间线**的连续 ts 写入 ring（`:184-201`、`:997-1055`）；预取只解决断粮，**不推进队列**。
- 显示与队列的错位由 `displayHold` 按住（§5.5）。

#### seek

- `seekCore(srv, clientId, seconds)`（`playerCore.ts:801`）：
  1. 钳制到本曲时长（`:809-812`）；
  2. `pump.seek(seconds, {clamp})` 发布位置（`:824`）；
  3. 起播窗口内只记 `pendingSeekMs`，由在飞的 `play()` 自纠，**不再起第二个 play**（`:830-840`）；
  4. 否则走完整起播路径重建流：`playCore(..., clampedMs, bridgeSpecs)`（`:841-865`）；
  5. 暂停中 seek 结束后恢复暂停（`:866-868`）。
- `GroupPump.seek()`（`streamEngine.ts:1966`）写 `positionMs`、`reportedFloorMs`、`timelineReseed++`、pacing 锚点；`armSeek()`（`:2001`）给起播窗口用。

#### 暂停/停止/恢复

- `pauseCore`（`playerCore.ts:759`）：`pump.pause()`，组状态 `paused`；暂停看门狗 `PAUSE_AUTO_STOP_MS=30s` 到点自动 stop（`:640`、`:714-740`）。
- `resumePumpCore`（`:775`）：清看门狗、`pump.resume()`。
- `stopCore(keepCurrent?)`（`:378`）：停泵 + `stream/end`；`keepCurrent=true` 保留曲目/位置（看门狗转 stop 语义）。

#### 失败与自愈

- `pushLoop` 判死：`stream-truncated`（提前 EOF）与 `decode-exhausted` 分开记（`streamEngine.ts:1094-1100`）；`onUnplayable` 回传主进程记负缓存（`playerCore.ts:278-282`）。
- 泵 `play()` 失败：`g.current=null`、`finishPlayback({silentState:true})`、`onPlayFailed`（`:361-370`）。
- QueueController 侧：cast 失败/stalled/frozen 走通用自愈（§5）。

#### 观测点

`[pump][play] song=... startMs=...` / `音源就绪`（`streamEngine.ts:702/741`）；`sendspin 流式窗口提前 EOF`（`:1200`）；`sendspin next-prefetch ...`（`:1025/1048/1054`）；`[Sendspin][seekCore]`（`playerCore.ts:813/836/854/868`）；`[Sendspin][handover]`（`:303`）。

#### 已知约束

- 单设备也走「组」模型；泵名由 `sendspinGroupName(clientId)` 生成（`playerCore.ts:57`）。
- 起播 `stream/start` 必须等首块音频，早了设备丢弃该流（`playerCore.ts:352-357`）。
- seek 只能整秒（HTTP 入口 `alignSeekSeconds`，`peers.ts:952-959`）；泵内 `alignFrameMs` 兜底（`streamEngine.ts:254`）。

### 3.4 sendspin 用户组组泵

#### 入口

- `sendspinGroupPlay(groupName, memberIds, item, ...)`（`services/sendspin/index.ts:766`）→ `playGroupCore(srv, groupName, memberIds, item, ...)`（`playerCore.ts:406`）。
- 用户组映射：`sendspinGroupName(userGroupId)`（`playerCore.ts:57`）与 `sendspinGroupNameForPeer(peerId)`（`:70`）。
- 组 player：`createSendspinGroupPlayer(userGroupId)`（`sendspin/protocolPlayer.ts:88`）。

#### 起播序列

1. `playGroupCore`：桥同步 `syncGroupBridges`（若有桥规格，`:431`）。
2. 借流判定与单设备同（`:432-441`）。
3. **接续判定**：`interrupted = pump.active`；`continuity = !interrupted && pump.continuityReady(item.songId, seekPositionMs)`（`:443-451`）——手动 next/prev/seek 打断时不接续。
4. `pump.stop()` → 可选 `armSeek`（`:452-453`）。
5. 接续：`g.close({keepBridgeDelivery:true})`，**不发任何边界消息**；否则 `g.close()` + `clearPlayback/finishPlayback`（`:455-477`）。
6. 写组状态 → 对**已是成员**的连接不重发 `stream/start`，只给新成员排队宣告（`:482-500`）。

#### 出流/推流

- 一个用户组 = 一个 `SendspinGroup` = 一个 `GroupPump` = **一条共享时间线**；所有成员收同一帧流（`sendspin/index.ts:766-803`）。
- 桥成员不进入 `members`，而是走 `bridgeSpecs` 并行集合（`playerCore.ts:295-296`、`:429-431`）；桥侧消费同一泵时间线。
- 混合组（直连 + 桥）的重锚：深锚只用于纯桥组；混合组走「首帧 ts 下移 sendAhead+lead」的回落链，避免直连成员听感跳变（`streamEngine.ts:1278-1300`）。锚点 lead 数值口径自 2026-11-02 起纯桥/混合统一（`:1302-1312`）。

#### 进度与切歌判定

- `pollCore` / `sendspinGroupPoll` 从组泵派生 `playing/paused/positionMs/durationMs/buffering`（`playerCore.ts:918`、`index.ts:929`）。
- 队列推进与单设备相同：泵内容结束 → tracker advance → QC 切歌；`S1` 只预取音频。
- 接续路径下，新曲首帧锚在上一曲自然播完的时间线尾（`continuityFromUs/lastContentEndUs`，`streamEngine.ts:948-995`），桥侧不换代、不清队列。

#### seek / 暂停 / 停止 / 恢复

- 组 seek：`seekCore` 走 `clientId.startsWith("ug:")` 分支 → `playGroupCore(..., memberIds, ..., clampedMs, bridgeSpecs)`，桥规格透传保持桥连接（`playerCore.ts:856-864`）。
- 组 stop：`stopGroupCore`（`:511`）→ 泵停 + `clearGroupBridges`（`:519`）。
- 组 pause/resume：`pauseCore/resumePumpCore`；暂停 30s 自动 stop（`:640`）。
- 组泵活性：`sendspinGroupPumpActive(groupName)`（`index.ts:952`），被 QueueController 用作 IDLE 误报的第二状态源（`QC:751-760`）。

#### 失败与自愈

- 成员离线：`playGroupCore` 只对在线 conn 起播，离线成员跳过（`:404`、`:488-500`）；重连由注册层/看门狗覆盖。
- 组泵停/重启后：`rejoinActiveGroups(clientId)` 重新入组（`index.ts:164`）。
- 泵判死回传与单设备相同。

#### 观测点

`[Sendspin][continuity] group=... interrupted=... continuity=... keepPrefetch=...`（`playerCore.ts:478-481`）；`[Sendspin][handover]`（`:303`）；`sendspin next-prefetch`（`streamEngine.ts:1025`）。

#### 已知约束

- 组内 sendspin 成员共用一个泵；**不存在逐成员独立时间线**（`sendspin/index.ts:766-803`）。
- `ug:` 前缀是内部组泵名的识别标志（`playerCore.ts:856`）。
- 组泵 seek 重建必须传 `bridgeSpecs`，否则桥被拆（`:858-864`）。

### 3.5 AirPlay 桥（默认路径）

#### 入口

- 总开关：`isAirplayBridgeEnabled()` = `MUSICFLOW_AIRPLAY_BRIDGE !== "0"`（`services/airplay/control.ts:278-280`）——**默认开启**。
- 播放器工厂：`createAirPlayPlayerForDevice()`（`airplay/protocolPlayer.ts:204-206`）。
- 单机桥：`createAirPlayBridgePlayer(deviceId)`（`:126`）；单机伪组 id `__bridge_solo:<deviceId>`（`soloBridgeGroupId:101`）。
- 组桥：由 `group/protocolPlayer.ts` 的 `prepareBridgeRoute()` 建（§3.7）。

#### 起播序列（单机）

1. 取上一条桥规格；`manual next/prev` 给已存在桥打 sticky 标记（`protocolPlayer.ts:138-142`）。
2. 选协议 `selectAirPlayBridgeProtocol()`（`control.ts:1083`）；同协议热复用 token（`protocolPlayer.ts:143-145`）。
3. `bridgePrepareDevice(deviceId, token, protocol, groupId=null, {initialVolume, settleDlna:!warm})`（`:148-151`；实现 `control.ts:311`）——冷建前对同 host DLNA 做 `yieldSiblingDlnaForAirPlay`（`:583-618`；调用点 `control.ts:353-361`）。
4. `soloBridgeRoutes.set(deviceId, spec)`（`protocolPlayer.ts:152-158`）。
5. `createSendspinGroupPlayer(__bridge_solo:<dev>)` → `playMedia(item, baseUrl, startMs, {sockets:[spec]}, opts)`（`:159-165`）——**音频完全来自 sendspin 单机伪组泵**。
6. 桥建立失败直接抛错（`:124-126`）：**不回落直连**。

#### 出流/推流

- PCM 由单机伪组泵产生（§3.3），桥子进程把 PCM 打成 RAOP RTP 发给设备（`services/airplay/bridgeSession.ts`；帧格式/锚点见 `airplay-权威方案文档.md` 第十部分）。
- `pollState()` 从泵派生，并把泵的 `BUFFERING` **归一为 PLAYING**（`protocolPlayer.ts:181-199`）——否则乐观窗口 5s 必超时。
- `/status` 的 AirPlay 分支：先取设备会话视图，再用 `getBridgePeerStatus()` 覆盖（`peers.ts:1197-1218`）；后者按「单机伪组泵 / 组泵」派生（`protocolPlayer.ts:219-279`）。

#### 进度与切歌判定

- 队列推进仍由 `QueueController` 的 tracker 对 `airplay:<id>` 判 `advance`；桥路径的 `positionMs` 来自泵（共享时间线）。
- 换歌/边界由泵的 `notifyBridgeGeneration(gen, kind, handoff, continuity)` 驱动（`streamEngine.ts:1233-1244`）；桥侧据此决定是否换代/清队列/发 BOUNDARY。

#### seek

- `playMedia` 的 `startMs>0` 直接传给 `castToAirPlayDevice({seekSec})`（`protocolPlayer.ts:41-57`）——**起播即落位**，不做「先起播再 seek」。
- `seek(seconds)` → `seekAirPlay()`（`control.ts:1583`）→ `seekUnlocked()`（`:1589`）：默认走**完整重建**（`AIRPLAY_SEEK_INPLACE=1` 才原地 FLUSH），因为 HiVi 等设备原地 seek 后持续缺包（`:1590-1604`）。
- 桥路径的 seek 实际是 sendspin 组泵 seek + 桥跟随（`protocolPlayer.ts:177`）。

#### 暂停/停止/恢复

- 单机桥：`stop/pause/resume` 全部转给单机伪组 player（`protocolPlayer.ts:167-177`）；stop 再 `bridgeStopDevice(token, deviceId)` 并删路由（`:168-173`）。
- 组桥：传输 op 由组泵承担，`fanOut` 必须跳过 `isBridgeOwned(d)` 的成员（`group/protocolPlayer.ts:476-479`）。
- 桥会话 owner 与 native cast 互斥；`bridgeStopDevice` 清 owner（`control.ts:282-305`、`:445`）。

#### 失败与自愈

- 桥 prepare 失败：单机直接抛错（不回落）；组桥逐设备回落 `bridgeUnavailable`，**本曲不播**（`group/protocolPlayer.ts:539-545`、`:741-752`）。
- 桥会话孤儿：`startBridgeRouteReconciler` 60s 对账、孤儿宽限 55s（`group/protocolPlayer.ts:960-967`）；单机伪组路由必须并入事实源（`airplay/protocolPlayer.ts:108-115`）。
- 暂停 30s 自动 stop 仍由 sendspin 泵执行。

#### 观测点

`[bridge-solo] <dev> 起播 protocol=... warm=... start=...s`（`protocolPlayer.ts:164`）；`[bridge-prepare] 同 host DLNA settle 完成`（`control.ts:360`）；`[bridge-prepare] skip device=... 负缓存命中`（`group/protocolPlayer.ts:572`）；`[group][bridge]`（`:707/749`）；桥 `stats`（见 `airplay-权威方案文档.md` §10）。

#### 已知约束

- 桥路径下 AirPlay 设备**没有 solo 会话**，`getAirPlayStatus` 恒空/IDLE，状态必须从泵派生（`protocolPlayer.ts:208-218`、`peers.ts:1202-1212`）。
- 桥成员在组内不得被 `fanOut` 传输 op（会与桥会话互踩）（`group/protocolPlayer.ts:476-479`）。
- 冷建桥会对同 host DLNA settle（冻结队列 → Stop → 等 STOPPED + 300ms），warm 复用不等（`control.ts:322-361`）。

### 3.6 AirPlay 直连（`MUSICFLOW_AIRPLAY_BRIDGE=0`）

#### 入口/起播

- `createAirPlayProtocolPlayer(deviceId)`（`airplay/protocolPlayer.ts:35`）。
- `playMedia`：`createAirPlaySession(songId, deviceId, baseUrl)` 拿 `streamUrl`（`:40`），`castToAirPlayDevice({..., seekSec: startMs/1000})`（`:45-57`）。

### 3.7 群组 player

#### 入口

- 组门面：`createGroupProtocolPlayer(groupId)`（`services/group/protocolPlayer.ts:468`），`playerId = group:<gid>`（`:469`）。
- 控制入口统一复用 peer API：`/v1/peers/group:<gid>/{play,pause,stop,seek,next,prev,...}`（`routes/api/peers.ts`）。

#### 路由决策（每首歌起播时）

1. `splitGroupMembers(groupId)` → `{dlna, airplay, spin}`（`group/protocolPlayer.ts:340`）。
2. 在线集合：DLNA `getOnlineMemberIds`（`:443`）、AP `getOnlineAirplayIds`（`:370`）、spin `getOnlineSendspinIds`（`:357`）。
3. 有在线 AirPlay 成员 → `prepareBridgeRoute(apOnline, reuseSpecs)`（`:546`）；否则 `bridgeRoute=null`（`:715`）。
4. 路由标签（现状）：`bridge`（`apOnline>0` 且桥开启）/ `legacy-cast`（无 AP 或桥禁用）（`:711-715`）。
5. 组泵：`spinOnline>0 || bridgeRoute` ⇒ 起 `createSendspinGroupPlayer(groupId)`，桥规格一起透传（`:728-738`）。
6. DLNA 成员：逐台 `createDlnaProtocolPlayer(d).playMedia(item, baseUrl)`（`:740`）。
7. AirPlay solo：**仅桥禁用时** `apSolo=apOnline` 逐台 cast（`:744-752`）。
8. `Promise.allSettled(jobs)`；全失败则回收桥路由并抛错（`:753-769`）。

#### 状态派生

- `pollState`：`getGroupLeader()` 取**固定成员顺序第一个在线成员**（`:418-435`）。
  - 无 leader（全员离线）→ 返回 `BUFFERING` 而不是 IDLE，防止 tracker 判 ended（`:814-822`）。
  - leader 是 sendspin → 从共享组泵派生（`:823-828`）。
  - leader 是 airplay：桥开启或 `isBridgeOwned` → 从组泵派生；否则从 solo 会话派生（`:829-843`、`885-948`）。
  - leader 是 DLNA → `getDeviceStatus`，组音量用 `GroupManager` 持久值（`:945-947`）。
- `getGroupStatus()`（`:885-948`）是 `/status`、流转源端读数（`routes/api/shared.ts:504`）的共同出处。

#### 组传输 op

- `stop`：`fanOut(stop)` → `spinOp(stop)` → `teardownBridgeRoute()`（`:778-784`）。
- `pause/resume`：`fanOut` + `spinOp`；resume 前 `ensureBridgeRouteOnResume()` 补建桥（`:785-794`）。
- `seek`：DLNA/AP 逐台扇出 + sendspin 组单发，两路结果分别打日志（`:795-807`）。
- `setVolume`：先落库，再扇出；桥占用成员例外仍扇出（纯控制链，不触 RTP）（`:808-813`、`:480-488`）。

#### 组看门狗

- 10s tick（`services/group/watchdog.ts:17`）；队列 `isActive` 且全员离线 → 记录位置并**悬挂**（队列保留在 DB，`isActive` 不变）（`:72-78`）；成员回归 → `resumeActive()`（`:94`），cast 后按最后位置 seek（`:96-102`）。

#### 已知约束

- 组 leader 只影响**状态派生**，不影响出流路由（出流按成员集合）。
- 组播放期间成员个人队列决策被忽略（`QC:699-701`）。

### 3.8 混合群组（DLNA + sendspin + AirPlay 共存）

现状行为（按代码）：

| 组合 | 实际行为 | 代码 |
|---|---|---|
| sendspin + AirPlay（桥开） | 一个组泵产生 PCM；sendspin 成员直接收 WS 帧，AirPlay 成员经桥收 RTP；**共享同一组时间线** | `group/protocolPlayer.ts:728-738`、`airplay/protocolPlayer.ts:126-165` |
| 只有 AirPlay（纯桥组） | 仍起组泵（桥的唯一 PCM 源），`members` 可为空 | `group/protocolPlayer.ts:725-739` |
| 有历史 DLNA 成员 | 入组新增被拒（`services/group/index.ts:420-422`）；**已存在的历史成员仍会被逐台 cast**（`group/protocolPlayer.ts:740`） | 同上 |
| DLNA + sendspin | 组泵推 sendspin；DLNA 单独拉流；两者**没有共享时间线**，进度/切歌各按自己链路 | `group/protocolPlayer.ts:740`；§3.1 |
| 桥禁用（rollback） | AirPlay 逐台 solo cast，DLNA 逐台 cast，sendspin 组泵；三条独立时间线 | `group/protocolPlayer.ts:744-752` |

**混合组的深锚限制**：组时间线全员共享；混合组（有直连 sendspin 成员）抬深锚会让直连 esp32 承受秒级时间戳跳变，因此深锚只用于纯桥组（`streamEngine.ts:1278-1300`）。自 2026-11-02 起**纯桥组与混合组统一锚点口径**，旧的 `mixed_anchor_lead_ms`（前端逐组覆盖）已从代码移除（`services/group/delayCalib.ts:18`、`streamEngine.ts:1302-1312`）；`player_groups.mixed_anchor_lead_ms` 列仅为兼容历史库保留（`db/schema.ts:441-442`），当前链路不读取。

> **与旧文档的矛盾**：`播放器链路调试与模拟播放器验收手册.md` §2.6 写「DLNA 成员在组里永远静默」。代码现状是**历史 DLNA 成员仍会被 `playMedia` 逐台投递**（`group/protocolPlayer.ts:740`），只是**没有共享时间线、无法同步**；新成员被服务端拒绝（`group/index.ts:420`）。该句「永远静默」已过时，按本文与代码为准。

### 3.9 客户端（Flutter local peer）

#### 入口/身份

- 客户端注册：`POST /rest/api/v1/peers/register`（`lib/providers/cast/cast_peer_provider.dart:291`），30s 心跳（`cast_peer_session.dart:33-57`）。

#### 起播序列（服务端视角）

1. `POST /v1/peers/local:<...>/queue/play` 或 `/v1/play` 或 `/queue/transfer-from`。
2. 服务端只写 `local_queues`：`PeerManager.localPlayFrom()`（`peer.ts:875-915`）——整队替换、`currentIndex`、`playMode="order"`、`isActive`。
3. 若带起点：`pendingStartPosition.set(peerId, startPosition)` → 取快照（快照带 `startPosition`）→ `emit("peer_queue_changed")` → **立即删除**（`:904-914`）。这就是 `QueueSnapshot.startPosition` 的「一次性」来源（`types.ts:158-166`）。
4. `scheduleLocalPreProbe` / `prefetchUpcoming` 后台跑（`:901-903`）。

#### 出流/播放（客户端侧）

- 音频完全在客户端：`just_audio`/`media_kit` 拉服务端 `/rest/stream?id=&token=`（URL 构造 `lib/data/sources/subsonic_api_client.dart:298-330`；起播 `lib/providers/player/player_provider.dart:1431`/`:1645`；seek 重拉 `transcoded_stream_seek.dart:182-204`）。
- 服务端**不能**替客户端 seek；只能靠 `startPosition` 在起播时落位（`routes/api/play.ts:92-99`、`peers.ts:523-529`）。
- 客户端跟随服务端队列：`peer_remote_control_provider.dart:169-380`（`startPosition` 一次性、`_adoptRemoteQueue`）。

#### 进度/切歌

- 客户端每 4s 上报 `POST /v1/peers/:id/local-status`（`cast_peer_session.dart:107`），字段 `state/position/duration/volume/songId`（`peer.ts:782-809`）。
- 服务端只存内存 + 30s TTL（`peer.ts:778-817`）；`/status` 把队列快照与本机上报合并（`peers.ts:1249-1270`）。
- 客户端本机队列的下一首由客户端自己推进，并回写 `currentIndex`（`localSetIndex`，`peer.ts:1030`）；服务端不主动 advance 本机队列。

#### 洗牌

- 服务端惰性物化 `shuffleOrder/shufflePos/shuffleEpoch`（`peer.ts:683-711`、`:744-752`），客户端只镜像（`types.ts:167-185`）。

#### 失败与自愈

- 心跳停止 → `markLocalOffline`（`peer.ts:304-314`）；`QUEUE_TTL_MS=6h` 后队列回收（`:125`）。
- WS 指令 `delivered=false`（客户端离线/Web 端）时接口仍返回 success，但实际无人执行（`shared.ts:580-585`、`peers.ts:979-985`）。

#### 已知约束

- 服务端没有本机音频会话；`position` 不可信到毫秒，只用于 UI 镜像（`peer.ts:765-776`）。
- `startPosition` 只随**当次广播**；后续轮询不会重复给（`:904-914`）。
- Web 平台 local peer 不再被控（`shared.ts:580-585`）。

### 3.10 Web 端（浏览器 local peer）

#### 入口/身份

- 规范 peerId：`local:<userId>`（`frontend/src/stores/player.ts:291`）；服务端为每个实例分配 `local:<userId>:<instanceKey>`，前端内部换算回 `local:<uid>`（`:2039-2055`）。
- 队列持久化：`local_queues`（`peerId` 为完整实例 id）。

#### 播放源

- `new Howl({ src: "/rest/stream?id=<songId>&token=<token>" })`（`stores/player.ts:604-616`），远程未入库歌走 `/rest/stream-remote`（`:200`、`:497-504`）。
- **Web 不传 `flow=1`**：前端源码中无 `flow=` 用法；服务端也说明「HTTP 客户端自己推进下一首，服务端替它拼流会让两边各推进一次」（`routes/rest/index.ts:2533-2536`）。
- 因此 Web 的每次播放都是一条**单曲管道流**；`timeOffset` 重新拉流实现 seek（`stores/player.ts:243`、`utils/transcodedSeek.ts:4-8`）。

#### 控制面与队列

- Web 自己维护 `local_queues` 镜像：播放/暂停/切歌后 `POST /queue/play`、`/queue/index`、`/play-mode` 等（`stores/player.ts:554` 起）。
- 播放器页可遥控其它 peer：轮询 `/status`（带 `queueRevision`，只在变化时拉 `/queue`）。
- Web 端**不再作为被控端**：`/v1/play` 对 Web local peer 直接 403（`routes/api/play.ts:42-48`）；`peer_command` 对 web 直返 `delivered:false`（`shared.ts:580-585`）。

#### 进度与切歌

- 进度权威在 Howl（浏览器）；Web 周期 `local-status` 上报（同 §3.9）。
- 队列的 `currentIndex` 由 Web 自己推进后写服务端；服务端不会替 Web 切歌。

#### 已知约束

- 服务端 `flow=1` 能力存在但 Web 未使用（`routes/rest/index.ts:2533-2558`）；启用会让服务端与 Web 各自推进队列（同一注释明确禁止）。
- 实时管道流无 Range，seek 只能 `timeOffset` 重拉（`:2475-2477`）。

### 4.2 播放器之间流转（transfer）

#### 入口

| 入口 | 语义 | 代码 |
|---|---|---|
| `POST /v1/peers/:to/queue/transfer-from` | 服务端从**另一个 peer** 搬队列并同位置起播（body 只收 `from`、可选 `position`） | `routes/api/peers.ts:340-542` |
| `POST /v1/peers/:to/queue/play` | 客户端把**整队**交给目标端；可选 `position` | `peers.ts:263-295` |
| `POST /v1/play` | 按内容（type/id）+ `songId/startIndex/position` 起播 | `routes/api/play.ts:24-132` |

#### `transfer-from` 的现状时序（逐条）

1. 解析 `from`（body 里的 peerId 必须走 `resolveBodyPeerId`，否则掩码会被当成真键）（`peers.ts:351-354`）。
2. 源端必须真实存在：local 看 PeerManager；cast 端看 QueueController 快照（`:356-377`）。
3. **sendspin 源的队列键映射**：若源是 `sendspin:<bare>` 且它是某个用户组成员，队列实际挂在 `group:<gid>` 下（`:361-373`）。
4. 源端空队列 → `{success:true, transferred:0}`（`:380-382`）。
5. **起点定格（早读）**：`srcPosEarly = askPosition ?? readPeerPositionSeconds(from)`（`:399`）。必须在任何起播动作前读，因为目标端起播的双协议互斥会停掉源端（`:391-398`）。
6. **索引校正**：优先用源端**实报当前曲** `readPeerCurrentSongId()` 在 `items` 中定位；镜像 `src.currentIndex` 只兜底（`:400-408`）。
7. 目标是 cast 端：
   - 冷启动预热落点歌可播性（`:419-426`）；
   - 源端此前被自动摘组的，回流到同一组（`:427-448`）；
   - `detachFromActiveGroups(parsedTo)`（`:449-450`）；
   - **sendspin→sendspin 借流**：`tryArmSendspinBorrow`，成功则整泵移交，不重启 ffmpeg/不 seek（`:451-454`、`routes/api/shared.ts:639-676`）；落点确认用 `borrowLandingConfirmed`（`shared.ts:676`）；
   - 起点注入本次 cast：AirPlay 用 `askPosition/早读`，同设备 DLNA 用早读，**跨设备 DLNA 例外**（先起播再 seek）（`:456-467`）；
   - AirPlay + 带起点：整曲预取与建会话并行（fire-and-forget）（`:468-490`）；
   - `playFrom(..., startPositionMs)` 起播（`:491-496`）；
   - 落点归属：借流成功用借流位置；本次 cast 落位用 `inCastPos`；否则晚读优先、早读兜底，再 `seekPeerToSeconds`（`:497-522`）。
8. 目标是 local：起点随 `localPlayFrom(..., at)` 一次性交出去（`:523-529`）。
9. **播放模式随队列流转**（`:531-539`）。
10. 返回 `{success, transferred, startIndex, position}`（`:541`）。
11. **源端停止不在这里做**：由客户端成功后另调 `/stop`（`:306-309`）。

#### 三种「位置载体」的分工

| 载体 | 作用域 | 生命周期 | 代码 |
|---|---|---|---|
| `startPosition` | local 目标起播 | 随一次 `peer_queue_changed` 下发后删除 | `peer.ts:904-914`、`types.ts:158-166` |
| `playFrom(..., startPositionMs)` | cast 目标起播 | 只对本次 cast 有效 | `QC:1843-1889`、`1625-1640` |

#### 同设备双协议流转

- AirPlay → DLNA：`castToDevice` 先停同 host AirPlay（`control.ts:840-850`）；因此落点必须早读（`peers.ts:391-398`）。

### 5.2 `stalled` / `frozen` / `linkLost`

| 情形 | 判定 | 处理 | 代码 |
|---|---|---|---|
| 链路不可用（RPC 超时/子进程僵死） | `state.unavailable` 或 poll 抛错 | `noteLinkLost`：**不切歌、不计数、不重投**，等恢复续播 | `QC:629-641`、`:731-737`、`:949-953` |
| 链路恢复 | 下一轮轮询/看门狗 | `resumeAfterLinkRecovery` → `recoverInPlace(lastPos)` | `QC:642-674`、`:1434-1462` |
| `stalled` 第 1 次 | 同一首 count=1 | 重投当前首 `playCurrent("stall-reinvest")` | `QC:1022-1027` |
| `stalled` 第 2 次 | 同一首 count≥2 | 放行切歌 `stall-skip` | `QC:983-1019` |
| 跨曲连续卡死 ≥3 首 | `STALL_SKIP_LIMIT=3` | `isActive=false, ended=true` + 停设备，停止推进 | `QC:165`、`:991-1004` |
| `frozen` 第 1 次 | 位置未推进 | `recoverInPlace(lastPos)` | `QC:919-921` |
| `frozen` 第 2 次 | 同一首 count≥2 | 放行切歌 `stall-frozen` | `QC:900-917` |
| `idle_early` | 进度未到时长 | 先复查；PLAYING/泵在推 → 撤销；确认停 → 放行 | `QC:714-783` |
| cast 失败 | `playMedia` 抛错/超时 | `castFailStreak++`；上限 `2×曲数` → 停队列 | `QC:1712-1722` |
| cast 30s 超时 | `withTimeout` | 回收设备会话 + 抛错 | `QC:1627-1638`、`:1471-1480` |

### 5.5 可听显示延迟（`DisplayHold`）

- 触发：`decision==="advance"` 且 `nextIdx !== currentIndex`，用最后一次 PLAYING 采样外推旧曲还可听 `remain`；`remain>1s` 才设持有（`QC:810-831`）。
- `until = now + remain`；`releaseAt = until + 5000ms` 硬顶（`QC:2044-2058`）。
- 释放：设备新曲 `position>0 && position<posAtSet`（`QC:2069-2076`）或硬顶定时器。
- 出口：`snapshot`、`/queue` 的 `currentMedia`、`/status`（所有 kind）、WS `player_state_changed/media_changed` 全部按旧曲（`QC:2009-2029`、`peers.ts:247-251/1158-1164/1187-1193/1215-1217/1230-1245`、`ws/index.ts:230-249`）。
- 用户主动操作（play/pause/stop/seek/next/prev/清队列）立即清除（`QC:479-480`）。

### 5.7 组看门狗（悬挂/恢复）

- 10s tick（`services/group/watchdog.ts:17`、`:27-31`）。

## 8. 已知约束与坑

> 每条都给出代码出处/注释原因；`旧文档已过时` 单独标注。

1. **flow 会话内不可变速**：输出采样率与每曲 DSP 锚定率必须同一个键；中途改率 = 爆音/失步（`routes/rest/index.ts:1984-1990`）。
2. **flow 只支持 `order`**：`shuffle/one/all` 的下一首不是「下标+1」，会话内推进必然与设备顺序不一致（`services/audio/flowSource.ts:68-83`）。
3. **flow 至少 2 首，且首曲必须解析成功**（`routes/rest/index.ts:1933/1969-1970`）。
4. **flow 不支持 `timeOffset>0`**：连续流没有「第 N 秒」的稳定语义，seek 一律回退单曲管道（`routes/rest/index.ts:2763`）。
5. **flow 的队列推进按可听边界，不按编码边界**：`onItemStart` 只写 ICY；`flowAdvance` 由 200ms 可听时钟驱动（`routes/rest/index.ts:2027-2048`）。
6. **flowOwned 吞 `advance/track_changed/idle_early`，不吞 `ended`**：否则重投会打断流；但流自然结束仍要 `markEnded`（`QC:705-712`）。
7. **同一设备只保留一个 flow 会话**：新会话先 abort 旧会话，否则旧会话占满 flow 槽（`routes/rest/index.ts:1903-1910`）。
8. **flow 实时节流默认 5s**：关闭后设备贪婪读会把队列推到几分钟后（`services/audio/flow.ts:62-70`、`:474-478`）。
9. **MUZO/HiVi `RelTime=0`/`TrackDuration=0`**：进度只能按起播锚点 + 墙钟外推；锚点必须带 `timeOffset`，且必须同步记 `songId`（`services/dlna/control.ts:912-939`）。
10. **DLNA SOAP Seek 在实时管道上不可靠**：一旦 `verifySeekLanding` 证实无效，后续 seek 直接 `reseekByRecast`（`control.ts:1244-1258`）；重投带 settle 400ms 串行化（`:1198-1213`）。
11. **DLNA 双协议互斥**：DLNA 起播前停同 host AirPlay；AirPlay 桥冷建前对同 host DLNA settle（`control.ts:840-850`、`airplay/control.ts:583-618`、`:353-361`）。
12. **桥默认开启且失败不回落 solo**：`MUSICFLOW_AIRPLAY_BRIDGE=0` 才是回滚专线（`airplay/control.ts:278-280`、`airplay/protocolPlayer.ts:124-126/203-206`）。
13. **桥成员没有 solo 会话视图**：`/status`、组状态必须从泵派生（`airplay/protocolPlayer.ts:208-218`、`peers.ts:1202-1212`）。
14. **桥组无直连成员时 `canKeepStream=false`**：S1/S2 必须改走 `clearPlayback`，否则桥收 `BOUNDARY{stop}` 清掉预取帧（`services/sendspin/playerCore.ts:326-338`、`:455-476`）。
15. **混合组不能用纯桥深锚**：直连 esp32 硬同步阈值 5ms，深锚会造成秒级跳变；深锚仅纯桥组（`services/sendspin/streamEngine.ts:1278-1300`）。
16. **组内 DLNA 无共享时间线**：新成员禁止入组（`services/group/index.ts:420-422`）；历史成员仍会被逐台 cast（`group/protocolPlayer.ts:740`），但无法同步。
17. **客户端洗牌以服务端为权威**：`shuffleOrder/shufflePos/shuffleEpoch` 随快照下发，客户端不得自行生成（`services/player/types.ts:167-185`；`QC:1819-1842`）。
18. **`startPosition` 一次性**：只在一次 `peer_queue_changed` 里带出，随后删除；后续轮询不会重复给（`services/peer.ts:904-914`、`types.ts:158-166`）。
19. **本机播放状态权威在客户端**：服务端只存内存 + 30s TTL；重启后靠下一次上报补齐（`services/peer.ts:765-817`）。
20. **Web 播放器不再被控**：`/v1/play` 对 Web local 403；`peer_command` 直返 `delivered:false`（`routes/api/play.ts:42-48`、`routes/api/shared.ts:580-585`）。
21. **Web 不走 `flow=1`**：HTTP 客户端自己推进队列，服务端替它拼流会让两边各推进一次（`routes/rest/index.ts:2533-2536`；前端无 `flow=`）。
22. **cast 30s 硬顶**：超时必须回收设备半开会话，且兜底回调不能 throw（`QC:1627-1638`、`:1465-1480`）。
23. **乐观窗口 5s / DLNA 25s**：cast 前开窗，seek 时立即关窗，否则误判 stalled（`services/player/PlayerController.ts:22/27`、`QC:502-511`）。
24. **暂停看门狗 30s 自动 stop**：该 stop 产生的 IDLE 不是曲目结束，`pauseStopSettle` 必须拦住（`services/sendspin/playerCore.ts:640`、`services/player/pauseStopSettle.ts:46-62`）。
25. **seek 最小粒度 1s**：HTTP 入口统一 `alignSeekSeconds`，非整秒会让子进程帧栅格错位并饿死事件循环（`routes/api/peers.ts:952-959`）。
26. **显示持有硬顶 +5s**：设备迟迟不进入新曲也要放开，避免 UI 永久卡旧曲（`QC:2051`）。
27. **组看门狗 10s tick，全员离线即悬挂**：`isActive` 不变、队列保留；成员回归 `resumeActive`（`services/group/watchdog.ts:17/72-94`）。
28. **桥路由对账 60s、孤儿宽限 55s**：只摘不建；单机伪组路由必须并入事实源（`group/protocolPlayer.ts:960-967`、`airplay/protocolPlayer.ts:108-115`）。
29. **`MUSICFLOW_AIRPLAY_BRIDGE=0` 时 AirPlay 逐台 solo**：组内无共享时间线（`group/protocolPlayer.ts:744-752`）。
30. **`flow` 的「缺省关」是由 crossfade 默认 disabled 实现的**，不是 `FLOW_ENABLED` 默认 0（`flowSource.ts:51-63`）。`routes/rest/index.ts:2760` 注释「缺省关」是结果描述，易误读。
31. **`QueueSnapshot.revision` 在事件载荷里是变更前值**：自增发生在 `emit` 的监听器里，快照先构造（`QC:265-272`）。
32. **`persist` 不存 `ended/contentContext/洗牌序列`**：重启后 `ended=false`，`contentContext` 失效，洗牌序列惰性重建（`QC:2454-2455`、`types.ts:95-96`）。
33. **`mixed_anchor_lead_ms` 已不作为链路配置**：P3（2026-11-02）统一纯桥/混合组锚点口径后该值被移除（`services/group/delayCalib.ts:18`、`streamEngine.ts:1302-1312`）；列仍在 `player_groups` 中仅为历史兼容（`db/schema.ts:441-442`）。

**旧文档过时点**

- `播放器链路调试与模拟播放器验收手册.md` §2.6「DLNA 成员在组里永远静默」：代码仍会对历史 DLNA 成员逐台 `playMedia`（`group/protocolPlayer.ts:740`），只是无共享时间线。以本文为准。
- `routes/rest/index.ts:2760` 注释「开关打开时（缺省**关**，见 flowSource.resolveFlowSettings）」：`enabled` 缺省实际为 `1`，实际默认关来自 `crossfade=disabled`（`flowSource.ts:55-57`）。

## 10 倍速播放（2026-11-14 起；服务端权威）

> 本章描述**已实现并实测**的倍速能力。倍速只作用于**服务端出流/推流**的播放器
> （DLNA、sendspin 单机与组、AirPlay 桥/直连、用户组与混合组）；客户端/浏览器
> **本机播放**的倍速仍由各自播放器负责，服务端不参与（见 §10.6）。

### 10.1 档位与归一

- 白名单：`0.75 / 1 / 1.25 / 1.5 / 1.75 / 2`，与 MusicFlow-client
  `lib/features/player/widgets/player_utility_bar.dart` 完全一致。
- 任何入参都经 `normalizePlaybackSpeed()` 收敛到最近档位；非法/NaN 回落 1。
  实现在 `backend/src/services/player/playbackSpeed.ts`。
- 持久化：`settings` 表 `playback_speed:<裸 id>`（设备/组各自一份），不写队列表。

### 10.2 时间轴约定（唯一口径）

| 概念 | 定义 | 谁维护 |
|---|---|---|
| 内容时间 | 用户感知的歌曲时间；`duration`、`seek`、歌词、进度条都用它 | 对外唯一口径 |
| 输出流时间 | 经 `atempo` 压缩后的音频秒（1.5x 时 60s 内容 = 40s 音频） | ffmpeg 解码段 |
| 设备可听时间 | 设备上报的 `RelTime`（连续流不换曲归零） | 设备 |

换算只有一处来源：`contentToStreamSec / streamToContentSec`。
**禁止**在调用点手写 `* speed` / `/ speed`。

### 10.3 各链路实现点

| 链路 | 倍速落点 | 位置/时长换算 | seek |
|---|---|---|---|
| DLNA 单曲（`/rest/dlna/stream`） | `resolveRequestAf` 之后 `withAtempo`（链尾） | `getDeviceStatus` 读 `castSpeed`：Raw×speed；墙钟外推×speed；`TrackDuration`×speed | SOAP `REL_TIME` 用 `内容/speed`；URL `timeOffset` 同 |
| DLNA flow（`serveFlowQueue`） | 逐曲 af 追加 `atempo`；`FlowItem.durationSec/speed` 只用于预取点 | 会话时间轴保持**输出流秒**（`itemStartSec`/`streamSec`/节流都不除 speed）；DLNA `pollState` 用 `flowProgress` 把累计位置减去当前曲起点（×speed） | `timeOffset>0` 走单曲管道，不做流内 seek |
| sendspin 单机泵 | `resolveSendspinAf` 链尾 `atempo` | 泵内全部时间轴为输出流 ms：`durationMs = 内容/speed`、游标 1× 墙钟；`pollCore` 对外 `positionMs×speed`、`durationMs` 保持内容 | `seek/armSeek` 入参内容秒 ÷speed；seekCore 夹取仍用内容时长 |
| sendspin 用户组 | 同上（组泵） | 同上（`pollCore` 统一） | 同上 |
| AirPlay 桥（默认） | PCM 来自单机伪组泵 `__bridge_solo:<dev>`，`speed` 由桥 player 显式下传 | `getBridgePeerStatus → sendspinGroupPoll`，天然内容口径 | 走泵 seek（内容秒） |
| AirPlay 直连（`MUSICFLOW_AIRPLAY_BRIDGE=0`） | 出流 af 追加 `atempo` | `sessionSpeedMeta`：`内容 = seekStart + (RAOP 流位置 − seekStart)×speed` | URL `timeOffset` = 内容/speed；`setStartPosition` 用内容秒 |
| 用户组 / 混合组 | 组泵统一（sendspin 全组）；DLNA 历史成员扇出时显式传组倍速（`opts.speed`） | 组状态来自 leader 泵（内容） | 组 seek 走泵 |

### 10.4 变速语义

出流是在 cast/起泵时由 ffmpeg 一次性生成的，**不存在运行中改滤镜**。
`POST /v1/peers/:id/speed` 的语义是：

1. 写入注册表 + settings；
2. 广播 `queue_changed`（快照带 `speed`）；
3. 队列在播时，用**当前内容位置**重投当前曲（`QueueController.setPlaybackSpeed`
   → `playCurrent(..., posMs, "speed")`），新流按新倍速生成；
4. 未在播 / `advancing` 在途 ⇒ 只记偏好，下一次 cast 生效。

副作用（已知、可接受）：变速瞬间有一次重组流的短暂停顿；DLNA flow 若在
`timeOffset>0` 上重投会退化为单曲管道，下一曲起恢复 flow。

### 10.5 控制面

- `POST /v1/peers/:peerId/speed`，body `{"speed": 1.25}` → `{success, speed}`；
  `local:*` 返回 400（本机倍速由客户端负责）。
- `GET /v1/peers/:peerId/status` 增加 `speed` 字段；`GET .../queue` 的
  `QueueSnapshot.speed` 同步下发。
- 客户端/Web 只回显 `speed`，**不得**据此自行换算时间。

### 10.6 客户端与 Web 本机

- 客户端本机播放：`player_provider.dart` 的 `setPlaybackSpeed` 已存在并持久化，
  与本文无关；投屏到远端设备时由服务端倍速生效。
- Web 端本机播放：`player` store 的 `playbackRate` 只作用于 Howler；远端设备
  需调用 §10.5 的接口。
- 两者与服务端队列共用同一份 `speed` 展示字段，但**不是同一份执行体**。

### 10.7 已知限制

1. 组内倍速以**组**为单位，组内各设备不能各放各的快慢（同一首歌两种音高不可接受）。
2. 设备侧 `Access` 的流缓冲无法被服务端修改：变速靠重投，不能"平滑渐变"。
3. AirPlay 直连（回滚专线）的组扇出不做组倍速传递（桥为默认路径，不受影响）。
4. 客户端 UI 尚未把远端 `speed` 做成可点选控件；接口已可用，Web 端同理。

### 10.9 实测中修掉的四处缺陷（230，2026-11-14）

| # | 现象（可复现） | 根因 | 修法 |
|---|---|---|---|
| 1 | 起播后 4s 切 1.5x，设备 URI 没有 `timeOffset`，从头重放 | `setPlaybackSpeed` 的落点只读 `lastPos / lastPlaying`，两者只在 5s 一轮的 poll 里更新 | 切倍速前向播放器要一次 `pollState()`（内容秒现场）；非 PLAYING 只记偏好不重投；落点按当前曲时长夹紧 |
| 2 | 重投后 URI 已带 `timeOffset=3`，但 `/status` 位置从 0 重新爬 | 设备 `RelTime` 以**本次 URI 起点**计数，`getDeviceStatus` 直接用 `streamToContentSec(RelTime)`，丢掉了起播偏移 | `DeviceRuntime.castContentOffsetSec` 记录本次 cast 的内容秒偏移，位置换算补上；SOAP Seek 成功后清零（设备轴已与内容轴对齐），`clearCurrentMedia` 复位 |
| 3 | flow 下 `/api/v1/peers/:id/status` 位置越过单曲时长（1.5x 播到 24s 后仍 27/30/33…） | 归零只在协议 player 的 `pollState` 做，而该 REST 路由**直接调 `getDeviceStatus`** | 把 flow 归零移进 `getDeviceStatus`（DLNA 时间轴唯一出口），协议 player 那份删除，避免二次相减 |
| 4 | 暂停中把 0.75x 改成 1.25x，恢复后声音仍是 0.75x（进度却按 1.25x 走） | 恢复播放走 `player.resume()` / DLNA 直连 `playDevice()`，设备继续拉旧速率的编码流 | `appliedSpeed` 记录最近一次 cast 实际倍速；`transport("play")` 与 DLNA `/play` 分支在「偏好 ≠ 已应用」时以当前位置重投新流 |

对照组实测（同一模拟渲染器，`/tmp/test_speed_matrix.py`）：

| 阶段 | 观测 |
|---|---|
| 1x → 1.5x（4.0s 处切） | `timeOffset=3`（=4/1.5 取整），位置 4→4 连续，其后 1.5×/s 增长 |
| 1.5x → 0.75x（14.5s 处切） | `timeOffset=19`，位置 14.5→15 连续，其后 0.75×/s 增长 |
| 暂停（0.75x，19.5s） | 状态 `PAUSED_PLAYBACK`、位置冻结、流请求数不增 |
| 暂停中设 1.25x | 状态与位置都不变（只记偏好，不把暂停的设备拉起） |
| 恢复 | 新流 `timeOffset=16`（=19.5/1.25 取整 ⇒ 内容 20s），位置 19.5→20 连续，其后 1.25×/s 增长 |
