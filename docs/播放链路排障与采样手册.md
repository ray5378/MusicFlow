## 0 一分钟速查（决策树）

| 现象 | 第一步先看 | 第二步 | 指向 |
|---|---|---|---|
| 秒级 / 持续卡顿，进度在走但没声 | `bridge-window-dead` | `bridge-servo` → `ring-diag` | §2（三步定位）、§4.1 |
| 切歌**开头丢 1~2s** | `[airplay-bridge] realigned: … drift=<负> drop=<N>` | `droppedFrames` vs `newgenSkipFrames` | §4.2 |
| 换歌后**一串异常**（进度/封面/断粮齐发） | 接续四级同链 | 反向判据（否决/撤回） | §3、§4.3 |
| 两台设备**不同步**（快/慢几百 ms） | `anchor-content` 的 `picked=` | tick 的 `driftUs` | §5 口径 + §5.7 |
| 队列见底、`late` 暴涨 | `bridge-servo` 的 `cand`/`backlogMs` | `ring-diag` 的 `bufferedMs`/`budgetMs` | §2.4 |
| 「到底该不该信 `inQueueMs`」 | — | — | §5 |
| 想改阈值 / 试新方向前 | §8 已证伪清单 | A/B 判据模板 | §6、§8 |

### 1.4 采集完整性与启动期

- `docker restart` 后 **~90s 是启动期**，指标不可采信（设备握手、桥重建、时间线首锚都在此窗口内）。
- **部署/重启瞬态**：2026-11-24 的 `18:38`、`18:52` 两次重启后，首代各出现 **1 次** `bridge-window-dead`，`reason` 均为 `content-beyond-horizon`：
  ```
  bridge-window-dead dev=00226CFFA0C0 reason=content-beyond-horizon
    cursorVsNowMs=-287540060 tailVsNowMs=10575 horizonMs=5500 firstCandVsNowMs=6750
  ```
  **特征**：`cursorVsNowMs` 是极大负值（游标未初始化的哨兵值）⇒ **属启动期瞬态，不可当稳态断粮**。
  稳态断粮的 `cursorVsNowMs` 是「小幅度负/正」量级，不会出现 `-2.8e8 ms`。
- 采集完整性自检：`base.jsonl` 的 `tick` 频率是否 250ms、`ring-diag` 是否按设备齐全、
  `media` 是否 1s 心跳；用 `an_recent3.py` 的「采集完整性」段确认。

## 2 断粮三步定位法（缺一步都别下结论）

**断粮定义**：播放器状态正常、进度在走，但这一拍**一帧音频都没投出去**。
判据不是「没声」（那是 §4.2/失声文档的领域），而是「**投递侧零输出**」。

### 2.0 先排除三类「看着像断粮」的（否则三步就白做了）

| 形态 | 与断粮的区别 | 该去哪 |
|---|---|---|
| **静音填充**（`silenceChunks` 高） | 有包、有投递，内容本身是静音 | 「曲中失声」复盘文档（有包但没声） |
| **设备僵死**（`status=stop` / `curpos=0`，服务端仍报 PLAYING） | 投递正常，设备侧不消费 | 监控台的 `L5_SESSION_DEAD` 判定 + TEARDOWN 探测 |
| **网络丢包**（`late` 涨但 `cand>0`、`deliveredMs>0`） | 投得出，路上丢 | RAOP 重传/控制通道（pcap 领域） |

断粮的签名只有一个：**`cand=0` 或 `deliveredMs=0`**，且 `ring-diag` 与之一致（§2.4）。


### 2.1 `bridge-window-dead` —— 断粮的唯一直接证据

```
bridge-window-dead dev=<id> reason=<content-beyond-horizon|no-frame-in-window>
  cursorVsNowMs=<ms> tailVsNowMs=<ms> horizonMs=<ms> firstCandVsNowMs=<ms|null>
  oldEp=<N> ringFrames=<N> group=<name>
```
（源：`sendspin/server.ts:1622`；门控 `candCount===0 && deliveredUs===0n && tailUs>0n`，`:1619`）

| reason | 语义 | 首查 |
|---|---|---|
| `content-beyond-horizon` | 内容**尾**越过投递上沿（`tailVsNowMs > horizonMs`）⇒ 时间线被锚到墙钟之后 | 锚点/时间线：`sendspin timeline anchored: base=…`、`anchor-content`、视界配置 |
| `no-frame-in-window` | 内容在窗口**下沿之前**（游标/水位推过了内容）⇒ 窗口内无帧 | `bridge-servo` 的 `cursorVsNow` vs `horizonMs` |

**读反的典型**：把 `content-beyond-horizon` 当成「上游没货」（≠）。它是「货在，但在未来」。

### 2.2 `bridge-servo` —— 判断「没货」还是「没投」

```
bridge-servo dev=<id> cursorVsNow=<ms> backlogMs=<ms> shiftMs=<ms> targetMs=<ms>
  dueMs=<ms> deliveredMs=<ms> aheadMs=<ms> horizonMs=<ms>
  firstCandVsNow=<ms|null> cand=<N> oldEp=<N>
```
（源：`sendspin/server.ts:1608`）

- `cand=0` ⇒ 窗口内**一个候选帧都没有**（没货）
- `deliveredMs=0` ⇒ 这一拍**没投出去**
- `firstCandVsNow` ⇒ 下一帧还要多久才进窗（`null` = 一帧都没有）
- `backlogMs` ⇒ 上游积压（相对设备消费水位）

### 2.3 `ring-diag` —— 环里存货 vs drain 预算

```
[ring-diag] dev=<id> pull#<N> n=<n> buffered=<帧> bufferedMs=<ms> inQMs=<ms>
  budgetMs=<ms> prefilled=<bool> pushed=<N> dropOld=<N>
```
（源：`airplay/bridgeSession.ts:1564`）

- `bufferedMs=0` 而 `budgetMs>0` ⇒ **父侧没填货**（**不是** drain 不喂）
- `bufferedMs>0` 而 `deliveredMs=0`（来自 §2.2）⇒ **子进程没投**

### 2.4 三者交叉判定表（穷举 4 种组合）

| # | `bufferedMs` | `cand` / `deliveredMs` | `window-dead` | 结论 | 处置 |
|---|---|---|---|---|---|
| 1 | 0 | `cand=0` | `no-frame-in-window` | **上游断供**：环空 + 窗口无帧 | 回到供源/泵（不是桥） |
| 2 | 0 | `cand>0` / `deliveredMs=0` | 无 | **父侧没填货**，drain 想补但无货 | 查父侧 `bridge-servo` 的 `backlogMs` 与 ring 投递 |
| 3 | >0 | `cand>0` / `deliveredMs=0` | 无 | **子进程没投**（有货不出） | 查 drain 节拍、`prefilled`、`pushed` 是否停涨 |
| 4 | >0 | `cand=0` | `content-beyond-horizon` | **时间线被锚到未来**：有货但落在窗口外 | 查锚点（`anchor-content` / `timeline anchored`）与视界 |

**只有第 4 种**才该动「锚点/视界」；第 1–3 种动锚点等于掩盖问题。

## 3 接续四级同链判据

### 3.1 四级日志（少看一级就会误判「接续生效」）

| 级 | 日志 | 含义 | 源 |
|---|---|---|---|
| ① | `sendspin 曲末排空跳过:接续下一首 continuity=1 next=<id>` | 泵在**曲末那一拍**用 `cursorUs` 一次定死 granted | `sendspin/streamEngine.ts:2044`（单一产地 `:2021`） |
| ② | `[Sendspin][continuity] group=… song=… interrupted=… continuity=… keepPrefetch=…` | 起播侧**只读**该结论，不重算 | `sendspin/playerCore.ts:515` |
| ③ | `bridge-generation group=… gen=… reason=… continuity=1 keep=queue,epoch,watermarks` | 桥**不换代**、沿用同一时间线与各设备水位 | `sendspin/server.ts:1011` |
| ④ | `sendspin timeline anchored: base=… lead=…us (sendAhead=…)us handoff=… contig=… continuity=… lastEnd=…` | 泵把 contig 锚点接到上一首末尾 | `streamEngine.ts:1638-1643` |

**同链 = 四级全部出现且 `continuity` 一致、`contig`/`lastEnd` 等于上一首末尾。**

### 3.2 反向判据（出现即「本次不接续」，属**预期**）

| 日志 | 含义 | 源 |
|---|---|---|
| `sendspin 接续承诺被时间窗否决: 尾=<u> now=<u> …` | 时间窗不满足 ⇒ denied | `streamEngine.ts:2036` |
| `sendspin 接续承诺撤回(ring 将被清空,放弃 contig 锚点) song=<id>` | 非接续分支清 ring 时同步撤回 | `streamEngine.ts:1158` |

出现以上任一条时，**两侧 `continuity` 应同时为 `false`**；若一侧仍 `true` ⇒ 撤回没传达，属故障。

### 3.3 两侧分叉的两种历史形态

| 形态 | 后果 |
|---|---|
| 泵 `true` / 起播侧 `false` | 起播侧按「新曲」清 ring ⇒ **断粮**（连接续锚点一起丢） |
| 起播侧 `true` / 泵 `false` | 两套时间轴并存 ⇒ 进度与声音错位、`driftUs` 长期非 0 |

## 4 三类故障的指纹与处置

### 4.1 断粮（队列空、`late` 暴涨）

- **指纹**：`bridge-window-dead` 按拍周期复现 + `cand=0` + `deliveredMs=0`；`ring-diag` 的 `bufferedMs` 与其配对（见 §2.4 表）。
- **自愈条件**：手动 `next`（`mfctl.py next`）会强制换代重建时间线 ⇒ 多数情况下**可自愈**；自动换歌若判定为「不接续」也会重建，但会伴随一次开头静音。
- **处置顺序**：① 按 §2.4 定性 → ② 只有组合 4 才动锚点/视界 → ③ 组合 1–3 回到供源与 drain → ④ 反复复现再上 §6 基线对照。

### 4.2 裁头 / 吞开头（开头丢 1~2s）

- **指纹 A**：`[airplay-bridge] realigned: device=… drift=<负值> frames (<ms>ms) insert=… drop=<N> skip=…`
  （源：`airplay/bridgeSession.ts:2720`）——`drop>0` 且 `drift<0` = 对齐器判定「来晚了」，把开头**裁掉**。
- **指纹 B**：tick 的 `droppedFrames` 突变。**只在 `continuity=false` 的换代窗口出现**（D5：早于 `contentAnchorUs` 的内容整块丢弃）。
- **必须分开读**：`droppedFrames`（D5 主动裁头）vs `newgenSkipFrames`（换代跳段，`bridgeSession.ts:1115`）。
  两者混算会得出「丢包」的错误结论。
- **处置**：查锚点是否**越过首帧**——forceNow 分支 lead 被夹在 `[minSafe, 首帧−200ms]`，
  越过首帧即触发 D5；`deltaUs` 恒定**不代表**锚点没越界。

### 4.3 接续分叉

直接用 §3.1 四级同链 + §3.2 反向判据判定；两种分叉形态与后果见 §3.3。
处置：**不要**在分叉态下改 lead/视界（会同时移动两侧），先让两侧判据重新同源。

## 5 口径铁律（最容易踩的 6 条）

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **`inQueueMs` ≠ 缓冲深度** | 它含对齐器补入的静音：历史 2.7s 里 `insertedFrames=117866 ≈ 2.67s` 就是静音在排队。代码原话：「`deltaUs` 才是设备提前拿到多久的音频，`inQueueMs` 里含对齐器垫的静音，不要拿 `inQueueMs` 当缓冲深度来调这个值」（源：`airplay/bridgeSession.ts:707-712`） |
| 2 | **真缓冲看 `deltaUs`** | `deltaUs` 是「已写入 RAOP 的内容前沿相对 A′ 的超前量」≈ `L + 队列深度`，即设备**出音提前量**（源：`airplay/bridgeSession.ts:13-14`） |
| 3 | **`insertedFrames` 是静音，不是多余音频** | 对齐器补的静音，计入时间线但不发声；累加点 `bridgeSession.ts:2698`、上报点 `:2533` |
| 4 | **`driftUs=0` 只表示对齐** | 它不说明缓冲够不够；缓冲看 `deltaUs` 与 `ring-diag` |
| 5 | **`droppedFrames` 与 `newgenSkipFrames` 分开读** | 前者 D5 裁头，后者换代跳段（`bridgeSession.ts:1115`） |
| 6 | **UTC / CST 混用会得出相反结论** | 见 §1.3 字段级依据 |

**反例（都真踩过）**：把 `inQueueMs` 掉 0 判成断粮（其实是设备当前没排队）；把 `silenceChunks` 高判成失声
（那是有包但静音，与断粮相反）；把 `deltaUs` 恒定判成「缓冲已到 2.5s」（forceNow 下它就是恒定值）。

### 5.7 补充：两台设备不同步怎么读

1. 先按铁律 1/2 排除误读（别拿 `inQueueMs` 比两台）。
2. 比 `anchor-content` 的 `picked=` 与 `finalLeadMs`（源：`bridgeSession.ts:746`）——两队是否吃了同一个共享锚点。
3. 比 tick 的 `driftUs`（是否长期非 0）与 `deltaUs`（两队差距）。
4. **成员补偿**（`anchorShiftUs`，源：`bridgeSession.ts:640`）：正数 = 该设备更晚出声。
   ⚠️ **当前没有独立的补偿下发日志**，只能从锚点差异与听感间接判断——这是已知的观测缺口，
   需要日志时请按 §9 反馈，**不要**据此推断「补偿没生效」。

## 6 基线对照法（区分「预存红」与「新增回归」）

### 6.1 代码侧

```bash
git stash            # 或 git stash push <仅相关文件>
npx vitest run <同一批用例>   # 记录失败集
git stash pop
npx vitest run <同一批用例>   # 与基线失败集逐条比对
```
判据：**失败集完全一致 = 零新增**；多出任意一条即本次改动引入。

### 6.2 现场侧

- 基线必须取「**未改动版本**」的时段：2026-11-24 用 `an_recent.py` 实测 `15:41~17:18`

## 8 已证伪方向（防后人重试）

### 8.1 投递视界抬到 8s —— **两次证伪**

先分清**两个"视界"**，混谈会得出相反结论：

| 名称 | 现值 | 源 |
|---|---|---|
| 桥窗口（子进程向设备推的上沿/下沿） | `BRIDGE_PUSH_HORIZON_US` = **4s** / `BRIDGE_PUSH_FLOOR_US` = **2.5s** | `sendspin/constants.ts:86` / `:100` |
| 父侧投递视界 | `BRIDGE_FEED_CAP_US` = **5s**，实际上沿 `horizonFinal = now + 5s + ahead`（实测 `horizonMs≈5.5s`） | `sendspin/server.ts:1493` / `:1504` |

**证伪的是"父侧投递视界"**：抬到 8s 会超出设备队列容量（实测 `maxQueueMs=4163ms`，源：`server.ts:1486` 注释）⇒
`inQ=0` / `late=17006`，两次证伪；现行仍为 **5s**。

### 8.2 按成员补偿扩视界（`c4190985`）—— **已 revert（`53f7c8c2`）**

结果：`newgenSkip` 7~9 万、`cursor-jump` 31 次。
**结论：同组内所有成员的投递视界必须一致**，按成员差异化扩视界必然打崩时间线。

### 8.3 抬 lead 换缓冲 —— 无效

forceNow 语义是「到包即播」，`deltaUs` **不随 lead 变大**；抬 lead 只把出音推后，
不增加设备可播时长（源：`bridgeSession.ts:13-14` 同段注释）。

### 8.4 A/B 判据模板（任一条违反立即回退）

1. 目标指标**必须改善**；
2. `lossFuture` / `droppedFrames` / `newgenSkipFrames` **不得上涨**；
3. `inQ` **不得塌 0**。
