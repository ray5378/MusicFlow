### 1.4 采集完整性与启动期

- `docker restart` 后 **~90s 是启动期**，指标不可采信（设备握手、桥重建、时间线首锚都在此窗口内）。
- **部署/重启瞬态**：2026-11-24 全天 `docker logs -t musicflow | grep bridge-window-dead` 实测 **7 条 / 4 组**（多数是每次重启后两台设备各 1 条），`reason` 全为 `content-beyond-horizon`：
  时间戳（UTC / CST）：`10:12:05`(18:12,×2)、`10:29:06`(18:29,×1)、`10:38:12`(18:38,×2)、`10:52:02`(18:52,×2)。

  原始行（逐字）：
  ```
  bridge-window-dead dev=00226CFFA0C0 reason=content-beyond-horizon cursorVsNowMs=-287540060
    tailVsNowMs=10575 horizonMs=5500 firstCandVsNowMs=6750 oldEp=0 ringFrames=254 group=ug:12a04c2c-21…
  ```
  **判据靠量级**：`cursorVsNowMs` 出现 `-1e8 ms` 量级 = 游标未初始化（`bcCursor ?? 0n` 撞单调时钟 `hrtime`）⇒ **启动期瞬态**；
  实测稳态 `cursorVsNowMs` 为 **+5475~+5500ms**（≈ 视界 5.5s），断粮态可到 **+33740ms**。三者量级互不重叠，可直接分档。
- 采集完整性自检：`base.jsonl` 的 `tick` 频率是否 250ms、`ring-diag` 是否按设备齐全、
  `media` 是否 1s 心跳；用 `240:/root/an_recent3.py` 的「采集完整性」段确认。

### 1.5 网络面：常驻环形 pcap（与日志面互补，不进判据）

日志面三条（§1.1）只能证明「服务端逻辑有没有给货、有没有投」；**网络丢包、设备到底有没有收到包**这两件事日志面天然证伪不了，必须靠 pcap。所以抓包是整套采样/取证方法里与日志面并列的一环，不是临时补丁。

- **常驻命令（240，手工起、PPID=1、非 systemd 服务）**：
  ```bash
  tcpdump -i eno1-ovs -n -s 0 -U -C 50 -W 12 -w /tmp/pcap2/a.pcap host 192.168.10.30
  ```
  `-C 50 -W 12` = 12 片 × 50MB ≈ 531MB 环形，实测覆盖约 50 分钟（流量越大窗口越短），**滚动覆盖、不可追溯更早**。
- **产物**：`/tmp/pcap2/a.pcap00..11`（属 `tcpdump` 用户）；`tcpdump.log` 起包记录。
- **消费方式**：按需 `tcpdump -r`，先确认时间戳口径再合并切片（环形回绕点 mtime 乱序，多文件须按首包时间排序）；UDP RAOP 载荷过滤 `udp[4:2]=40`。详见 `曲中失声-抓包取证方法论与复盘-2026-10-31.md` §2。
- **时间口径**：`tcpdump -r` 打 **CST**、`docker logs -t` 打 **UTC**（§1.3 铁律），混用会得出相反结论。
- **边界**：pcap 是**取证层**，不进 `playback_side_guard.py` 自动判据（判据只吃日志正文）；常驻抓包会持续占盘，取证窗口结束或任务收工后应停掉并删 `/tmp/pcap2/`，避免长期噪声与磁盘占用。

## 2 断粮三步定位法（缺一步都别下结论）

**断粮定义**：播放器状态正常、进度在走，但这一拍**一帧音频都没投出去**。
判据不是「没声」（那是 §4.2/失声文档的领域），而是「**投递侧零输出**」。

### 2.0 先排除三类「看着像断粮」的（否则三步就白做了）

| 形态 | 与断粮的区别 | 该去哪 |
|---|---|---|
| **静音填充**（`silenceChunks` 高） | 有包、有投递，内容本身是静音 | 「曲中失声」复盘文档（有包但没声） |
| **设备僵死**（`status=stop` / `curpos=0`，服务端仍报 PLAYING） | 投递正常，设备侧不消费 | 监控台的 `L5_SESSION_DEAD`（**判定码，非代码符号**，定义见 `播放监控-多维度监控台使用手册.md:125`；注意其三道闸门 `:132`，重启接管期会误报）+ TEARDOWN 探测 |
| **网络丢包**（`late` 涨但 `cand>0`、`deliveredMs>0`） | 投得出，路上丢 | RAOP 重传/控制通道（pcap 领域） |

断粮的签名只有一个：**`cand=0` 或 `deliveredMs=0`**，且 `ring-diag` 与之一致（§2.4）。


### 2.1 `bridge-window-dead` —— 断粮的唯一直接证据

```
bridge-window-dead dev=<id> reason=<content-beyond-horizon|no-frame-in-window>
  cursorVsNowMs=<ms> tailVsNowMs=<ms> horizonMs=<ms> firstCandVsNowMs=<ms|null>
  oldEp=<N> ringFrames=<N> group=<name>
```
（源：`sendspin/server.ts:1622`；门控 `candCount===0 && deliveredUs===0n && tailUs>0n`，`:1619`）

| reason | 语义 | 首查 |
|---|---|---|
| `content-beyond-horizon` | 内容**尾**越过投递上沿（`tailVsNowMs > horizonMs`）⇒ 时间线被锚到墙钟之后 | 锚点/时间线：`sendspin timeline anchored: base=…`、`anchor-content`、视界配置 |
| `no-frame-in-window` | 内容在窗口**下沿之前**（游标/水位推过了内容）⇒ 窗口内无帧 | `bridge-servo` 的 `cursorVsNow` vs `horizonMs` |

**读反的典型**：把 `content-beyond-horizon` 当成「上游没货」（≠）。它是「货在，但在未来」。

### 2.2 `bridge-servo` —— 判断「没货」还是「没投」

```
bridge-servo dev=<id> cursorVsNow=<ms> backlogMs=<ms> shiftMs=<ms> targetMs=<ms>
  dueMs=<ms> deliveredMs=<ms> aheadMs=<ms> horizonMs=<ms>
  firstCandVsNow=<ms|null> cand=<N> oldEp=<N>
```
（源：`sendspin/server.ts:1608`）

- `cand=0` ⇒ 窗口内**一个候选帧都没有**（没货）
- `deliveredMs=0` ⇒ 这一拍**没投出去**
- `firstCandVsNow` ⇒ 下一帧还要多久才进窗（`null` = 一帧都没有）
- `backlogMs` ⇒ 上游积压（相对设备消费水位）

### 2.3 `ring-diag` —— 环里存货 vs drain 预算

```
[ring-diag] dev=<id> pull#<N> n=<n> buffered=<帧> bufferedMs=<ms> inQMs=<ms>
  budgetMs=<ms> prefilled=<bool> pushed=<N> dropOld=<N>
```
（源：`airplay/bridgeSession.ts:1564`）

- `bufferedMs=0` 而 `budgetMs>0` ⇒ **多数是稳态常态，不是没货**：`buffered*` 是子进程
  ring 里**尚未下泄**的存量，100ms 一拍 drain 取走后即为 0；设备手里可播的水位看
`inQMs`。完整判据见 C-4d（2026-11-25 修正，旧「父侧没填货」口径已作废）。
- `bufferedMs>0` 而 `deliveredMs=0`（来自 §2.2）⇒ **子进程没投**

### 2.4 三者交叉判定表（4 种**异常**组合；正常态不在此表）

| # | `bufferedMs` | `cand` / `deliveredMs` | `window-dead` | 结论 | 处置 |
|---|---|---|---|---|---|
| 1 | 0 | `cand=0` | `no-frame-in-window` | **上游断供**：环空 + 窗口无帧 | 回到供源/泵（不是桥） |
| 2 | 0 | `cand>0` / `deliveredMs=0` | 无 | **父侧没填货**，drain 想补但无货 | 查父侧 `bridge-servo` 的 `backlogMs` 与 ring 投递 |
| 3 | >0 | `cand>0` / `deliveredMs=0` | 无 | **子进程没投**（有货不出） | 查 drain 节拍、`prefilled`、`pushed` 是否停涨 |
| 4 | >0 | `cand=0` | `content-beyond-horizon` | **时间线被锚到未来**：有货但落在窗口外 | 查锚点（`anchor-content` / `timeline anchored`）与视界 |

**只有第 4 种**才该动「锚点/视界」；第 1–3 种动锚点等于掩盖问题。

两个读表前提（踩过）：
- **`deliveredMs=0` 在稳态也会出现**（游标已贴视界、这一拍确实没东西可投），此时必须再看
  `ring-diag` 的 `pushed` 是否**停涨**、`bufferedMs` 是否见底，才能定性为异常。
- **`budgetMs` 只是背景量**（drain 这一拍想补多少），它本身不构成判据；判据永远是
  `bufferedMs`（有没有货）× `deliveredMs`（有没有投）。

## 3 接续四级同链判据

### 3.1 四级日志（少看一级就会误判「接续生效」）

| 级 | 日志 | 含义 | 源 |
|---|---|---|---|
| ① | `sendspin 曲末排空跳过:接续下一首 continuity=1 next=<id>` | 泵在**曲末那一拍**用 `cursorUs` 一次定死 granted | `sendspin/streamEngine.ts:2044`（单一产地 `:2021`） |
| ② | `[Sendspin][continuity] group=… song=… interrupted=… continuity=… keepPrefetch=…` | 起播侧**只读**该结论，不重算 | `sendspin/playerCore.ts:515` |
| ③ | `bridge-generation group=… gen=… reason=… continuity=1 keep=queue,epoch,watermarks` | 桥**不换代**、沿用同一时间线与各设备水位 | `sendspin/server.ts:1011` |
| ④ | `sendspin timeline anchored: base=… lead=…us (sendAhead=…)us handoff=… contig=… continuity=… lastEnd=…` | 泵把 contig 锚点接到上一首末尾 | `streamEngine.ts:1638-1642` |

**同链 = 四级全部出现且 `continuity` 一致、`contig`/`lastEnd` 等于上一首末尾。**

### 3.2 反向判据（出现即「本次不接续」，属**预期**）

| 日志 | 含义 | 源 |
|---|---|---|
| `sendspin 接续承诺被时间窗否决: 尾=<u> now=<u> …` | 时间窗不满足 ⇒ denied | `streamEngine.ts:2036` |
| `sendspin 接续承诺撤回(ring 将被清空,放弃 contig 锚点) song=<id>` | 非接续分支清 ring 时同步撤回 | `streamEngine.ts:1158` |

出现以上任一条时，**两侧 `continuity` 应同时为 `false`**；若一侧仍 `true` ⇒ 撤回没传达，属故障。

### 3.3 两侧分叉的两种历史形态

| 形态 | 后果 |
|---|---|
| 泵 `true` / 起播侧 `false` | 起播侧按「新曲」清 ring ⇒ **断粮**（连接续锚点一起丢） |
| 起播侧 `true` / 泵 `false` | 两套时间轴并存 ⇒ 进度与声音错位、`driftUs` 长期非 0 |

## 4 三类故障的指纹与处置

### 4.1 断粮（队列空、`late` 暴涨）

- **指纹**：`bridge-window-dead` 按拍周期复现 + `cand=0` + `deliveredMs=0`；`ring-diag` 的 `bufferedMs` 与其配对（见 §2.4 表）。
- **自愈条件**：手动 `next`（**240**`:/root/mf_watch/mfctl.py next`）会强制换代重建时间线 ⇒ 多数情况下**可自愈**；自动换歌若判定为「不接续」也会重建，但会伴随一次开头静音。
- **处置顺序**：① 按 §2.4 定性 → ② 只有组合 4 才动锚点/视界 → ③ 组合 1–3 回到供源与 drain → ④ 反复复现再上 §6 基线对照。

### 4.2 裁头 / 吞开头（开头丢 1~2s）

- **指纹 A**：`[airplay-bridge] realigned: device=… drift=<负值> frames (<ms>ms) insert=… drop=<N> skip=…`
  （源：`airplay/bridgeSession.ts:2720`）——`drop>0` 且 `drift<0` = 对齐器判定「来晚了」，把开头**裁掉**。
- **指纹 B**：tick 的 `droppedFrames` 突变。**只在 `continuity=false` 的换代窗口出现**（D5：早于 `contentAnchorUs` 的内容整块丢弃）。
- **必须分开读**：`droppedFrames`（D5 主动裁头）vs `newgenSkipFrames`（换代跳段，`bridgeSession.ts:1115`）。
  两者混算会得出「丢包」的错误结论。
- **处置**：查锚点是否**越过首帧**——forceNow 分支 lead 被夹在 `[minSafe, 首帧−200ms]`，
  越过首帧即触发 D5；`deltaUs` 恒定**不代表**锚点没越界。

### 4.3 接续分叉

直接用 §3.1 四级同链 + §3.2 反向判据判定；两种分叉形态与后果见 §3.3。
处置：**不要**在分叉态下改 lead/视界（会同时移动两侧），先让两侧判据重新同源。

## 5 口径铁律（最容易踩的 6 条）

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **`inQueueMs` ≠ 缓冲深度** | 它含对齐器补入的静音：历史「缓冲 2.6s」里 `insertedFrames=117866`（≈2.67s）就是这部分静音在排队（两个数别混：2.6s 是当时的缓冲口径，2.67s 是帧数折算时长）。代码原话：「注意 `deltaUs` 才是「设备提前拿到多久的音频」，`inQueueMs` 里含对齐器垫的静音，**两者不是同一口径，**不要拿 `inQueueMs` 当缓冲深度来调这个值」（源：`airplay/bridgeSession.ts:707-712`） |
| 2 | **真缓冲看 `deltaUs`** | `deltaUs` 是「已写入 RAOP 的内容前沿相对 A′ 的超前量」≈ `L + 队列深度`，即设备**出音提前量**（源：`airplay/bridgeSession.ts:13-14`） |
| 3 | **`insertedFrames` 是静音，不是多余音频** | 对齐器补的静音，计入时间线但不发声；累加点 `bridgeSession.ts:2698`、上报点 `:2533` |
| 4 | **`driftUs=0` 只表示对齐** | 它不说明缓冲够不够；缓冲看 `deltaUs` 与 `ring-diag` |
| 5 | **`droppedFrames` 与 `newgenSkipFrames` 分开读** | 前者 D5 裁头，后者换代跳段（`bridgeSession.ts:1115`） |
| 6 | **UTC / CST 混用会得出相反结论** | 见 §1.3 字段级依据 |

**反例（都真踩过）**：把 `inQueueMs` 掉 0 判成断粮（其实是设备当前没排队）；把 `silenceChunks` 高判成失声
（那是有包但静音，与断粮相反）；把 `deltaUs` 恒定判成「缓冲已到 2.5s」（forceNow 下它就是恒定值）。

### 5.7 补充：两台设备不同步怎么读

1. 先按铁律 1/2 排除误读（别拿 `inQueueMs` 比两台）。
2. 比 `anchor-content` 的 `picked=` 与 `finalLeadMs`（源：`bridgeSession.ts:746`）——两队是否吃了同一个共享锚点。
3. 比 tick 的 `driftUs`（是否长期非 0）与 `deltaUs`（两队差距）。
4. **成员补偿**（`anchorShiftUs`，源：`bridgeSession.ts:640`）：正数 = 该设备更晚出声。
   补偿值**条件性**打印在两处：① 改延迟（`PUT /v1/groups/:id/delays`）时
   `[bridge-rebuild-delay] enter dev=… shiftUs=…`（`airplay/control.ts:493`）；
   ② 暖复用 prepare 时 `[airplay-bridge] sessions: prepare warm-reuse … shiftUs=…`（`bridgeSession.ts:3160`）。
   常规 prepare / 起播**不打**这两行 ⇒ **不能凭"没日志"推断补偿没生效**；要验证就改一次延迟再看 `shiftUs=`。


### 5.8 补充：`docker logs --since` 的时区陷阱（2026-11-26 实锤）

`docker logs -t` 打印 **UTC**，而 `--since` 对**裸时间按容器本地时区（CST）**解释，
只有带 `Z` 才是 UTC。实测同一时刻：

```
$ docker logs -t musicflow --since 2026-11-26T14:34:35Z | head -1 → 2026-11-26T14:34:35.384  ✅
$ docker logs -t musicflow --since 2026-11-26T14:34:35  | head -1 → 2026-11-26T06:34:35.031  ❌
```

**代价**：按裸时间给「热补丁前后」分段，会把修复后的窗口取成 8 小时前，
得出「stall=0、一切正常」的假结论。铁律：

1. 分段统计**一律带 `Z`**；写给人看的时间**一律折算 CST = UTC+8**。
2. 分段边界取 `Database initialized successfully` 的时间戳（每次热补丁重启的锚点），
   不要凭记忆估。
3. 统计脚本里 `awk` 取时间戳必须配 `docker logs -t`，否则 `$1` 是日志前缀，
   脚本会静默输出 `n/a`（servo 间隔统计就踩过这个）。

## 8 已证伪方向（防后人重试）

### 8.1 投递视界抬到 8s —— **两次证伪**

先分清**两个"视界"**，混谈会得出相反结论：

| 名称 | 现值 | 源 |

| 桥窗口（子进程向设备推的上沿/下沿） | `BRIDGE_PUSH_HORIZON_US` = **4s** / `BRIDGE_PUSH_FLOOR_US` = **2.5s** | `sendspin/constants.ts:86` / `:100` |
| 父侧投递视界 | `BRIDGE_FEED_CAP_US` = **5s**，实际上沿 `horizonFinal = now + 5s + ahead`（实测 `horizonMs≈5.5s`） | `sendspin/server.ts:1493` / `:1504` |

**证伪的是"父侧投递视界"**：抬到 8s 会超出设备队列容量（实测 `maxQueueMs=4163ms`，源：`server.ts:1486` 注释）⇒

### 8.2 按成员补偿扩视界（`c4190985`）—— **已 revert（`53f7c8c2`）**

结果：`newgenSkip` 7~9 万、`cursor-jump` 31 次。
**结论：同组内所有成员的投递视界必须一致**，按成员差异化扩视界必然打崩时间线。

### 8.3 抬 lead 换缓冲 —— 无效

forceNow 语义是「到包即播」，`deltaUs` **不随 lead 变大**；抬 lead 只把出音推后，
不增加设备可播时长（源：`bridgeSession.ts:13-14` 同段注释）。

### 8.4 A/B 判据模板（任一条违反立即回退）

2. `lossFuture` / `droppedFrames` / `newgenSkipFrames` **不得上涨**；

### C-4 死锁形态判读(2026-11-25 真机标定)

`bridge-start-seek-deadlock` 一条日志的 `ringFrames` + `shiftMs` + `headVsNowMs`
三个字段即可定性:

| 字段组合 | 形态 | 处置 |
|---|---|---|
| `ringFrames≈1400`(环满) + `shiftMs≈6000` 且**连发多次** | 整帧对齐首帧被 `ts<=cursor` 跳过 ⇒ 连环 | 见下方「余量判据」;未修版会连累到 `offset=-31M` |
| `ringFrames≈260`(环空) + `shiftMs≈6500` | 起播/换代冷启动 | 单次即恢复,正常 |
| `mode=light-restart` + `pullBackMs≈32000` | shift>16s 走轻重启 | 正常;确认 `offset -= pullBack` 而非 `= -pullBack` |
| `ringFrames≤60` + `shiftMs≈9000` | 环几乎空 | 换代残留,1 次即恢复 |

**余量判据(2026-11-25 起)**:修好后 `shiftMs` 恒比 `headVsNowMs` 小
`BRIDGE_PUSH_TICK_MS=250`,例 `shiftMs=6250 headVsNowMs=6500`。
**两者恒等 ⇒ 余量失效,连环会复发**(改前实测 5 连、offset 累到 -31M)。

**offset 判读**:每次死锁精确 `-=shiftUs`(整环前移)或 `-=pullBack`(轻重启),
单调递减、只在新代次清零。看到「增量与 shift 不符」先查采集口径(见上方 cut 警告),
再看是否夹了换代清零。

**`droppedFrames` 的准确语义(2026-11-25 更正,勿再误判)**:
它统计的是「**ts 早于锚点(`contentAnchorUs = anchorUs`)的内容被裁/跳**」
(`bridgeSession.ts:2942`),**不是「新曲开头丢帧」**。切歌时它必然上涨,涨的量 =
**旧曲尾未播完的部分**:
- `newgen-skip`(独立日志,带 frames/ms)= 新代次首帧前的大缺口跳段,**不裁首帧**;
- 其后 `droppedFrames` 增量 = 锚点之前的旧曲尾实际内容。
两者相加 = 旧曲尾总长(真机 06:34《燃》:newgen-skip 1200ms + 裁剪 2.3s = 3.5s)。

**判据**:看 `anchor-content` 日志 ——
- `contentVsNowMs > finalLeadMs`(锚点在首帧**之前**)⇒ 新曲首帧在保护范围内,
  `droppedFrames` 上涨属**正常切歌代价**,不是缺陷;
- `contentVsNowMs < finalLeadMs`(锚点**晚于**首帧)⇒ 才会裁新曲开头,需修锚点。

**反直觉事实(2026-11-25 实证)**:把锚点往首帧靠拢**会放大** `droppedFrames`
(4s 上限丢 1.03s → 30s 上限丢 3.5s),因为锚点越晚,落在它之前的旧曲尾越多。
故「锚点对齐首帧」的正确判据不是 `droppedFrames` 变小,而是
`contentVsNowMs > finalLeadMs` **且** `newgen-skip` 两台一致。

### C-4b 显示进度视觉停顿(音频正常, 仅进度条突变; 2026-11-25)

**现象**:用户听感无停顿,但进度条在切歌/换代附近**快速停顿又继续**。
这是**显示层**问题,不是播放/投递卡顿,判据:

- 先看 `bridge-servo` / tick: `inQueueMs` 稳定、`silenceChunks=0`、
  `realigned` 不涨、`deltaUs` 稳态 ⇒ 音频链路健康,直接转显示层。
- 根因: `displayPosition = framePos - depthMs + lead`,`depthMs = cursor - now`;
  cursor 在换代/重锚时复位到 now ⇒ depthMs 从 ~5.5s 突变 0 ⇒ 显示凭空前跳
  被 `capDisplayByElapsed` 钳住 ⇒ 进度条停住等墙钟追上。
- 修法(v4.15.3): 组级 `displayDepthMs` 每拍最多变 50ms 限速跟随,换曲/seek
  清 null。**禁止**改成硬粘/历史最大值 —— 会让 seek 往回拖时进度卡死
  (2026-11-21 血律)。
- 观测口径: 容器日志**没有** displayPosition 字段;用双机进度差采样
  (`test5.log` 的 `差=/期望=/残差=`) 判定。v4.15.3 部署后 397 条
  `|残差| max=8ms avg=2.8ms`、>50ms 为 0,换代 ±30s 峰值全 ≤6ms ⇒ 平滑。
- 诚实边界: 若窗口内无 deadlock/LR/重锚(显示纠错触发条件),只能判「稳态无
  停顿 + 无回归」,不能声称纠错能力已被真机触发验证。

### C-4d `buffered=0` 不是断粮(2026-11-25 修正, 勿再误判)

`ring-diag` 的 `buffered` / `bufferedMs` 是**子进程私有 ring 里尚未下泄给设备的存量**，
不是设备缓冲。`startRingDrain()` 每 100ms 取走一批下泄，`buffered` 归 0 是**取走后的
正常状态**;真机 2h24min 采样 `buffered=0` 出现 3538 次,同期 `inQMs` 恒 2000~2975、
`prefilled=true`、`budgetMs=525/575`,播放全程健康。

**三级口径(代码:`bridgeSession.ts:1577-1650`)**:

| 字段 | 真实语义 | 断粮判读 |
|---|---|---|
| `buffered` / `bufferedMs` | ring 里**未下泄**的帧/毫秒(每 100ms 被 drain 取走) | 归 0 **正常**,不单独判据 |
| `inQMs` | **设备 RAOP 发送队列** `inBytes` 换算的可播毫秒 | 这才是设备水位;`→0` 且持续才危险 |
| `budgetMs` | 本拍下泄预算:未首灌 3500 / 低于 3000ms 目标 `max(servo,150)` / 达标 105(1.05x) | 105 是稳态维持档,**不是没货** |

**正确判据**:
- 稳态 `buffered=0 + bufferedMs=0 + inQMs≈2500 + budgetMs≈105 + prefilled=true`
  ⇒ **健康**,ring 取空正说明供给被设备及时消化(对齐 MA PushStream 按成员水位供给)。
- 真断粮仍只看 §2 三条:`bridge-window-dead` + `cand=0/deliveredMs=0` + `inQMs` **持续**见底;
  `inQMs=0` 只在换代瞬间偶发(本窗口 4 次)属正常。
- 旧判据「`bufferedMs=0 且 budgetMs>0` ⇒ 父侧没填货」**已作废**(那是 budget 改语义前的结论,
  按它会把上述稳态全判成断粮)。§2.3 已同步修正。

### C-4c 时间口径统一(2026-11-25 17:14 CST 起)

- `docker logs -t` 的时间戳由 Docker daemon 打、固定 UTC(`Z`),**不受容器 `/etc/localtime` 挂载或 `TZ` 环境变量影响**(容器 `date` 早已是 CST)。采样器在写入侧把行首转 CST `+08:00`。
- **切换点**:`2026-11-25T17:14:33+08:00`(日志内 `TZ CHANGE` 行)。此前 `base_raw.log` 为 UTC `Z`、此后为 CST `+08:00`;`test5.log` 一直是本地 CST `HH:MM:SS`。
- **判读纪律**:跨切换点比对一律先归一到同一口径(UTC 行 +8h);分析脚本窗口常量一律写 CST (`an_hotfix.py` 起点 `2026-11-25T15:22:06` = 原 UTC `07:22:06` + 8h);历史 5h 回溯脚本 (`analyze_5h`/`probe_5h*`/`refute_5h`)保留 UTC 窗口并已标注口径,正则兼容 `Z|\+08:00`。

### C-5 注入纪律(2026-11-25 卡顿事故后写死)

1. **一次只改一个变量**:禁止「连点下一首×6 + pause + stop/play」连招。实测把桥侧
   积压顶到 `inQueueMs=9700`(设备容量仅 4163ms)、`realigned` 累积 408 ⇒ 设备端秒级抖动。
2. **用户可能在听时禁止破坏性注入**(连切/pause/stop/断网)。要做先问,或等无人时段。
3. **`docker restart` 本身有副作用**:重启后设备重连 + 时钟重同步需要时间,期间
   `late` 会短暂上涨、偶发一次死锁。**判「修复无效」前先给 ≥2 分钟稳定窗**,
   否则会把重启副作用算到代码头上(2026-11-25 12:24 即此误判)。
4. **判「卡顿」三指标同看**:`realigned`(累计值,重启归零会误导)、`inQueueMs`
   (桥侧积压,>4163ms 即溢出)、`droppedFrames` **增速**(非总量)。只看一个必误判。
5. **上线后用户报异常,先回滚止血,再离线分析**。不要在用户耳朵上做实验。
6. 回滚前确认备份 tgz 层级:`docker cp src:/dir dest` 得到的 `dest` **就是 dir 内容**,
   不是 `dest/dir`(2026-11-25 踩过:cp 报 no such file 但 restart 已执行,白回滚一次)。
7. 本仓「断粮补静音」autostart 只在**真断粮**(`contentTail < now+2.5s`)触发;
   环满/游标贴边型死锁它不是解药 —— 别拿它当万能兜底。
