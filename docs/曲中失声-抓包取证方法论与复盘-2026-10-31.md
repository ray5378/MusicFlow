# 曲中失声：抓包取证方法论与复盘 ★ 2026-10-31

> 本文是「HiVi 播放中曲中（同一首歌内）偶发失声数秒自愈」问题的**完整取证复盘**。
> 包含：最终根因（修正版）、误判时间线、可复用的抓包/解析/对账工具箱、伪证陷阱清单。
> **本文修正 `airplay-权威方案文档.md` 顶部「排障必读」块中已被推翻的结论**——重传缓冲大小不是根因。

---

## 0. 一分钟结论（最终根因，2026-10-31 修正版）

```
桥投递侧速率被精确钳在 1x（250ms tick × [now+1.5s+ahead, now+2.5s+ahead] 窗口）
  ↓ outBuf 恒 0~8ms（供=耗=1x，缓冲攒不起来），late 以 ~22/秒（18%）单调累积
发送节拍抖动 → 设备 1.05s 播放缓冲被逐渐抽干
  ↓ 设备进入追赶模式：2 秒内发 657 条重传请求（n=1），seq 从「当前−23」一路递增
     冲到服务端尚未发送的位置（+763 ~ +25110）—— 656/657 条要的是"未来包"
服务端物理上无法补发还没产生的包 → 补发 0 命中 → 哑音数秒 → 设备自愈
```

**与「重传缓冲」的关系**：v4.10.6 把 backlog 128→2048（含 512~8192 档位可配）**不是这个问题的解**——
设备要的包不在过去，而在未来，缓冲开多大都无差别。该改动对「真实小丢包」（4~8 条、同 seq 重试）
仍有效，保留无害，但不要把它当根因修复。

**真正的修复**：投递侧开局批量灌入（`ad294ae2`：换代后 bulk 灌 6s 到接收侧 inQueue），
使接收侧长期持有 jitter buffer，节拍抖动失去来源。消费者端 prefill（`acb1aece`）方向修正后保留
（首填预算独立 300ms + `hasInFlight` 门控，避免空载首块被拖 2s）。

## 1. 误判时间线（五个假说的生灭——复盘最有价值的部分）

| # | 假说 | 依据 | 怎么被推翻/纠正 | 教训 |
|---|------|------|----------------|------|
| A | 切歌 2.25s 垫片是 bug | 统计 8/8 换歌后都有 ~2250ms 静默 | 用户拍板：是 AP↔Sendspin 协议对齐垫片，设计如此 | 「每次都出现的延迟」不等于 bug，先问设计意图 |
| B | WiFi 空口丢 240 连续包 + 重传缓冲 128 太小 | 抓到 657 条重传请求，按 352 samples/包折算 ≈1.9s 音频 | 修 2048 热补丁后**真机仍失声**（02:29 再爆） | 修复无效 = 假说错误的最硬证据，必须回头重查 |
| C | seq 空间错位 / 孤儿会话 | 服务端 RTP seq=31965 vs 设备请求 7187 | 环形 pcap 分钟级对账：请求 seq 大多**落在本分钟 RTP 区间内**（02:29 是 657/657）——是我拿"抓包时刻的 seq"去比"5 分钟前的请求" | 对账必须在**同一时间窗**内做，跨窗比对会造出错位假象 |
| D | 「未来包」定性 | 秒级对账：656/657 条请求 seq **大于**服务端爆发结束时刻已发 seq | 成立。设备在追赶，服务端物理无法满足 | 决定性一步是 **delta = reqSeq − sentSeq** 的秒级计算 |
| E | （真根因）投递侧 1x 钳制 | 设备为什么追赶？→ 桥 tick 里 `late` 单调涨到 7000+、`queueMs` 恒 0~8ms、`silenceChunks=0` | 读代码：`late` 的语义就是「producer 阻塞越过 sendAt」；投递窗口/tick 设计使供=耗=1x | 症状（设备请求未来包）要向上游追「为什么它没收到」，一直追到自己代码的节拍设计 |

**观测代码自身的坑（差点造成二次误判）**：v4.10.6 新增的 `lossWinMiss` 只被重置、**从未被累加**，
日志恒显 `miss=0`。真实命中率要从 `totalMiss` 增量反推（增量=请求次数 ⇒ 零命中）。
→ **新加的观测指标，第一次真实事件时必须人工核对它"会动"**。

## 2. 抓包工具箱（全部在 240 实战验证过）

### 2.1 探针三件套（240 `/tmp/e*.sh`，只读不进仓库）

| 脚本 | 作用 | 判定价值 |
|------|------|---------|
| `e3_lossreq_live.sh` | 实时抓设备→服务端 UDP 重传请求，CST 毫秒精度，格式 `时间 seqhex nhex` | **P0**：唯一能直接看见设备侧的信号 |
| `e1_silence_watch.sh` | 亚秒级桥 tick 采样（state/queueMs/late/dropped，CST） | 与失声时刻对齐 |
| `e2_lossprobe.sh` | 1s 级 ICMP 探活 | **伪证**（见 §3.1），只作参考 |

### 2.2 环形 pcap 姿势

```sh
tcpdump -i eno1-ovs -n -s 96 -C 10 -W 24 -w /tmp/pcap/mf.pcap \
  '(udp and host 192.168.10.30) or (tcp port 4515)'
```

- `-s 96` 只留头部，24×10MB 能覆盖 ~3.5 小时（125 包/s 时）。
- 双向抓（`host` 不写方向）：重传请求（入）和 RTP（出）都要。
- ⚠️ 用 `-i any` 会产生 **SLL2** 链路（见 2.3）；用真实网卡名（如 `eno1-ovs`）则是标准 Ethernet。

### 2.2.1 必抓方向：设备 → 服务端 control 端口（重传请求）★

**这是整套方法论的第一原则，单独列出来。** 只抓「我们发出去的 RTP」永远看到完美曲线
（125 包/秒、seq 连续、pcap 速率无塌陷），据此得出「服务端没问题」是早期误判的技术根源。
**设备主动发回的重传请求，是唯一能直接证明「设备侧真的丢包了」的证据**——ICMP、
pcap 速率、seqHole 三者都无法否定它（见 §3 伪证清单）。

```sh
# ① 精确：RAOP 重传请求的 type 字节 = 0x55 | 0x80 = 0xd5（UDP 载荷第 2 字节）
tcpdump -i eno1-ovs -n -s 96 -w /tmp/pcap/req.pcap 'udp and src host <HiVi-IP> and udp[1] = 0xd5'

# ② 兜底：不确定 type 就先按来源全抓，事后用 §2.3 的脚本分类
tcpdump -i eno1-ovs -n -s 96 -w /tmp/pcap/req.pcap 'udp and src host <HiVi-IP>'
```

- 先确认设备 IP 与我们的 control 端口：`avahi-browse -rt _raop._tcp` / `ss -unp | grep node`。
  **设备 IP 会变（曾从 .30 漂到别处），不要硬编码旧值**；HiVi 侧源端口固定 49152。
- 载荷格式与解析同 §2.3；`n` 实测恒 = 1（16 位 bitmap 全 0）⇒ **一条请求 = 一个包**，
  所以聚合行里的 `req=N` 就是真实请求包数。

**三列判读（2026-10-31 补充，最容易读错的地方）**

| 现象 | 含义 | 结论方向 |
|------|------|---------|
| `miss = 0` | 请求的包全部命中 backlog 并补发 | 缓冲够；只要设备还有余粮就不会断声 |
| `miss > 0` 且 `future < miss` | 有包「比缓冲 tail 更老」或查不到 | 缓冲深度不足 / 键域错位 —— 才是「调大缓冲」能解决的 |
| `miss == future`（**逐行完全相等**） | 全部请求指向「比已发送位置更晚」的 seq | **不是缓冲问题**：设备已经饿到索要未来的包，矛头转向「设备保持深度 vs 空口空洞」 |

- 实例（2026-10-31 13:21:50）：8 条聚合行，`totalMiss` 0→635、`miss==future` 逐行相等；
  同一时刻 tick 却是 `inQueueMs=2700 / late=6 / droppedFrames=0 / deltaUs` 稳定。
  ⇒ 一句话否掉「重传缓冲不足」，把根因锁定为「设备保持深度 1.0s < 空口空洞 1.92s」。
- **陷阱**：`seq0=` 是聚合窗口的**陈旧字段**（13:17:55 与 13:21:50 两次都打 `seq0=35888`，
  明显没重置），不要拿它判断请求范围；只信 `seq1`（当前请求）与 `cur`（已发送位置）。

### 2.3 python 解析脚本（struct 手解，链路类型自适应）

```python
link = struct.unpack('<I', d[20:24])[0]
hl = {1: 14, 113: 16, 276: 20}.get(link, 14)   # Ethernet / SLL / SLL2
# RTP 音频:   pay[0]==0x80 and (pay[1]&0x7f)==0x60 ; seq = pay[2]<<8|pay[3]
# 重传请求:   pay[0]==0x80 and (pay[1]&0x7f)==0x55 and len>=8
#             格式 12 字节: 80 d5 00 01 <seq:2> <n:2> 00 00 00 00
#             seq = pay[4]<<8|pay[5], n = pay[6]<<8|pay[7]   (实测 n 恒 =1)
```

- `readUInt16BE(4)/readUInt16BE(6)`（raop.ts onLoss）与 pcap 实测一致，解析无偏移。
- 判「多会话」：按 (sport,dport) 分组统计；判「严格递增」：`all(seq[i]<=seq[i+1])`。

### 2.4 两级对账（核心方法论）

**分钟级粗筛**：按本地时间分钟聚合，输出 `rtp n=.. seq[min..max]` 与 `req n=.. seq[min..max]`，
算「请求 seq 落在同分钟 RTP 区间的比例」。→ 用于快速排除/确认"seq 大范围错位"类假说（推翻了 C）。

**秒级定性（决定性）**：把请求按「间隔 >2s 归新爆发」分组（burst），对每个 burst 计算：

```
sentSeqAtStart/End = 服务端在爆发开始/结束时刻已发的最大 RTP seq
delta0 = min(reqSeq) − sentSeqAtStart     # 首个请求相对当前位置
delta1 = max(reqSeq) − sentSeqAtEnd       # 最后一个请求相对当前位置（正 = 未来包）
future% = reqSeq > sentSeqAtEnd 的占比    # 实测 656/657 —— 定性"追赶"的铁证
```

> 三个数字（`delta0≈−23`、`delta1=+763~+25110`、`future%=656/657`）就是「设备在要还没被产生的包」
> 的全部证据，也是把根因从"网络丢包"扭向"服务端供料"的转折点。

## 3. 伪证陷阱清单（每条都真踩过）

1. **ICMP ping 0% 丢包**：与 RTP 不同路径，且是服务端出口口径——设备收不到它照样报 0，**结构上恒为 0**。
2. **pcap 里 RTP 速率正常 / 无 seq 空洞**：只证明服务端发了；丢在采集点**之后**（WiFi 空口）看不见。
3. **「我这段窗口没看到」≠「不存在」**：QA 曾用 00:2x~00:3x 窗口的 `ctrl_in=0` 否证网络丢包，而三次爆发在 23:29~23:37——整个错过。另外 `ctrl_in` 是 RTSP 控制面，重传请求走 RAOP UDP 通道，两者正交。
4. **环形 pcap 文件边界有 0.5~1.5s 观测盲区**，会造伪事件；**mtime 顺序 ≠ 时间顺序**（回绕点乱序），多文件合并前必须按首包时间排序。
5. **时间口径**：`docker logs -t` 打 **UTC**；`tcpdump -r`/`date` 打**本地 CST(UTC+8)**。混用会得出完全相反的结论（曾据此误判"看门狗误杀"）。
6. **日志行内没有时间字段就不能按时间 grep**：桥 tick 的 `ev:tick` 行本身无时间戳，取时间要用 `docker logs -t` 的前缀。
7. **观测代码自己的 bug 会制造假象**：`lossWinMiss` 从未累加 → `miss=0` 恒假象。新指标首次真实事件必须验证"会动"。
8. **计数口径要对齐**：`req` 是请求**次数**、`requested` 是请求**包数**（n=1 时相等，n>1 时差 n 倍）——先确认 n 的实测值再推 miss 率（本次 n 恒为 1，是从 pcap 逐条验证的）。
9. `cmd | tail; echo $?` 拿的是 tail 的退出码 → `set -o pipefail`；日志 grep 加 `-a`。

## 4. 关键数字速查（下次直接对号）

| 指标 | 健康值 | 病态指纹 | 含义 |
|------|--------|---------|------|
| RTP 包率 | 125/s（352 samples @44.1k） | — | 节拍基准 |
| `late`（桥 tick） | 0~2 | **~22/s（18%），歌内单调涨** | producer 阻塞越过 sendAt = 投递侧钳 1x 的指纹 |
| `queueMs`（tick） | 深水位（bulk 后 ≈6000） | **恒 0~8ms** | outBuf 供=耗，jitter buffer 不存在 |
| `maxQueueMs` | — | — | **历史峰值**，不是配置上限 |
| `inQueueMs`（ad294ae2 新增） | ≈6000（bulk 生效） | ≈0 | 分辨「上游没给」vs「resample 没转」 |
| `future=`（raop-loss） | — | 656/657 | 设备在要服务端还没产生的包 = 追赶模式 |
| `delta0 / delta1` | ≈−23 / <0 | −23 / **+763~+25110** | 首包正常、尾包超前 |
| `silenceChunks` | 0 | 0 也可能是病 | waitDataMs(1000) 内等到料就不计——**=0 不代表没欠料** |
| 重传爆发 | — | 657 条/次、n=1、~2s | 恒定数字说明是设备固定行为（追赶），不是随机丢包 |
| 设备缓冲 | leadUs=1050000 | — | 抽干即哑音 |
| 桥断连红线 | — | inQueue/backlog > 8s | `BRIDGE_QUEUE_HARD_CAP_MS` / `BRIDGE_RECEIVE_OVERFLOW_MS`，批量灌入必须 ≤6s 分片 |
