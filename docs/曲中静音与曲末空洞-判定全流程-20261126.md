# 曲中静音与曲末空洞：判定全流程 ★★ 2026-11-26

> 本文记录 2026-11-26 这一轮「AirPlay 每首必现静音」的**完整判定流程**：观测口径 → 采集方法 → 五个独立缺陷逐一判定 → 修复 → 验收判据 → 误判清单。
> 结论已分别落入三份权威方案文档（airplay / sendspin / group）的 `v4.15.9` 与 `v4.15.10` 增补段；**本文保留「怎么判出来的」**，权威语义以三份文档为准。
> 所有时间戳一律 **CST（UTC+8）**，与用户听感对齐。

---

## 0. 一分钟结论

同一个听感（每首都有静音）背后是**五个互相独立的缺陷**，必须分开判、分开修：

| 编号 | 缺陷 | 代码位置 | 听感位置 | 状态 |
|---|---|---|---|---|
| **D1** | 曲末续静音按固定 lookahead 灌满，实灌 34.8s | `streamEngine` 曲末排空段 | 曲末长静音（单桥 8s / 群组 30s） | 方案 A 已修 |
| **D2** | 泵进程内同步 `stat` 冻住事件循环 0.6~3.5s | `localSourceProbe.ts` / `resolveAudio.ts` ★0 | 曲中 1~5s 空洞 | v4.15.9 已修 |
| **D3** | 断帧 2s 即判「传输死亡」→ FLUSH + 重连 | `bridgeServer.checkStalls` → `bridgeSession.onLinkStall` | 把 0.2s 抖动放大成 2~5s 真空 | v4.15.9 已修 |
| **D4** | 负缓存把挂载瞬时抖动写成「5 分钟不可播」 | `resolveAudio` 负缓存分支 | 在盘上的歌被判死 | v4.15.9 已修 |
| **D5** | 「预取已就绪 → 跳过曲末排空」不校验预取是否真的接住曲末 | `streamEngine` 曲末判据 | 曲末 6.5s 全空 + FLUSH + 118 次 realign | v4.15.10 已修 |

**判定的分界线**：D1 是「我们主动灌静音」，D2/D3 是「泵被冻住导致断粮」，D5 是「泵提前收工」。三者症状都是静音，但日志指纹完全不同 —— 见 §6 判据表。

## 1. 观测口径（先定口径，再谈数据）

这一轮最大的时间浪费来自口径不清，固化成四条：

### 1.1 时间口径

| 来源 | 打印的时区 | 说明 |
|---|---|---|
| `docker logs -t` | **UTC** | 必须 +8 才能和用户听感对上 |
| 用户反馈 / 本文 / 三份权威文档 | **CST** | 唯一对外口径 |
| `tcpdump -r` | **本地 CST** | 与 `docker logs -t` 混用会得出相反结论 |
| `docker logs --since <裸时间>` | **容器本地时区（CST）** | ⚠️ 坑，见下 |
| `docker logs --since <时间>Z` | **UTC** | 唯一无歧义写法 |

**实测（2026-11-26 22:37 CST）**：

```
$ docker logs -t musicflow --since 2026-11-26T14:34:35Z   | head -1 → 2026-11-26T14:34:35.384  ✅
$ docker logs -t musicflow --since 2026-11-26T14:34:35    | head -1 → 2026-11-26T06:34:35.031  ❌ 差 8 小时
```

**教训**：裸时间被当成 CST（14:34 CST = 06:34 UTC）。第一次分段统计因此把「修复前 7 小时」和「修复后」混算，得出「stall=0」的错误结论。**分段统计一律带 `Z`**。

### 1.2 水位口径（四个数字不能混用）

| 字段 | 含义 | 典型值 | 用途 |
|---|---|---|---|
| `queueMs` | 设备侧队列（HiVi 上就是「收到即播」的余量） | **p50=204 / p90=214**（上限 1475） | 设备抗抖动能力 |
| `inQueueMs` | 已发到设备、未播（含设备内部缓冲） | p50=2575 / p90=2725 | 端到端在途 |
| `backlogMs` | 桥环内待发 | 2500~2650 | 桥侧存量 |
| `deviceLeadMs` | `deltaUs`：设备已收未播 | 实测 3965 峰值 / ～2100 常态 | 方案 A 的 hold 组成项 |

### 1.3 「泵是否被冻住」的唯一硬判据

`bridge-servo` 是**每 2s 无条件一条**的心跳，由泵进程定时器驱动。

> **servo 间隔 > 3s ⇒ 泵进程被阻塞过**（正常为 2.0s + 250ms 投递定时器相位 ≈ 2.25s）。

不要用 `ring-diag`、`late`、`droppedFrames` 判冻结，它们在有数据时也会变（见 §7 误判 2）。

## 3. D1 判定：曲末续静音（「我们主动灌的」）

### 3.1 症状

曲末出现明显静音，**与歌长无关**（185s 与 259s 的歌都是同一段长度）。

### 3.2 判据

`bridge-drain-fill` 的 `drainMs` 是一个**恒定值**，而不是「距歌曲结束还剩多少」：

| 观测值 | 次数 | 结论 |
|---|---|---|
| `34827 / 34833 / 34834 / 34896 / 34905 / 34934 / 34935 / 34995 / 35002 ms` | 多次 | 恒 ≈34.8s |
| 单桥：被 `BRIDGE_END_DRAIN_SAFE_MAX_MS = 8000` 钳成 **8000ms**（5 次） | 5 | 单桥静音 8s |
| 群组：`pureBridge=false` 不钳制 ⇒ **30000ms / chunks=1200**（7 次） | 7 | 群组静音 30s |

群组 30s 实灌样本（**当日累计**，CST）：`01:36 / 15:23 / 15:33 / 15:44 / 16:07 / 19:00 / 19:07`。
注意这些都在 §2.4 的 S1 窗口之外，所以 S1 那一行只统计到 2 次单桥 8000ms。

### 3.3 根因

`PUMP_LOOKAHEAD_DEFAULT_US` 从 6s 抬到 30s（对齐 MA `_PRODUCER_BUFFER_LIMIT_US`）之后：

```
rawDrainMs = (cursorUs − nowUs() − ANCHOR_SAFE_LEAD_US) / 1000   →  恒 ≈ 34.8s
```

lookahead 越大，`cursorUs − nowUs()` 越大，排空量就越大 —— 这是个**结构性**后果，不是配置错。

### 3.4 修法与验收（方案 A：桥水位透传）

泵侧不再自己猜「要补多少静音」，改为问桥「你还能撑多久」：

```
holdMs   = max over bridges( backlogMs + deviceLeadMs ) 的组内最薄值
silenceNeed = max(0, min(drainMs, PREFILL_MAX) − max(0, contentMs − max(MARGIN_2500, holdMs))) / speed
```

实测：`bridge-drain-fill-skip reason=covered bridges=1 holdMs=4787 remainMs=30109 drainMs=8000` —— **一帧未灌**。
`holdMs` 实测区间 4588~4787，与 `backlogMs(2500~2650) + deviceLeadMs` 同量级。

⚠️ 单机与群组用**同一个公式**，不允许出现「单机 8s、群组 30s」的分叉。

## 4. D2 + D3 判定：曲中空洞（本轮主案）

### 4.1 症状

用户三次收窄描述：「播放过程中」→「同一首歌里面」→「春三月这首中间」。**曲中、每首必现**。

### 4.2 判据一：慢解析与冻结时长一一对应

| 时刻(CST) | 解析日志 | `[loop-lag]` | 泵日志空档 | 后果 |
|---|---|---|---|---|
| 21:50:29 | `ensure-ok ms=3510` | `lagMs=3510` | **3.26s** | 桥 `stall: no frame for 2000ms` |
| 21:54:19 | `preferred-swap ms=2164` | `lagMs=2618` | 2.17s | 桥环吸收，无 stall |
| 22:01:28 | `ensure ms=636` | `lagMs=636` | 0.64s | 无感 |

`loop-lag` 累计 6 次：`2618 / 1337 / 636 / 922 / 1312 / 1272 ms`。

### 4.3 判据二：不是死循环，是 I/O 阻塞

CPU 采样：冻结期间 `utime` 在 0.5s 窗口内全程 <0.15s ⇒ 进程在等，不在算。

### 4.4 判据三：放大器是设备缓冲只有 0.2s

`queueMs` 分布（近 20 分钟，597 个 tick）：**min 192 / p50 204 / p90 214 / max 1484**。
HiVi（2017 MUZO 固件）收到即播、不吃 RTP 时间戳 ⇒ 设备抗抖动能力 ≈0.2s，而我们的判死阈值是 2s —— **结构性必然误杀**。

### 4.5 根因链

```
曲末 next-prefetch → resolvePlayableRow(next) → resolvePreferredSong → 逐候选 probeLocalSourceOk
  ↓ 内部 fs.existsSync（同步 stat），15 万首跨挂载点冷 stat 0.6~3.5s（最坏 14.4s）
泵是单线程 ⇒ 250ms 投递定时器与 bridge-servo 的 2s tick 一起饿死
  ↓ 桥侧 checkStalls：2s 无帧 ⇒ onLinkStall() ⇒ flush() + 清 aligner/anchors
  ↓ producer 结束 ⇒ scheduleRaopReconnect("stream ended") ⇒ 2~5s 真静音
```

### 4.6 MA 对照（为什么 MA 没这么严重）

| 维度 | MA | 我们（修复前） |
|---|---|---|
| 音频泵职责 | `_on_audio_chunk` 纯回调，不做解析；PCM 走独立 CLI 进程 stdin | 泵进程内跑选源/探测/裁决 |
| 判死条件 | 只有 CLI 进程**真的退出**才 `transport_lost` | 2s 没帧就断流重连 |
| 设备缓冲期望 | `MAX_DEVICE_BUFFER_SECONDS = 8.0` | 无（HiVi 实际 0.2s） |

结论：**抄「职责分离 + 不轻易判死」，不抄「换 CLI 进程」**（换进程会丢掉 PCM 旁路、成员延迟补偿、混音组、AP2/HAP）。

### 4.7 修法与验收

| 改动 | 内容 |
|---|---|
| `utils/localSourceProbe.ts` | 本地 `l:` 分支 `fs.existsSync` → `await fsp.stat`（libuv 线程池） |
| `services/source/resolveAudio.ts` ★0 | `existsSync` → `await statAsync`，语义不变 |
| `airplay/rates.ts` | 新增 `BRIDGE_STALL_FATAL_MS = 15_000`，`NO_FRAME_MS = 2_000` 降级为告警 |
| `airplay/bridgeServer.ts` | `checkStalls` 两级化，`onStall({fatal, silentMs})`；收帧复位 |
| `airplay/bridgeSession.ts` | 非致命时**什么都不做**：不 flush、不清锚点、不 abort |

**最硬的一条验收证据**：

| | 修复前 | 修复后 |
|---|---|---|
| 慢解析 | `[resolve] ms=3510` | `[resolve] ms=13661`（**更慢**） |
| servo 最大间隔 | **5311ms** | **4002ms** |

解析慢了 4 倍，泵却没被冻住 —— 这才是「异步化生效」的证明。看 `ms=` 变小是错误判据（缓存命中也会让它变小）。

## 5. D5 判定：曲末空洞（「泵提前收工」）

### 5.1 症状

用户报「O' Holiday 曲末出现空洞」。查库确认 `68e89e48-e4c9-4fbf-b2f7-6b7f09acc97d = O' Holiday / Ellem / 185s / type=web`。

### 5.2 ms 级时间线（CST）

| 时刻 | 事件 | 间隔 |
|---|---|---|
| 22:27:22.462 | `曲末排空跳过:下一首预取已就绪` ← 泵立刻收工 | — |
| 22:27:26.488 | `auto-advance` | **+4.026s** |
| 22:27:28.992 | `[cast] 起点 idx=3186` | +2.504s |
| 22:27:29.014 | `起播 protocol=raop warm=true`（cast 21ms） | +0.022s |
| 22:27:30.149 | `ev:"stale" reason=seek staleFrames=153777`（≈3.49s 音频） | +1.135s |
| 22:27:30.151 | `RAOP FLUSH` | |
| 22:27:32.99 起 20ms 内 | `realigned` ×118，`drift` 从 −2936.3ms 追到 0 | |

**净空档 22:27:22.462 → 22:27:29.014 = 6.552s**。设备侧当时 hold ≈4.7s，故可闻空洞 ≈1.8s；FLUSH 又把已排队内容清掉，实际扩展到 ~3s。

### 5.3 判据

「预取已就绪 ⇒ 跳过排空」这条捷径的成立前提是**预取帧真的接住曲末**。实测：

```
预取帧 startTsUs = 474125916164
曲末游标         = 474098241164
差               = 27,675,000us = 27.675s      ← 接不住
```

同时判据里写了 `!this.prefetch` 才置 `continuity=false`，于是起播走了完整 cast 路径 → 6.5s 真空 + FLUSH + 118 次 realign。

### 5.4 对照：健康路径长什么样（22:38，修复后）

| 时刻 | 事件 |
|---|---|
| 22:38:31.364 | `曲末排空:纯桥组,排空量按桥投递上界钳制 34827ms → 8000ms` |
| 22:38:39.372 | `bridge-drain-fill-skip reason=covered holdMs=4786 remainMs=30041` |
| 22:38:44.132 | `auto-advance`（设备正好播完缓冲，+4.76s ≈ holdMs） |
| 22:38:44.157 | `起播 protocol=raop warm=true`，`cast 完成 22ms` |

无 stale、无 FLUSH、无 realign 风暴 —— 设备一直在播，听感连续。

### 5.5 修法

```ts
// streamEngine.ts
export const BRIDGE_PREFETCH_BOUNDARY_TOLERANCE_US = 1_500_000;   // 1.5s
...
const canSkipDrain = this.prefetch != null
  && Math.abs(prefetchBoundaryGapUs) <= BRIDGE_PREFETCH_BOUNDARY_TOLERANCE_US;
// 不满足则落回已验证的 covered 排空路径，并告警：
// sendspin 曲末预取未接住曲末:gap=27675ms 容差=1500ms ⇒ 不跳过排空
```

取值依据：正常接续时预取帧与曲末游标的差在 100ms 量级；1.5s 留 15 倍余量，又远小于一次真实切歌的空档。

## 6. 验收判据（2026-11-26 定稿，十条硬判据）

修复后跑一首完整的歌，按下表判，**任一不满足即回退**。第 6~10 条是两级 stall 与
方案 B（预取整链删除）落地后新增的；原五条按新语义重写，旧口径已作废。

| # | 判据 | 命令 | 通过线 |
|---|---|---|---|
| 1 | 无帧级断帧（降级为告警，不判死） | `grep -ac '\[bridge-server\] stall'` | 允许出现，**仅告警**；`BRIDGE_STALL_NO_FRAME_MS=2000` 不再断流 |
| 2 | 无致命断流 | `grep -ac 'link stall'` | **0**（`BRIDGE_STALL_FATAL_MS=15000` 才允许重锚） |
| 3 | FLUSH 只能冷启动 / 用户操作触发 | `grep -a 'RAOP FLUSH'` 配合 `warm=false`、`seek/stop` 上下文 | 切歌自触发 **0**；冷启动起播 + 首投 seek 各一次可解释（上界 = `warm=false` 数 + 冷启动 reason 的 seek 数） |
| 4 | 泵未被冻住 | §2.3 servo 最大间隔 | **≤3.0s**（真机实测 2.00s 中位 / 2.25s max） |
| 5 | 曲末静音不再被主动灌 | `grep -a 'bridge-drain-fill-skip' \| grep -avc covered` | **0**（covered 排空是设计内） |
| 6 | 曲末接续零间隙 | `endUs` 对照新曲 `timeline anchored: base=` | **Δ=0us**；非零即空洞 |
| 7 | 首投 seek 只允许冷启动 | `grep -a 'bridge-start-seek'` | 每次容器生命周期 **≤1** 次，且 reason=`new-session-first-delivery` |
| 8 | 预取三链恒 0 | `grep -acE 'next-prefetch\|bridge-prefetch\|bridge-track-keep'` | **0**（v4.15.11 整链删除，复活即回归） |
| 9 | 灌静音计数为 0 | tick 的 `silenceChunks` | **0** |
| 10 | 跳过排空捷径恒 0 | `grep -ac '曲末排空跳过:下一首预取已就绪'` | **0**（D5 曲末空洞直接根因，旧版有 11 次） |

辅助观察（不作硬判据）：`[resolve] ms=` 可以很大（10s+）而系统正常——`DrainPreheat`
提前 27s 把下一首解析好，`ms=3458` 走预热子进程，不冻泵；`realigned` 只应在 seek
后出现一次爆发；`[DrainPreheat] song=` 是**下一首**，不能拿它统计当前曲切换。

**CI 固化**：以上判据已实现为 `backend/scripts/baseline/playback_side_guard.py`，
短跑（`playback-baseline.yml`）与长跑（`playback-baseline-longrun.yml`）共用同一脚本，
L1 `selftest.py` 用正反样本钉死阈值；改动判据必须同步改脚本、selftest 与本节。

## 7. 误判清单（本轮踩过的四个坑）

| # | 误判 | 当时的依据 | 为什么错 | 教训 |
|---|---|---|---|---|
| 1 | 对 pcap 算 PCM 能量判断是否静音 | pcap 里是 RTP 包 | RAOP 是 **AES 加密**，算出来全是噪声 | 只能从**出口明文**取证（PCM 探针） |
| 2 | `ring-diag n=0 buffered=0` + `inQMs=2625` 判为「缺料」 | 环里没数据 | 设备队列里有 2.6s，是**健康态** | `n=0` 只说明环被抽干，不代表没在播 |
| 3 | 探针 `step` 粘滞，把后续卡顿归到前一步 | 探针输出顺序 | 探针变量未及时刷新 | 冻结归因要配 CPU 采样交叉验证 |
| 4 | 用裸时间做 `--since` 分段 | `--since 14:34:35` | 被解释成 CST ⇒ 实际取到 06:34Z，把修复前后混算 | **一律带 `Z`**，见 §1.1 |
| 5 | 假设「群组是干净的，只有单机有问题」 | 单机日志 | 群组 `pureBridge=false` 不钳制 ⇒ 灌 **30000ms**，比单机 8000ms 更狠 | 同一症状必须**两端分别取证** |
