# 桥投递窗口水位死锁 —— 曲中失声的总根因与修复

- 日期：2026-10-31
- 版本：v4.10.7（修复 `sendspin/server.ts` `deliverBridgeWindow`）
- 设备：HiVi H5MKII（MUZO 固件，`00226CFFA0C0`），服务端 240 容器
- 关联文档：`曲中失声-抓包取证方法论与复盘-2026-10-31.md`、`sendspin-权威方案文档.md`

## 一、现象

曲中（**不是歌开头、也不是切歌点**）突然无声数秒后自愈，反复发作。用户多次独立报告：14:38（约 15s）、14:47（约 5s）、15:25 / 15:26（约 15s）。

服务端观测指标在多数时段「全绿」：`droppedFrames=0`、`silenceChunks=0`、`realigned=0`、`deltaUs` 稳定在 2.556s。**唯一持续异常的是 `late` 单调递增、永不回落。**

## 二、证据链

### 2.1 设备请求方向（pcap，`/tmp/mfpc/mf.pcap02`，14:41–14:52）

| 类型 | BPF（注意载荷偏移） | 数量 |
|---|---|---|
| timing 请求（设备→我们） | `udp[9]=0xd2` | 231（每 3.0s 一个） |
| 重传请求（设备→我们） | `udp[9]=0xd5` | 1975（与日志 `total=1975 totalMiss=1968` 完全吻合） |

> ⚠️ **BPF 偏移易错点**：UDP 头 8 字节之后才是 RTP 载荷。RTP 第 2 字节是 `udp[9]`，**不是 `udp[1]`**。用 `udp[1]` 会得到 0 条命中的假阴性（本次排查中真实踩到）。

14:47 的请求按秒分布：

```
14:45:30 ~ 14:47:10   零请求（100 秒，设备收得很顺）
14:47:10  req=280
14:47:11  req=355
14:47:12  req=22
```

**657 包 × 8ms ≈ 5.26 秒**，与用户听到的失声时长吻合。

### 2.2 发送方向（同一 pcap，按秒）

```
14:46:50 ~ 14:47:40  每秒 126~130 包，100 秒零中断
```

**我们一刻没停。** 所以不是供料不足、不是发送节拍断裂、不是空口连续丢包。

### 2.3 补发结果（`[raop-loss]`）

```
req=106 miss=106 future=106
req=105 miss=105 future=105
req=69  miss=69  future=69
```

`miss` 与 `future` **逐行完全相等**。

- `miss` 定义（`raop.ts` `onLoss`）：`lossWinMiss += max(0, n - 本轮实际补发数)`
- `future` 判定：`ahead = (idx - this.seq) & 0xffff; if (ahead !== 0 && ahead < 0x8000) futureThis++`

即：**设备索要的包全部落在「我们已发位置之前不到」的未来区间，一个都补不了。**

### 2.4 窗口与内容的位置关系（`[sendspin] bridge-window`）

```
contentFrontierVsNowUs = 14950079   (内容前沿在 now + 14.95s)
tailVsLoUs             = 12950259
tailVsHiUs             = 11950259   (内容在窗口上界之上 11.95s)
queueMs                = 0          (桥 PCM 队列空)
```

同一时刻窗口是 `[now+2s, now+3s]`。

**窗口内根本没有内容可以投。**

### 2.5 断粮的直接后果（tick 遥测，15:26）

```
15:26:34  inQ=2750  late=12  tA=1852   sil=0
15:26:42  inQ=1750  late=12  tA=9851   sil=0
15:26:44  inQ=0     late=17  tA=11851  sil=0
15:26:46  inQ=0     late=37  tA=13851  sil=1   ← 开始注入静音
```

`inQueueMs` 从 2750 直接归零且重连后不再恢复；`late` 以 250/s 暴涨（每包都迟到追发）。

## 三、根因

### 3.1 直接原因：投递窗口上界与水位脱钩

`backend/src/services/sendspin/server.ts` `deliverBridgeWindow`（修复前）：

```ts
const leadCapUs = lo + BigInt(BRIDGE_BACKFILL_MAX_US);   // = lo + 6s
const followUs = last + tickUs;
const hiEff = clamp(max(hi, followUs), ≤ leadCapUs);
for (const e of ring) {
  if (e.tsUs < lo)   { last = e.tsUs; continue; }   // 丢弃并推水位
  if (e.tsUs > hiEff) break;                        // 顺延
  ...
}
```

`leadCapUs` 只与 `lo` 有关，**与水位 `last` 无关**。而 `bulkBackfillBridge` 的上限恰好也是 6s，一旦它把水位推到 `lo + 6s`：

- 之后每个新帧 `ts` 都恒略高于 `lo + 6s`；
- `hiEff` 被死死钳在 `lo + 6s`；
- ⇒ **每次 tick 第一个候选帧就 `ts > hiEff` 直接 break，一帧都投不出去。**

于是系统退化为：**每 6 秒一次 bulk 灌 6 秒 + raop 追发硬撑**。歌开头 bulk 刚建立对齐时暂时正常，随后逐秒恶化 —— 这精确解释了「为什么总是曲中卡，歌开头不卡」。

### 3.2 次生原因：基准平移后水位越界

`shift`（`bridgeAnchorShiftUs`）会在两类事件后变化：成员延迟 PUT、watchdog 重连。`lo/hi` 随 `shift` 整体平移。

`Fix D.1` 只让「shift 变更那一拍退回严格 `hi`」，但没有处理**旧水位已经越到新窗口之外**的情况。一旦 `last > hiEff`，后续帧全部 break，形成与 3.1 同款的永久死锁 —— 且不会自愈，直到下次换代。

### 3.3 为什么「加深保持深度」治不了

`MF_BRIDGE_RAOP_HOLD_MS` 从 1000 提到 2500 只是把设备饿肚子的时间点往后推。**它加厚的是设备侧缓冲，而病灶在服务端投递侧**：窗口投不出 → 桥队列恒空 → 发出去的内容没有余量。所以听觉上「好了一阵又复发」。

## 四、修复（v4.10.7）

`deliverBridgeWindow` 两处：

1. **上界改为「当前水位 + 队列余量」**，与 `bulkBackfillCapUs` 同口径：

```ts
const queueBudgetMs = Math.max(
  1000,
  BRIDGE_QUEUE_HARD_CAP_MS - this.bridgeQueuedMs(b) - BRIDGE_BULK_QUEUE_MARGIN_MS,
);
const leadCapUs = last + BigInt(queueBudgetMs) * 1000n;
```

水位推进从此受「桥队列余量」约束，而不是一个与水位无关的常量；同时仍不会顶穿 `BRIDGE_QUEUE_HARD_CAP_MS`，不会引发 overflow 断连。

2. **基准平移且水位越界时复位**：

```ts
if (shiftChanged && last !== 0n && last > hiEff) {
  last = 0n;
  this.bridgeWatermarks.delete(deviceId);
}
```

回到「本代次尚未投递」语义，由下一 tick 从当前窗口重算。`ep !== epoch` 过滤保证不会重投旧代次帧。

## 六、未闭环

1. **设备 NTP 心跳停摆**（`timingAgeMs` 单调涨至 15~20s）是独立故障面，本修复不覆盖。它由 watchdog 以 15s 判据兜底，代价是 15s 无声。历史共触发 8 次。
2. `future` 包的 burst 追发（`sendAt` 门禁止抢跑）未实施 —— 待本修复实测后判断是否仍需要。
3. `late` 的 50ms 恒定欠账（`forceNow` 的 `floorLeadUs = lUs + safetyUs` 恰好让 `sendAt(0) = now`，未留 plan→stream 的启动延迟余量）未处理。
4. `v4.10.6` 的 `security` CI job 为 failure（`build-and-push` / `Version Guard` / `contract-gate` 均 success），需单独核查。

## 七、S1「下一首预解码」真机验收补记（2026-11-01）

本节补充与「投递窗口水位」同链路的三个新根因 —— 它们都只在**曲边界**出现，且都被 240 真机日志直接证伪/证实。

### 7.1 曲边界 `stop → FLUSH`：S1/S2 双双失效的真凶

`playCore` / `playGroupCore` 起播时用 `g.canKeepStream()` 决定走 `clearPlayback()` 还是 `finishPlayback()`。
纯桥组（`ug:__bridge_solo:<dev>`）的 `members.size === 0` ⇒ `canKeepStream()` **恒 false** ⇒ 每次都走
`finishPlayback()` ⇒ 桥收 `BOUNDARY{stop}` ⇒ RAOP FLUSH ⇒ 旧曲尾 + 刚预解的新曲头一起被清。

实测（同一轮）：

```
{"ev":"stale","reason":"stop","staleFrames":250618}     ← 自然边界不该有
{"ev":"track-keep-queue","reason":"track","keptFrames":0}
```

修法：`streamEngine.hasPendingPrefetch(songId)`（与预取采纳判据同源 `bridgeEpochNow()+1 === pf.epochAtStart`）
成立时改走 `clearPlayback()`（只发 `BOUNDARY{track}`，队列由 S2 保留）。修后同一场景：

```
{"ev":"track-keep-queue","reason":"track","keptFrames":217264}
```

（`pump.stop()` 不清预取，故 stop 之后判定仍有效。）

### 7.2 曲末上报位置必须钉到时长

「曲末排空跳过」会在**设备播完之前**就收尾，此时 `group.positionMs` 仍停在起播点（实测 seek 67 s / 时长 76 s
⇒ 恒报 `pos=67`）。`PlaybackTracker` 的 `idle_early`（IDLE 但位置远未到时长）+ seek 冷静期（8 s）叠加后
既不 `advance` 也不 `stalled` —— 真机卡 20 s 后靠 `stall-reinvest` 重投。修法：自然结束
（`endedNaturally && durationMs>0`）时 `group.positionMs = durationMs`；非自然结束（截断/链路死亡）不动。

### 7.3 seek 必须取消「等 PLAYING」乐观窗口

`PlayerController.reportState` 在乐观窗口内会**吞掉**所有非 PLAYING 上报。近曲末 seek（剩余 ≤ 预取长度）
会立刻触发 7.2 的跳过排空，泵在 seek 后 60 ms 收尾、下一拍 `IDLE(pos=时长)` 正好落在窗口里被吞掉，
5 s 到点判 `stalled` ⇒ `stall-reinvest` 从 **0 s 重投**（实测 seek 183 s 被打回 0 s，自动换歌空等 35 s）。

真机原文：

```
[optimistic] 阶段2 起 5s 等 PLAYING 计时
[optimistic] 窗口内忽略 IDLE(等待 PLAYING 确认)
[optimistic] 阶段2 超时(5000ms 未收到 PLAYING)→ stalled
[QueueController][playCurrent] source=stall-reinvest idx=0 …
```

修法：`QueueController.transport` 的 `op === "seek"` 分支在 `markSeekIssued` 之后追加
`endOptimistic(player.playerId)`。seek 后的状态真空由 `seekSettle`（8 s）负责，窗口留着只会制造误判。

### 7.4 验收数字（10 次自然换歌 + 17 次手动 next，240 真机）

| 指标 | 结果 |
| --- | --- |
| 自动换歌 | 10/10；`wait` 1.24 / 4.37 / 4.57 / 10.45 / 4.37 / 4.60 / 4.37 / 4.58 / 4.37 / 4.54 s |

### 7.5 开关现状（2026-11-01 收尾：S1 改为 Web 开关，默认开）

**S1「下一首预解码」的唯一入口是 Web「音频」页的管理员开关**（卡片标题「下一首预解码（S1）」，**默认打开**）；
值落在 sendspin 插件配置 `plugins.config.next_track_prefetch`（`id/name = 'sendspin-renderer'`），
读取口为 `backend/src/services/sendspin/bridgePrefetchConfig.ts` 的 `readBridgePrefetchConfig()`（**缺省 true**，读库异常同样回落 true）。

- 读写在管理端 API：`GET /rest/api/v1/sendspin/bridge-prefetch` → `{ enabled, envOverride }`；
  `PUT` 同路径 body `{ enabled }`，合并写插件 config 后回显同结构；
- 生效：Sendspin 子进程**每次判定直读 plugins 表**（WAL 多进程安全），改完**下一首换歌即生效**，不重启、不打断当前播放；
- 排障总闸仍在：容器 env `MF_BRIDGE_NEXT_TRACK_PREFETCH=0/false/off`（关）/ `1/true/on`（开）**优先于 Web 开关**；
  线上 240 `compose.yaml` 为备份版（无该变量），故实际以 Web 开关为准；
- 关闭语义：S1 关 ⇒ 预取态机完全不启动，边界行为与改造前逐字节一致（单开关整体回退）；
- S2 缺省 ON，回退 `MF_BRIDGE_TRACK_KEEP_QUEUE=0`；
- 部署验证（240，容器 `2026-11-01T04:08:54Z` 重启）：后端 `dist` 含 `bridge-prefetch` 路由；前端产物含
  `settings.bridgePrefetch.*` 与中文语言包键；容器内三态验证 `默认 true / 写 false / 删键 true`（DB 已还原）；
  默认 ON 复验 `s4_drive.py 3 0`：3/3 预取开始、3/3 排空跳过、3/3 采纳，`wait` 4.34 / 4.57 / 4.35 s。
