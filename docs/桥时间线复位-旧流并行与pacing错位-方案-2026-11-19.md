# 桥时间线复位：旧流/新流并行与 pacing 错位（立项）

- 日期：2026-11-19
- 状态：**P1/P2 已实现，待真机回归**；B（skip 复位）暂缓，等 P1/P2 验证通过再议
- 关联：v4.14.11（引入回归）/ v4.14.12（撤回）/ `docs/airplay-权威方案文档.md`

## 1. 现象

240 全屋组（6 成员，HiVi H5MKII = `00226CFFA0C0`，RAOP/AirPlay1）播放中偶发：

- **起播全程不出声**，手动 seek（重建流）立刻恢复；
- `airplay-bridge` tick 的 `state` 仍报 `live`，`inQueueMs` 正常，`lossMiss=0`；
- 同屏 `pacing rebase(lag)` 每秒一条，量级稳定 `+600~650ms`，`RTP 映射不动`。

## 2. 现场数据（2026-11-18 15:54，UTC）

```
15:54:18 timeline-reset reason=warm-reuse-poisoned
15:54:18 forceNow anchor commandedLeadUs=2050000
15:54:18 newgen-skip frames=71703 ms=1626          ← 4.14.11 的改动让它走 skip
15:54:18 realigned insert=0 drop=0 skip=71703
15:54:20 pacing rebase(lag): +614538µs idx=107
15:54:21 pacing rebase(lag): +569426µs idx=25788   ← idx 跳变
15:54:22 pacing rebase(lag): +606008µs idx=240     ← 又跳回
15:54:26 pacing rebase(lag): +646916µs idx=26075
...                                                （每秒一条，持续到 15:56:33 手动 seek）
```

`idx` 在 **107 / 25788 / 240 / 26075** 之间交错 ⇒ 同时存在两套 `streamBridge` 循环，
各自维护自己的 `idx`，都在向同一个 RAOP socket 发包。设备收到两套时间戳（旧循环用
`resetTimeline` 已作废的 `startTs`，新循环用新锚点）⇒ 缓冲被抽空、欠载静默。

## 3. 根因（两条，缺一不可）

### P1 `RaopPlayer.waitUntilUs` 不可中止

```ts
for (;;) {
  const delayUs = Number(targetUs - nowUs());
  if (delayUs <= 0) return;
  await new Promise((r) => setTimeout(r, Math.min(delayUs / 1000, 50)));
}
```

只等时钟、不看任何中止标志。`resetTimeline` 里 `player.flush()` 已把 `streaming`
置 false（同步生效），但**旧循环正卡在 `waitUntilUs(sendAt)`**，最多要等满一个
sendAt 周期（≈2s）才回到 `while (this.streaming && ...)` 条件 —— 这 2 秒里它继续
按作废的 `startTs` 打包、发包。

### P2 `maybeBeginStream` 从不等待旧流

```ts
this.streamPromise = player.streamBridge(...)   // 直接覆盖
```

旧 promise 被丢弃，新循环立刻启动 ⇒ **两条流并行**（上面的 idx 交错就是它）。

## 4. 修法

### P1（`raop.ts::waitUntilUs`）

每轮先查 `!this.streaming || this.destroying`，成立即返回。`flush()` 之后最迟一个
50ms 轮询，旧循环就回到主条件并因 `pull()` 返回 null 而 break。

### P2（`bridgeSession.ts::maybeBeginStream`）

赋值前 `await Promise.race([旧 streamPromise.catch(()=>{}), 1500ms 超时])`，然后清空
引用。1.5s 兜底 —— 起播宁可多等一瞬，也绝不被卡死的旧流拖住；旧流 reject 一律吞掉。

**不改 skip/insert 语义**：本项只做「退出顺序」，所以 `warm-reuse-poisoned` 复位后
仍是补静音（4.14.10 的既有行为），2.1s 可闻但对设备安全。

## 5. 验证判据（真机，缺一不可）

复现条件：会话建立后**第一次**切歌（`skippedFrames>0` ⇒ 下一次 warm-reuse 判
`poisoned` ⇒ `resetTimeline`）。

| 判据 | 期望 |
|---|---|
| `pacing rebase(lag)` | **0 条**（这是本项的核心指标） |
| `idx` 单调 | 日志里不出现两套交错 idx |
| `realigned` | 允许 `insert≈2.1s`（复位补静音，已知遗留），但**不得**伴随 rebase |
| `lossMiss` / `lossReq` | `lossMiss=0`；`lossReq` 仅零星 |
| 可听 | 起播出声，无"全程无声" |
| 连续 5 次切歌 | 全部满足以上；末次后 `pacing rebase` 累计仍为 0 |

## 6. 后续（B，暂缓）

P1/P2 验证通过后，再评估恢复「`resetTimeline` 递增帧代次」（4.14.11 的做法，让复位
后首帧走 `newgen-skip` 不补静音）：

- 若那时 `pacing rebase` 仍为 0，说明当初的 lag 是**并行双流**造成的，skip 本身安全
  （新会话的 skip 已在 15:59:05 实测安全：`skip=94406 insert=0`、`pacing rebase` 零次）；
- 若仍出现 lag，则说明 skip 会抽干设备缓冲，B 永久否决，2.1s 静音保留。
