# 桥时间线复位：旧流/新流并行与 pacing 错位（已闭环）

- 立项：2026-11-19 00:30
- 闭环：2026-11-19 01:00，随 **4.14.13** 发布
- 关联：v4.14.11（引入回归）/ v4.14.12（撤回）/ v4.14.13（双修 + 跳段）/ `docs/airplay-权威方案文档.md`

## 1. 现象

240 全屋组（6 成员，HiVi H5MKII = `00226CFFA0C0`，RAOP/AirPlay1）播放中偶发：

- **起播全程不出声**，手动 seek（重建流）立刻恢复；
- `airplay-bridge` tick 的 `state` 仍报 `live`，`inQueueMs` 正常，`lossMiss=0`；
- 同屏 `pacing rebase(lag)` 每秒一条，量级稳定 `+600~650ms`，`RTP 映射不动`。

## 2. 现场数据（2026-11-18 15:54，UTC）

```

15:54:18 forceNow anchor commandedLeadUs=2050000
15:54:18 newgen-skip frames=71703 ms=1626
15:54:18 realigned insert=0 drop=0 skip=71703
15:54:20 pacing rebase(lag): +614538µs idx=107

15:54:26 pacing rebase(lag): +646916µs idx=26075
```

**`idx` 在 107 / 25788 / 240 / 26075 之间交错，是唯一根因的直接证据**：同时存在两套
`streamBridge` 循环，各自维护自己的 `idx`，都在向同一个 RAOP socket 发包。设备收到两套
时间戳（旧循环用 `resetTimeline` 已作废的 `startTs`，新循环用新锚点）⇒ 缓冲被抽空 ⇒
MUZO 类固件欠载**静默**。

## 3. 根因

### P1 `RaopPlayer.waitUntilUs` 不可中止（致命）

```ts
for (;;) {
  const delayUs = Number(targetUs - nowUs());
  if (delayUs <= 0) return;
  await new Promise((r) => setTimeout(r, Math.min(delayUs / 1000, 50)));
}
```

只等时钟、不看任何中止标志。`resetTimeline` 里 `player.flush()` 已把 `streaming` 置 false
（同步生效），`streamAborted` 也置 true（旧循环 `shouldStop` 成立），但旧循环正卡在
`waitUntilUs(sendAt)`，最多要等满一个 sendAt 周期（≈2s）才回到主条件 —— 这 2 秒里它继续
按作废的 `startTs` 打包发包。

### P2 草案「起新流前 await 旧 streamPromise」——**已否决**

`streamBridge` 返回的 promise 在**整首歌期间都不 resolve**，`await` 它必然等满兜底超时；
实测把 6 次 boundary 压成 1 次（`bridgePhase5.qa2` 直接红），且把起播路径从同步变成异步。
**不要**再往这个方向做。

## 4. 修法（4.14.13 实际落地）

### P1：`waitUntilUs` 每轮检查中止判据

```ts
if (!this.streaming || this.destroying) return;
```

轮询粒度 `50ms → 10ms`：复位后旧循环最多再发 1 帧（8ms）旧包即退出。

### B：`resetTimeline` 清 `lastResampledGen`

复位语义 = 开一条新代次，故必须同时清"上一次重采样的帧代次"；否则新首帧
`genChanged=false`，2.1~2.3s 结构缺口不进 `newgen-skip`（阈值 500ms），被 `aligner.onFrame`
物化成静音。

> 4.14.11 曾单独上线这一行并被真机否决（起播无声）。真因是 P1 未修时的并行双流，
> **不是跳段本身**。两件事必须成对：`bridgeResetGen.test.ts` 末条锁住「P1 必须同时在场」。

## 5. 真机验证（同一 `warm-reuse-poisoned` 条件）

| 版本 | reset 后对齐 | `pacing rebase` | 结果 |
|---|---|---|---|
| 4.14.10（原） | `insert=94434`（2.14s 静音） | 0 条 | 能出声，但每轮复位断 2 秒 |
| 4.14.11（只有 B） | `skip` | 每秒一条 +600ms × 2min | **全程无声** |
| **4.14.13（P1+B）** | `skip=102448 insert=0` | **0 条** | 无静音、正常出声 |

4.14.13 实测细节：`state=live`、`insertedFrames=0`、`late=4`、`lossReq=0`、`lossMiss=0`、
`driftUs=0`、`deltaUs` 稳 +2.06s；新会话首帧基线 `skip=94713 insert=0` 同样安全。

## 6. 「pacing 基准随内容轴同步复位」——**否决：不需要做**

立项时曾判断"复位后内容轴重置了，但 RAOP pacing 基准带着旧值，需要一起复位"。**这个判断
是错的**，原因是把"两条循环各自的 idx"读成了"一条循环里基准被搅乱"。

### 证据：基准本来就整体重建

`streamBridge` 每次被调用（`resetTimeline` 后必然重走 `maybeBeginStream` → 又一次
`streamBridge`），开头就把基准全部重写：

```ts
this.baseTs   = anchor.baseTs >>> 0;   // 与内容轴同一次 planBridgeAnchor 的产物
this.startTs  = anchor.startTs >>> 0;
this.headTs   = anchor.headTs >>> 0;
this.startNtp = anchor.startNtp;
...
this.bridgeLatePackets      = 0;
this.bridgePacingShiftUs    = 0n;      // pacing 偏移清零
this.bridgePacingRebaseAtMs = 0;
let idx = 0;                           // 局部变量，每次调用全新
```

四字段锚点、`pacingShift`、`idx` 全部随新流重建，且与 aligner 零点（`plan.anchorUs`）来自
**同一次** `planBridgeAnchor` —— 天生同源，不存在"没跟着复位"。

### 唯一跨流保留的状态：`lastSentTs`

```ts
} else if (this.lastSentTs >= 0 && anchor.allowTsRewind !== true) {
  const minNext = (this.lastSentTs + CHUNK_LEN) >>> 0;
  const ahead = (minNext - this.startTs) >>> 0;
  if (ahead !== 0 && …) { this.baseTs += ahead; this.startTs += ahead; this.headTs += ahead; }
```

它是**保护**（RTP ts 回退会被设备丢弃），不是污染：三者同量移动 ⇒ `positionSec` 不变；
只往前不往后 ⇒ 正好配合跳段那 2.3s 的前移。

### 什么情况下才真的需要同步复位

只有一种：把 `resetTimeline` 改成**热复用同一条 `streamBridge` 循环**（不重新调用、只改
内部状态）。那时 `idx` / `pacingShift` 不会重建，才需要显式复位。**当前没有这条路径** ——
`resetTimeline` 设 `streamAborted` → 旧循环 break → 下一帧重新 `maybeBeginStream`，每次都是
全新的函数实例，局部状态天然隔离。

## 7. 回滚

- 只回滚 B ⇒ 回到 4.14.10 行为（复位补 2.14s 静音，能出声）；
