# 群组切歌等待自适应 · 调研与方案

- 日期：2026-11-02
- 状态：**P1 + P2 已落地并灰度（2026-11-02）**；纯桥默认 ON，混合组待第二阶段开启（见 §5.1）
- 范围：Sendspin 组泵（`backend/src/services/sendspin`）+ AirPlay 桥（`backend/src/services/airplay`）
- 目标：把「每首歌切换要等 4~5 秒才出声」压到 1~2 秒，且**不吞新歌开头、不破坏组内同步**

---

## 0. 结论摘要（TL;DR）

1. 当前「切歌等待」是**两道独立的固定量**，与设备是否真的需要这么久没有关系：
   - **组时间线锚点 lead**：混合组 = 组值 `mixed_anchor_lead_ms`（「全屋」当前被手动设为 **4000ms**；未设时走默认 5000ms）；纯桥组 = 冷启动固定 4.5s。
   - **桥投递切歌垫片** `pendingTrackLeadUs`：冷 2.5s / 暖 0.8s / 预取就绪 0。
2. 这个等待是**纯静默**，不是解码预算：锚点在**首帧已经解码就绪之后**才计算（`anchor = handoffUs ?? nowUs() + lead`），且每个新曲的 `pushLoop` 都会把 `timelineBaseUs` / `cursorUs` 归零，所以 `now + lead` 就是实打实的额外静默。
3. 2026-10-27 定标「5s 才不吞开头」的前提**已经部分失效**：该定标是「切歌时桥会话重启（0xE0 重锚）」场景；v4.11.x 的 S2（`MF_BRIDGE_TRACK_KEEP_QUEUE` 缺省 ON）让**自然换歌不再 FLUSH/重启/重锚**，接收端不再需要 2~3s 重建窗口。
4. S1（下一首预取）在**纯桥组自然连播**上已经能把等待降到 0（交接锚点 = 上一首时间线终点）；但它**只服务纯桥组**，混合组被代码硬性排除。**「全屋」正是混合组**，所以它的自然连播也吃满 4s，`handoff` 恒为 `-`。
5. 对标 MA：MA 不是固定 5s，而是 **暖 2.5s / 冷 4.5s**（`BRIDGE_WARM_START_LEAD_MS = 2500`，`BRIDGE_COLD_START_LEAD_MS = 4500`），并且 `min_buffer = 1s`。纯桥分支目前硬编码 `warm:false`（没用暖档）；混合组则完全按组值/默认，不分冷暖。
6. 推荐路线（分三期，先低风险分档，再做结构性「接续锚点」，最后做混合组解码前滚）：
   - **P1 分档**：自然换歌且会话暖 → 2.5s；重启型边界 → 4.5s；预取就绪 → 0。收益约 −1.5~2.5s/首。
   - **P2 接续（推荐主方案）**：自然换歌时锚点 = `max(上一首内容终点, now + 桥投递地板 1.75s)`，把「新歌延后 4s」换成「紧接旧曲尾巴」，静默可压到 **≈1s**，且**时间戳跳变比现在更小**（对混合组直连 esp32 更安全）。
   - **P3 混合组解码前滚**：当前曲播放期预解码下一首（不污染 ring），边界瞬接。把 P2 的地板从「解码不确定」变成确定值。

### 1.3 为什么是「纯等待」

- 首帧产出路径：`decode → 首帧就绪 → 计算 anchor`。因此 `now + lead` 里的 `now` 已经含了解码耗时。
- 新曲 `pushLoop` 从 `cursorUs=0` 开始，锚点不会被上一首的游标 clamp 掉（`clamped = max(anchor, cursorUs)` 在首个锚点时 `cursorUs=0`）。
- 结论：**lead 值 = 用户实际多等的秒数**（再加上设备侧本来的调度缓冲与排空尾巴）。

### 1.4 与 MA 对比

| 项 | MA | MusicFlow 现状 |
|---|---|---|
| 暖启动 lead | 2500ms | 纯桥**未使用**暖档（硬编码 `warm:false` → 4.5s）；混合组 5s |
| 冷启动 lead | 4500ms（2500 + 2000 连接预算） | 4.5s（线上 4.11.0 为 4.0s） |
| 持续缓冲 | `min_buffer_ms=1000` | `BRIDGE_MIN_BUFFER_US=1s`（一致） |
| 边界接续 | 暖复用 + `MAX_DEVICE_BUFFER_SECONDS=8` 限流 | 有 S2 保留队列，但锚点仍回 `now + lead` |

## 2. 候选方案

> 下面 5 个方案按「风险从低到高、收益从小到大」排列，可叠加。

### P1 · 分档自适应（低风险，先做）

**做法**：按「边界类型 × 会话冷暖 × 预取就绪」三态决定 lead，而不是一个固定值。

| 边界 | 判定 | lead |
|---|---|---|
| S1 预取交接 | `handoffUs != null` | 0（保持现状） |
| 自然换歌 + 会话暖 + keepQueue | `reason=track && !manual && bridgeWarmAttach` | 纯桥 2.5s；混合 `max(2.5s, 投递下沿+补投周期)` = 2.5s |
| 自然换歌但会话冷 | 桥上冷启/重建句柄 | 4.5s |
| 手动 上/下一首、seek、rehost | 重启型边界 | 4.5s（保持现状） |
| 组级手动覆盖 | `mixed_anchor_lead_ms != 0` | 用户值优先（现语义不变） |

> 注意：**「全屋」当前就是手动 4000**。P1 落地后如果只改默认值，这个组不会有任何变化；要看到收益，需要把组值改回 `0`（自动），或由前端提供「恢复自动」。这一点必须写进 UI 文案，否则会被误判为「优化没生效」。

**收益**：自然连播 −1.5~2.5s/首；与 MA 口径一致。
**风险**：若某设备即使暖会话也要 >2.5s 才接得住，会吞开头（需要真机复测）。
**改动面**：`streamEngine` 锚点分支需要能读到「是否 manual」「是否暖复用」（`bridgeWarmAttach` 已在 `server.ts` 上有；manual 意图目前只在 `bridgeSession` 内部，需要经组泵透传一个只读标志）。

### P2 · 接续锚点（推荐主方案，结构性问题一次解决）

**现状问题**：自然换歌时，上一首的尾巴还在设备缓冲里（S2 保留队列），而新歌却被锚到 `now + 4/5s`。两者之间就是**人为挖出来的空洞**。

**做法**：自然换歌时，把新锚点改为「上一首内容终点」，只在必要时抬到桥能接住的地板：

```
anchor = max(prevContentEndUs, nowUs() + bridgeFloorLeadUs)
```

- `prevContentEndUs`：上一首 `pushLoop` 最后一条已产出内容的时间戳（需新增只读字段，由组泵持有）。
- `bridgeFloorLeadUs`：带桥的组 = `BRIDGE_PUSH_FLOOR_US(1.5s) + BRIDGE_PUSH_TICK_MS(0.25s) = 1.75s`；纯直连组 = `ANCHOR_SAFE_LEAD_US(0.8s)`。
- 只用于「自然换歌 + 会话未重启」；手动/seek/rehost 仍走冷 lead。

**为什么安全**：

1. 锚点仍在首帧就绪后计算，`prevContentEnd` 若已过期会被 `max` 抬到 `now+1.75s`，不会把内容排到过去。
2. 新时间戳**不再跨过**旧尾巴（现在 `now+4s` 反而可能大于或小于旧尾巴，属于隐性乱序风险）；接续锚点让「同组同内容零点」更连续，对混合组直连 esp32（硬同步 5ms）是**跳变更小**的改动。
3. 桥投递窗口 `[now+1.5s, now+2.5s]` 天然满足：锚点 ≥ now+1.75s 的帧会在后续 tick 正常投递。

**收益**：自然换歌静默从 ~4s 降到 **≈0.7~1.2s**（旧曲尾巴排空 0.8s + 地板差）。
**风险**：`prevContentEnd` 若在很远的未来（曲末排空策略变化），等待会等于尾巴长度 —— 但不会超过现在的 4s；需要给一个 `MAX_CONTINUITY_WAIT_US`（例如 2.5s）做上限。
**前置**：确认曲末排空（end-drain）后 `prevContentEnd` 与墙钟的实际关系；建议先加只读埋点观测一首歌，不改行为。

### P3 · 混合组解码前滚（根治，收益最大）

**做法**：当前曲还没播完时，先把下一首解到 PCM/流窗口（**不写 ring**，只做准备），边界时直接从接续锚点开始推帧。

- 纯桥组已有的 S1 是「解码 + 写 ring 预热桥队列」；混合组不能写 ring（会被直连成员提前消费、与正片重复造成跳变）。
- 折中：混合组只做「解码前滚」，ring 在边界后由正片直接续上；因为解码已完成，首帧立即可用，P2 的 `max()` 几乎不会落到解码上。

**收益**：把 P2 的不确定性（解码 0.5~2s）消掉，稳定落在 1.75s 地板附近；混合组也能享受。
**风险**：并行解码占 CPU/内存；seek/手动/停止必须取消（现有 S1 已有取消语义，可复用）。
**工作量**：中高（涉及 `streamEngine` 预取对象拆成「已解码资源」与「已写 ring」两种状态）。

### P4 · 每设备就绪学习（自适应调参）

**做法**：桥侧记录每次边界到「首包成功排程/首帧被接住」的耗时，按设备维护 EWMA；组 lead = 组内各设备需求的最大值 + 余量，夹在 `[1.75s, 4.5s]`。

- 判定「没接住」目前只有间接信号：对齐器在流首丢弃/跳过帧、`reAnchored` 次数、首包晚到量。
- 真正「设备吞掉开头」无法从服务端直接观测，只能在标定时用抓包/人耳确认。
- 因此 P4 更适合做**兜底与个性化**（HiVi 这类需要更深的设备单独抬高），而不是主收益来源。

**收益**：不必为最慢设备让全组陪等；组内可收敛到「刚好够用」。
**风险**：学习样本偏差会导致偶发吞音；需要上下限 + 手动覆盖 + 可回退。

### P5 · 体验层兜底（可立即做，不涉及时序）

- 「切歌等待」弹窗从「一个 0~30000ms 数字」改为：**自动（推荐）/ 快速 ~2s / 平衡 ~3s / 稳定 ~5s / 自定义**，并注明「下一首生效」。
- 播放器页显示「上一次切歌实测静默」与「本组学习值」，让用户能看到自适应是否生效。
- 保留环境变量回退（见 §5）。

## 3. 推荐路线

| 期 | 内容 | 预期 | 前置 |
|---|---|---|---|
| **P0** | 补埋点（不改行为）：每边界记录 `mode / lead / prevEnd / pad / 首包时刻 / 对齐器丢弃` | 拿到真实分布，验证 §1 结论 | 无 |
| **P1** | 分档自适应（自然暖 2.5s / 重启 4.5s / 预取 0） | 自然 −1.5~2.5s | P0 数据确认 |
| **P2** | 接续锚点（`max(prevEnd, now+1.75s)`），先纯桥组灰度 | 自然 ≈1s，且时间戳更连续 | P1 稳定 + 曲末排空关系确认 |
| **P3** | 混合组解码前滚 → P2 扩到混合组 | 混合组 ≈1.75s | P2 纯桥零吞音 |
| **P4** | 每设备就绪学习（可选） | 个性化兜底 | P2/P3 有稳定基线 |

**不建议**：直接把默认 5s 改成 2s 就上线。混合组当前 5s 是「重启型边界」的定标值，直接下调会复现「吞开头」；必须先吃 P1 的冷暖分档。

## 4. 验收判据与实验矩阵（必须真实数据）

### 4.1 指标

1. **切歌静默**：上一首最后一个可听样本 → 新歌第一个可听样本（抓包/人耳双证）。
2. **开头完整性**：新歌前 0.5s 不缺失（抓包对齐内容）。
3. **组内同步**：同刻包内音频内容一致；直连 esp32 首帧跳变 ≤5ms。
4. **桥健康**：`queuePeakMs` 不触 8s 硬上限；无重连风暴；`reAnchored` 不异常增长。

### 4.2 矩阵（每格 ≥10 次）

| 场景 | 群组形态 | 关注 |
|---|---|---|
| 自然连播（自动下一首） | 纯桥 | 静默、`handoff` 是否命中 |
| 自然连播 | 混合（桥+直连） | 静默、直连是否跳变 |
| 手动下一首/上一首 | 纯桥 / 混合 | 是否仍吞开头（应保持 4.5s） |
| 曲中 seek | 纯桥 / 混合 | 重锚、断流恢复 |
| 组内不同品牌 AP1 | 混合 | 同步误差、`padUs` 归零时机 |

### 4.3 通过标准（建议）

- 自然换歌静默：P1 ≤2.5s；P2 ≤1.2s；P3 ≤1.8s（混合）。
- 吞开头：0 次。
- 组内同步：满足现有抓包判据（同刻包内容一致，lag≈0）。
- 回退开关打开后，行为与 v4.11.1 逐字节一致（除日志）。

## 5. 开关与回滚设计（已按实现对齐）

| 开关 | 缺省 | 作用 |
|---|---|---|
| `MF_BRIDGE_LEAD_MODE` | `tiered` | `fixed` = 回到 v4.11.1 行为（恒冷 4.5s）；`tiered` = P1 分档 |
| `MF_BRIDGE_CONTINUITY_ANCHOR` | `1`（**纯桥默认 ON**） | P2 接续锚点总闸；`0` 关闭 |
| `MF_BRIDGE_CONTINUITY_MIXED` | `0`（**混合组默认 OFF**） | 第二阶段：`1` 才让混合组也吃接续锚点 |
| `MF_BRIDGE_CONTINUITY_MAX_WAIT_MS` | `3000` | 旧尾巴在未来的最长等待上限（防排空尾巴过长） |
| `MF_BRIDGE_CONTINUITY_STALE_MS` | `10000` | 旧尾巴在过去的过期阈值（超时则回退暖/冷 lead） |
| `MF_BRIDGE_TRACK_KEEP_QUEUE` | 开（S2） | P2 前置：自然换歌不清桥队列；设 `0` 连带关闭接续 |
| `MF_BRIDGE_MIXED_PREDECODE` | `0` | P3 混合组解码前滚（未实现，预留） |
| `BRIDGE_MIXED_GROUP_ANCHOR_LEAD_MS` | 空 | 既有全局覆盖，保留 |
| 组级 `mixed_anchor_lead_ms` | 0=自动 | 用户覆盖优先，语义不变 |

原则：**任何自适应都必须能被组级手动值覆盖**；自动值只在用户未设置时生效。

## 8. P3 落地结论（2026-11-02 真机实测，取代第 5/6 节的旧推断）

**目标**：去掉前端手动「切歌延迟 / 切歌等待」，由后端对纯桥组与混合组自动决定起播 lead；
既要稳（不吞歌曲开头），又要低延迟。

### 8.1 判据修正：锚点连续 ≠ 无吞歌

上一轮曾以「锚点精确连续 + 无 BOUNDARY / 无 RAOP FLUSH」判定通过，但桥侧日志显示每次换歌仍有
`insertedFrames`（补静音=可闻间隙）或 `skippedFrames`（跳段=可闻丢音）增长。
因此 P3 的验收判据改为**桥侧内容轴指标**：

- 换歌后 8~12s 内 `insertedFrames` / `skippedFrames` / `droppedFrames` **不得增长**；
- 不得出现 `pad-insert`、`realigned ... skip=`、`timeline-reset warm-reuse-poisoned`、`RAOP FLUSH`；
- 泵侧 `timeline anchored` 的 `handoff` / `contig` 与上一曲内容尾精确相等（差值 0）。

### 8.2 根因（三处，均已修复）

1. **`resetPushMeter()` 无条件清 ring**：`playGroupCore` 用 `close({keepBridgeDelivery:true})`
   保住的旧曲尾 / 预取帧，会在新 `pushLoop` 起手被这一拍 `recentByGroup.clear()` 清掉 ⇒
   桥在边界后断粮 ⇒ 补静音 / 跳段。
   修复：新增一次性 `keepRingForNextPush` 标志，`close(keep)` 置位、`resetPushMeter()` 消费并跳过清 ring；
   其余场景（seek / 真实停止 / 换组）行为逐字节不变。
2. **S1 预取路径 `g.close()` 清掉新曲预取帧**：预取白做，边界后仍静默 ~3.8s。
   修复：非接续分支改为 `close({ keepBridgeDelivery: keepQueueForPrefetch })`，
   预取帧与旧曲尾属于同一条跨曲时间线，一并保留。
3. **曲末续静音与新曲首帧 ts 重叠**：续静音写进 ring 占 `[contentEnd, contentEnd+fill]`，
   若 `lastContentEndUs` 仍取 `cursorUs`，下一曲首帧会落在静音区间内、被水位判「已投过」跳过。
   修复：内容尾改为 `contentTailUs`（有排空时后移到静音尾，无排空时与 `cursorUs` 同值）。

### 8.3 四组真机实测（240 容器，三首 44s/69s/73s，各两次自然换歌）

| 组合 | 走哪条路径 | 锚点连续性 | 桥侧指标 |

| 纯桥 pb（S1 开） | `handoff` 交接 | base→+44.000s→+69.000s | `insertedFrames=83703` 恒定、`skipped=0` |
